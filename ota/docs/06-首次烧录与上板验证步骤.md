# 06 · 首次烧录与上板验证步骤

> 目标：从零把两块板变成"可 OTA 升级"的系统，并按**风险从低到高**逐级验证，
> 最后跑通"升级 → 试运行 → 落定 / 回滚"。
>
> ⚠️ **本方案的固件从未在真实硬件上运行过**（开发环境无板、无 CAN 分析仪）。
> 因此本文所有判据都写成"可观察的现象"，请逐步核对，不要跳步。

---

## 0. 硬件与前置条件

### 0.1 最小可用配置

| 项 | 数量 | 说明 |
|---|---|---|
| STM32G474VE 板 + SN65HVD230 | **2 块** | 板 A = OTA 主机（串口↔诊断CAN 桥），板 B = 被升级的目标节点 |
| CAN 终端电阻 120 Ω | **2 个** | 接在总线两端（CANH–CANL）。**缺终端电阻是升级失败的第一大原因** |
| USB 转串口（板载或外接） | 1~2 | 至少板 A 要有（PC 经它下发诊断帧）；板 B 有则便于看 BL 日志 |
| ST-Link / DAP-Link | 1 | 首次烧录两个固件（之后 OTA 不再需要） |

总线接线：`板A PB12/PB13 ↔ 收发器 ↔ CANH/CANL ↔ 收发器 ↔ 板B PB12/PB13`。

### 0.2 三个编译期宏（**必须确认**）

| 宏 | 位置 | 板 A（OTA 主机） | 板 B（目标节点） |
|---|---|---|---|
| `CAN_NODE_ROLE` | `G474/Drivers/User/Inc/can.h` | `CAN_NODE_A` | `CAN_NODE_B` |
| `CAN_DEBUG_SELFTEST` | 同上 | `0` | `0` |
| `VECT_TAB_OFFSET` / `IROM1` | 工程宏 / uvprojx | `0xC080` / `0x800C080` | 同左（都跑在 Slot A） |

> ⚠️ **本仓库自带的 `G474.uvprojx` 是"Slot A 版"。**
> 若这块板要当 **Slot B**（A/B 对调），需改 `IROM1 → 0x8040820`、`VECT_TAB_OFFSET → 0x40880`。
> 首次验证**两块板都烧 Slot A 版**即可（B 板只在以后 OTA 时才会被写入 Slot B）。
>
> ⚠️ 改完 `can.h` 后，**每次用 Keil GUI 保存过工程都要重跑**：
> ```
> python ota\scripts\check_ota_intact.py    # 确认 OTA 改动还在
> python ota\scripts\fix_app_irom.py        # 确认链接基址还是 0x800C080
> ```

## 1. 阶段一：烧录 Bootloader 与 APP（**顺序不能错**）

```
① 先烧 BL.hex                  → 上电停在 BL，串口打印 recovery 等待刷写
② 再烧 <槽>_factory.hex        → 复位后 BL 校验通过并跳转 APP
```

### ⚠️ 关键：首次烧 APP 必须烧 **factory 镜像**，不能烧裸 APP

本方案的契约是 **镜像头由设备在激活阶段（`FF02`）自行合成**（"模式A：设备侧写头"）。
因此：

* 通过 **OTA** 刷进去的 APP，槽基址处**有** 32B 头；
* 用**编程器直接烧** Keil 生成的裸 APP（`G474_A.hex`，起始 `0x0800C080`）时，
  槽基址 `0x0800C000` 处**没有**头 → `BL_ImageReadHeader()` 失败 →
  BL 停在 recovery，**表现为"上电没反应"**（LED/LCD/串口全无输出）。

正确做法：先用工具把裸 APP 打包成"产线镜像"（32B 头 + APP），再烧到**槽基址**：

```powershell
# 1) 生成产线镜像（起始地址 = 槽基址 0x0800C000）
python ota/scripts/make_factory_image.py --hex firmware/G474_A.hex --slot A --version 3.0
python ota/scripts/make_factory_image.py --hex firmware/G474_B.hex --slot A --version 3.0

# 2) 烧录（hex 自带地址）
python ota/scripts/flash.py --file firmware/G474_A_factory.hex   # 板A
python ota/scripts/flash.py --file firmware/G474_B_factory.hex   # 板B
```

工具会自校验生成物（magic / hdrCrc / payloadCrc / SP / 复位向量），
并按 BL 的校验逻辑回读一遍，确保"烧进去就能被接受"。

**为什么必须先烧 BL**：APP 链接在 `0x0800C080`，若 `0x08000000` 是空的，
MCU 复位会从那里取初始 SP 与复位向量 → 取到 `0xFFFFFFFF` → **HardFault 死机**。

### 1.1 判据

| # | 现象 | 说明 |
|---|---|---|
| 1.1 | 只烧 BL 时，串口出现 `BL: recovery mode (wait diag)` 之类日志 | BL 启动且找不到有效 APP → 进 recovery（符合预期） |
| 1.2 | 再烧 APP 并复位后，串口出现 APP 横幅 `=== STM32G474 CAN Node v3.0.0 \| role:... ===` | **说明 BL 校验通过并成功跳转**（这是整条链路的第一个关键证据） |
| 1.3 | APP 横幅后出现 `ota: slot 0 state ...` | `Ota_Init()` 读到了控制区、识别出运行在 Slot A |

> 若 1.2 一直不出现、串口反复打印 recovery：说明 BL 校验 APP 没通过。
> BL 会把原因写进 `lastError`，用调试器看 `OTA_Cfg`，或读 `22 F183`（槽 CRC）比对。

## 2. 阶段二：基线 CAN 功能验证（**动 OTA 之前先确认没打坏原有功能**）

两块板都烧好 APP 后，复位。板 A 应每秒发 `0x321`，板 B 回 `0x322`。

| # | 操作 | 期望 |
|---|---|---|
| 2.1 | 串口 A 输入 `stats` | `tx` 持续增长、`rx` 持续增长、`txErr=0`、`ovr=0`、`busOff=0` |
| 2.2 | 观察两块板 LED1 | **同步闪烁**（板 A 按板 B 应答里的 LED 状态同步） |
| 2.3 | 板 A 输入 `sniff on` | 能看到 `RX ... 321 ...` 与 `RX ... 322 ...` 交替 |
| 2.4 | 板 B 拔掉 CANH 再插回 | 板 A 的 `stats` 出现 `busOff`/`errPas` 增长，**随后自动恢复**（指数退避） |

> 2.1 若 `tx` 不增长 → 发送侧没工作；若 `tx` 增长但 `rx` 为 0 → **终端电阻或接线问题**（这是最常见的坑）。
> 2.4 恢复时间会按 1s→2s→4s… 递增，属正常设计。

## 3. 阶段三：**硬性门槛**——OTA 服务与绝对保护区（不动真固件）

这一步**不刷任何东西，只发诊断请求**，用来验证最危险的三条保护。用板 A 的串口隧道或 USB-CAN 工具。

> 隧道用法：板 A 串口输入 `tun on`，此后 PC 发出的每一行 `tx` 都会变成一帧 CAN；
> 板 A 收到的诊断帧会以 `RXTX <id> <dlc> <hex>` 打印出来。详见 `ota/docs/03` §6。

| # | 发什么 | 必须得到 | 这条在证明什么 |
|---|---|---|---|
| **3.1** | `10 03` （进扩展会话） | `50 03 00 32 01 F4` | OTA 服务可用、`P2*=5000ms` 声明正确 |
| **3.2** | `22 F1 84` （读能力位图） | `62 F1 84 07` | 目标节点已识别为 OTA 目标 |
| **3.3** | `22 F1 81` （读活动槽） | `62 F1 81 00` | 当前运行在 Slot A |
| **3.4** | 🔴 `34 00 44 08 00 00 00 00 00 10 00`<br>（请求下载到 `0x08000000`） | **NRC `7F 34 31`** | **绝对保护区有效——BL 区不可被 OTA 擦写** |
| **3.5** | 🔴 `34 00 44 08 00 C0 20 00 00 10 00`<br>（请求写**正在运行的** Slot A） | **NRC `7F 34 22`** | 活动槽互斥——运行中的固件永不被覆写 |
| **3.6** | `36 00 AA BB` （块序号 0，非法） | **NRC `7F 36 73`** | 块序号校验 |
| **3.7** | `2E F1 90 01`（请求下次进 BL） | `6E F1 90` | F190 服务可用 |

> 🔴 **3.4 与 3.5 是本方案的生死线。** 只要其中一条返回了正响应或错误地被接受，
> **立刻停止上板，回到代码修**——那意味着 BL 或运行中的固件可能被擦掉。

> 3.5 的地址：Slot A 的 APP 链接基址 = `0x0800C000 + 0x20 = 0x0800C080`，
> 大端字节为 `08 00 C0 20`。Slot B 则是 `08 04 08 20`。

## 4. 阶段四：准备可区分的固件对

要"看得出升级成功了"，两个版本必须肉眼/串口可区分。

```powershell
# 1) 改版本号，让 v2.0 可识别
#    编辑 G474/Drivers/User/Inc/can.h:  CAN_APP_VERSION "3.0.0" -> "3.1.0"
& $uv -r "G474\MDK-ARM\G474.uvprojx" -j0 -o "$env:TEMP\app_v2.log"
python ota\scripts\verify_layout.py

# 2) 把 bin 加 32B 镜像头打包成 .ota（负载地址 = Slot B 的 APP 基址）
python ota\tools\ota_host.py --pack "$env:TEMP\app_v2.bin" --load-addr 0x08040880 --version 2.0 -o "$env:TEMP\app_v2.ota"

# 3) 离线自检：完整打印报文序列 + 校验和自洽
python ota\tools\ota_host.py --dry-run --verify "$env:TEMP\app_v2.ota"
```

> `--pack` 的输入是 Keil 生成的 `.bin`。Keil 默认只出 `.hex`，
> 用它自带的 `fromelf --bin` 转一下，或在 Options → Output 勾选生成 bin。

**再次确认 3.4/3.5 通过后**，才可以进入阶段五。

## 5. 阶段五：完整升级 + 试运行 + 回滚

### 5.1 正常升级 A → B

```powershell
python ota\tools\ota_host.py --port COMx "$env:TEMP\app_v2.ota" `
       --precheck --verify --timeout 6.0
```
> 串口隧道模式（板 A 中继）加 `--tunnel`；若走 USB-CAN 直连则不带。
> **`--timeout 6.0` 很重要**：全槽擦除约 2.6 s，默认 3.0 s 贴近边界。

| # | 观察 | 期望 |
|---|---|---|
| 5.1.1 | 工具输出 | `擦除预算: 目标区段 ... ≈ 104 页，预计擦除 ~2.6s` |
| 5.1.2 | 传输 | **210 个 `0x36` 块**（每块 1016 字节），每块回 `76 <seq>` |
| 5.1.3 | 收尾 | `37`（带 4 字节 CRC）→ `31 01 FF 01` 回 `00` → `31 01 FF 02` 回 `00` → `11 01` |
| 5.1.4 | **板 B 串口** | 复位后 BL 打印 `TRIAL_B`、`trialLeft` 从 3 递减；随后 APP 打印 `ota: TRIAL boot (slot 1, left 2)` |
| 5.1.5 | 约 3 秒后 | APP 打印 `ota: trial committed (IDLE)` —— 新固件**转正** |
| 5.1.6 | 再读状态 | `22 F1 80` → `01`(IDLE_B)，`22 F1 81` → `01`(Slot B)，`22 F1 82` 显示 B=2.0 |
| 5.1.7 | **断电重上电** | 仍运行 B 版、且**不再进 TRIAL**（这是"落定"的最终证据） |

### 5.2 🔴 回滚验证（本轮最有价值的一步）

目的是证明"升级失败**不会变砖**"。做法：传一个 CRC 正确但**跑不起来**的固件。

| # | 做法 | 期望 |
|---|---|---|
| 5.2.1 | 造一个"自杀版"APP：让 `Ota_Task()` 的自检条件永不满足（例如把 `CAN_GetStats()->rxCount > 0` 改成 `> 0xFFFFFFFF`），编译打包 | —— |
| 5.2.2 | 用它走一次完整升级（应能通过 `FF01` 与 `FF02`） | 激活成功，进入 `TRIAL_<槽>` |
| 5.2.3 | 连续复位 3 次 | 前两次 BL 跳进新固件但 APP 不自证；`trialLeft` 逐次递减 |
| 5.2.4 | **第 4 次复位** | BL 打印 `trial exhausted -> rollback`，**自动切回旧固件**并正常运行 |
| 5.2.5 | 读状态 | `22 F1 80` → `00`(IDLE_A)，即已回到原版本 |

**判据：全程无需人工干预，设备自己退回旧固件。** 这条不通过，"敢升级"就无从谈起。

### 5.3 🔴 掉电续传 / 掉电不砖

| # | 做法 | 期望 |
|---|---|---|
| 5.3.1 | 升级传输到约 50% 时**直接断电** | —— |
| 5.3.2 | 重新上电 | **正常启动旧固件**（控制区未被改动，仍指向原活动槽） |
| 5.3.3 | 再走一次完整升级 | 应能正常完成（目标槽被重新擦除，残留数据无影响） |

**判据：5.3.2 必须正常启动。** 若卡在 BL 或反复复位 → 控制区写入不是掉电安全的，
回到 `ota/docs/04` §2 检查写策略。

### 5.4 综合与边界

| # | 检查 | 期望 |
|---|---|---|
| 5.4.1 | 升级过程中业务心跳（`0x321/0x322`） | **不中断**；两板 LED 仍同步 |
| 5.4.2 | 读 `22 F002`（通信统计） | `rxOverruns == 0`、`txEvtLost == 0`（**优化后的重点**：1016B 块会产生 146 个连续帧） |
| 5.4.3 | 实测总耗时 | CAN 直连约 **9~15 s**；串口隧道约 **70~90 s** |
| 5.4.4 | 连续升级 10 次（A↔B 交替） | 每次都成功、`seq` 单调增长、无需进 recovery |
| 5.4.5 | 控制区损坏自愈：用调试器把 `0x08000000` 与 `0x08040000` 两页全写 `0x00` | 上电后 BL 重建默认配置 → 进 recovery；**能正常被上位机刷写，不死锁** |

## 6. 故障定位速查

| 现象 | 最可能原因 | 怎么查 |
|---|---|---|
| 上位机完全收不到应答 | ① 无终端电阻 ② 过滤器没放开 `0x7E8` ③ 隧道没 `tun on` | 读 `22 F002` 看 `rxCount` 是否增长；`sniff on` 抓包 |
| `Undefined symbol hiwdg` / 链接报错 | Keil 覆盖了 `main.c` | `python ota\scripts\fix_main_c.py` |
| APP 链到 `0x08000000`（应 `0x0800C080`） | `OCR_RVCT4` 与 `IROM` 不一致，Keil 重生成 scatter | `python ota\scripts\fix_app_irom.py --apply` |
| 升级成功但复位后仍跑旧版 | `FF02` 未成功 / 控制区没写进去 | 复位前读 `22 F180`，应为 `TRIAL_x` |
| 复位后直接进 recovery | 新镜像的 SP / 复位向量非法 | BL 日志会打印具体 `OTA_ERR_*`；读 `22 F183` 比对 CRC |
| 反复"升级→回滚" | APP 自检条件太严（CAN 实际未通信） | 看 APP 日志 `ota: self-check not passed` |
| `diag: isotp timeout` | STmin 太小 / 总线错误 | 读 `22 F002` 的 `errPassiveCount`、`busOffCount` |
| 擦除后校验总失败 | 目标槽地址算错（漏了 32B 镜像头） | `loadAddr` 必须 = 槽基址 + `0x20` |
| 设备完全无响应（疑似变砖） | BL 被擦 / 选项字节被改 | SWD 读 `0x08000000` 是否为有效向量表；全片擦除后按 §1 重烧 |
| 隧道模式传输很慢或丢帧 | 串口打印速度（≈2.3ms/帧）追不上 CF（2ms/帧） | 用 `--block-size 500`；读 `22 F002` 确认 `rxOverruns` |

## 8. 出问题时先做这三件事

1. **确认改动还在**：`python ota\scripts\check_ota_intact.py`
2. **确认链接地址对**：`python ota\scripts\fix_app_irom.py` + `python ota\scripts\verify_layout.py`
3. **留下现场证据**：串口日志全量保存（BL 与 APP 都要），以及上位机的 `--log` 报文日志
   （`ota_host.py --log run.log`，之后可用 `--replay` 离线复盘）

> 这三步能把"固件问题"与"环境问题（被覆盖/链接错/接线错）"分开——
> 本次开发过程中，**绝大多数坑都属于前两类，而不是协议设计本身**。
