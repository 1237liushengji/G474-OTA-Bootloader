## 一、当前确认的物理链路（全部由实测/目视确认）

```
PC ──USB线── [板载 CH340K] ──板上走线── MCU PA9(TX) / PA10(RX)
     （左侧 USB转串口 口，芯片就在口旁）
```

| 项 | 状态 | 来源 |
|---|---|---|
| 黑线插口 | 左侧 **`USB转串口`** | 用户确认 + 照片 |
| 该口旁芯片 | **CH340K** 存在 | 用户目视 |
| PA9/PA10 外接杜邦线 | **无**（空着） | 用户确认 |
| `USB设备` 口 | 走 MCU 原生 USB（PA11/PA12）；**本工程无 USB 设备固件** | `grep` 结果为空 |

## 二、🔴 核心矛盾（这是 P2 的真正难点）

| 方向 | 状态 | 证据 |
|---|---|---|
| **MCU → PC**（TX, PA9）| ✅ **通** | 完整 BL+APP 启动日志能被 PC 收到（1525 字节实锤）|
| **PC → MCU**（RX, PA10）| 🔴 **不通** | PC 连写 **200×32 = 6400 字节**（零写入错误），MCU 侧 `edges/20ms=0`、`rxIrq=0` |

**矛盾点**：两个方向**共用同一颗板载 CH340K、同一段板上走线**。
TX 通而 RX 不通，最可能是 **CH340K 的 TXD 引脚到 MCU PA10 那一段断了**。

### 2.1 已排除的软件侧（全部实测）

| 检查项 | 实测值 | 判定 |
|---|---|---|
| PA10 配成 AF7 | `MODER=ABEBFFFF` | ✅ |
| PA10 空闲电平 | `IDR` bit10 = 1 | ✅ |
| USART1 + RX 使能 | `CR1=0x002D` = UE\|RE\|TE\|RXNEIE | ✅ |
| 波特率 | `BRR=0x0516` | ✅ |
| RX 中断使能 | `ISER1=0x00000020` | ✅ |
| PA10 是否有其它代码占用 | `grep` 全项目 → **无** | ✅ |
| `MX_GPIO_Init()` 是否动了 PA10 | gpio.c **空实现** | ✅ |

**⟹ 软件侧干净，问题在 CH340K TXD → PA10 的物理段。**

## 三、可能的具体故障点（按排查成本排序）

| # | 可能 | 验证方法 |
|---|---|---|
| 1 | **CH340K TXD 与 PA10 之间串了 0Ω/跳线/焊盘未短接** | 目视板子，找 `USB转串口` 芯片旁到 PA10 的走线；看有无未焊的 0Ω 或跳线帽位 |
| 2 | **该段走线虚焊/断路** | 万用表通断档：CH340K 的 TXD 引脚 ↔ MCU PA10（J4 pin5）|
| 3 | **CH340K 的 TXD 被接到了别的脚**（设计变体/板子版本差异）| 同上，量 CH340K TXD 实际连到哪个 MCU 脚 |
| 4 | **CH340K 芯片本身 TXD 损坏** | 换板对比；或外接 USB-TTL 接到 J4 验证 MCU 侧 RX 是否好 |
| 5 | **板载 CH340K 与 J4 的 PA10 是"两套"**（板载口只接了某个子集）| 对比两块板行为是否一致 |

## 四、⭐ 决定性隔离实验（推荐先做这个，成本最低、信息量最大）

**用外接 USB-TTL 模块直接接到 J4 的 PA10，绕开板载 CH340K。**

- 外接模块 `TXD` → **J4 pin5（PA10）**
- 外接模块 `RXD` → **J4 pin6（PA9）**（可选，仅 TX 验证的话可不接）
- 外接模块 `GND` → **J4 pin3（GND）**
- **DTR / RTS / CTS / DSR / VCC 全部拔掉**（J4 pin7 经 R4=1.5kΩ 接 RST，接了会反复复位）

**判据**：

| 结果 | 结论 | 下一步 |
|---|---|---|
| 外接模块一发数据，MCU `edges>0` 且 `rxIrq>0` | **MCU 侧 RX 完好** → 故障**100% 在板载 CH340K → PA10 那段走线/器件** | 修板（补焊 0Ω/跳线）或改用 J4 外接方案 |
| 外接模块也 `edges=0` | **MCU 的 PA10 引脚本身有问题**（虚焊/损坏）| 检查 PA10 焊点；换板对比 |

> 这个实验能一刀切把"MCU 侧问题"和"板载 CH340K 侧问题"分开。

## 九、回答用户提问：「为什么工业数据采集终端项目串口能用，这里不行？」（2026-10-11 晚）

### 9.1 逐行比对结论：**MCU 侧两项目逐字节等价，不存在配置差异**

| 对比项 | 工业数据采集终端（能用） | 本项目 OTA 板（不能用） |
|---|---|---|
| 外设 / 引脚 | USART1，PA9/PA10，AF7 | USART1，PA9/PA10，AF7 |
| 波特率 | 115200 8N1，OVER8=0 | 115200 8N1，OVER8=0 |
| TX 引脚 Pull | `GPIO_NOPULL` | `GPIO_NOPULL` |
| RX 引脚 Pull | `GPIO_PULLUP` | `GPIO_PULLUP` |
| BRR 时钟源 | PCLK2=150MHz → `0x0516` | PCLK2=150MHz → `0x0516` |
| CCIPR / USART1SEL | 从未写（复位默认 = APB2） | 从未写（正常 BL 不碰，见 9.2） |

参考工程 `BSP/bsp_console.c` 用 `HAL_RCC_GetPCLK2Freq()` 运行时算 BRR；
本项目 APP 走 `HAL_UART_Init()` 由 HAL 按同一 PCLK2 算 —— **结果都是 `0x0516`，无差异。**

### 9.2 ⚠️ CCIPR / USART1SEL 假设的**证伪**（本顾问自查）

**曾怀疑：** `ota/bootloader/Core/Src/main.c:343` 有
`RCC->CCIPR = (RCC->CCIPR & ~(3UL << 0)) | (2UL << 0);  /* USART1SEL = HSI16 */`
+ `USART1->BRR = 0x8BU`，而 `HAL_RCC_ClockConfig()` 不碰 CCIPR、APP 不恢复 USART1SEL
⟹ 猜测「BL→APP 后 USART1 内核时钟卡在 HSI16，APP 的 BRR=0x0516 假设 PCLK2 → 波特率错 → RX 断」。

**证伪过程（证据）：**
- 该行代码属于 `#if (BL_BARE_BLINK != 0)` 的**裸机调试分支**（`main.c:300` 起，含 `Bare_UartInit`/`Bare_Send`/独立 `main`）。
- `main.c:236`：`#define BL_BARE_BLINK 0` → **该分支不参与编译**。
- 生效的是 `#else` 分支（`main.c:441` 起）的正常 BL：`HAL_Init() → SystemClock_Config() → BL_UartInit()`，
  其中 `BL_UartInit()` 走 HAL，**从不写 CCIPR**。
- 旁证：若 USART1 真按 HSI16 工作，实测 BRR 应为 `0x8B`；而实测 **`BRR=0x0516`=1302=150e6/115200**，
  证明内核时钟确为 PCLK2=150MHz。

**⟹ CCIPR 假设排除。** 记此条以防后人重复走弯路。

### 9.3 真正的差异 = **物理连接拓扑**

- **采集终端（能用）**：板上**无** USB 桥，PA9/PA10 引到排针（J1 pin11/12 或 J4）；
  PC ←USB→ **外部 USB-TTL 模块** ←3 根杜邦线（TXD→PA10 / RXD→PA9 / GND）→ 板；`DTR`/`RTS` 断开。
- **OTA 板（不能用）**：板上**有** CH340K，PA9/PA10 由**板内铜箔**直连 CH340K；
  PA9/PA10 外部空着，无杜邦线。

### 9.4 为什么「同一颗 CH340K 上 TX 通、RX 不通」

TX/RX **共用同一个 USART1 寄存器里的 BRR** ⟹ 波特率上两方向必然一致，
**不可能只坏 RX 的波特率**。配合 MCU 侧已全部实测排除（`MODER=ABEBFFFF`、`CR1=0x002D`、
`ISER1=0x20`、无代码占用 PA10、`MX_GPIO_Init()` 空实现），
**断裂点只可能在「CH340K 的 RXD 引脚 ↔ PA10」这段板级铜箔/元件。**
这与应用层代码无关。

### 9.5 待用户接线的决定性实验

按 §四，把**外部 USB-TTL 接到 OTA 板 J4**（TXD→pin5=PA10 / RXD→pin6=PA9 / GND→pin3），
**拔掉 USB-C 线**，DTR/RTS 不接，跑 `tools/p2_rx_probe.py`：
- 外接模块能通 ⟹ 板载 CH340K 侧故障（修板 / 飞线绕开）
- 外接模块也不通 ⟹ 才需回查 MCU 侧（概率低，已排除）

## 十、🔴🔴 结论推翻与真正的根因（2026-10-11 晚，v3）

> ⚠️ **§九 的 9.3/9.4/9.5 结论作废。** 用户澄清：**工业数据采集终端也是板载 CH340K，
> 同样没接外部 USB-TTL** —— 两项目**连接拓扑完全一致**，"板载 vs 外接"的差异**不存在**。

### 10.1 关键反证

用户确认：**OTA 板每次打开串口，都会重新打印启动横幅。**

⟹ **板子在被反复复位**，主循环从未持续运行。

### 10.2 真正根因：板载 CH340K 的 `RTS→NRST` 复位脉冲

参考工程 `docs/迁移说明.md` §18.5 明确记载：

> **A. 板载一键下载电路的标准行为（非接线错误！）**
> 板载 **CH340K 的 DTR→BOOT0、RTS→NRST（一键下载电路）** 导致"打开串口"的脉冲组合
> 会把芯片送入系统 bootloader（VTOR=0x1FFF0000 实锤）……

**现象逐条对应：**

| 观测 | 解释 |
|---|---|
| 打开串口 → 重新打印启动横幅 | `RTS→NRST` 脉冲复位 MCU |
| TX "通"（收到 1525 字节日志）| **不是持续运行日志，是每次复位瞬间的启动横幅**（TX 是复位后自动打印）|
| RX 断（`rxIrq=0`、`edges=0`）| MCU 刚复位，`Console_Task` 还没跑起来又被复位打断 |
| 两板现象**完全一致** | 同款板、同款 CH340K、同一个复位机制 |

### 10.3 参考工程的成功经验（可直接照搬）

参考工程 §18.5 根治手段：
1. **`STM32_Programmer_CLI -ob nSWBOOT0=0 nBOOT0=1`** —— 禁用 BOOT0 引脚，
   任何复位都从 Flash 启动（解决 `DTR→BOOT0` 导致的"进系统 bootloader"）。
2. **所有串口工具以 `dtr/rts=False` 打开** —— 避免 `RTS→NRST` 脉冲
   （但"打开"动作本身的瞬态脉冲未必可控，见 10.4）。

**验证标准（参考工程实测）**：零干预打开串口 → 834 字节帧流直出。

### 10.4 待验证（需 ST-Link）

## 十一、RTS 语义的硬件级证实（本轮新增，关键）

上一轮把根因归到 `RTS→NRST`，属于**"打开即复位"**的间接证据。本轮用
**"保持 RTS 电平 + SWD 同时读核心"**的办法拿到了直接证据。

### 11.1 实验：保持串口打开，期间用 SWD 读核心

工具：`tools/rts_state_probe.py`（只负责保持端口打开并锁定 dtr/rts 电平，
不碰 SWD；SWD 由外部 CLI 执行）。

| 保持状态 | SWD 读到的寄存器 | 板子状态 |
|---|---|---|
| `dtr=False rts=True`（保持 25s） | `SP=LR=PC=XPSR=MSP=0x04000000` | **CPU 完全不可访问** |
| 释放 RTS 后立刻读 | `PC=0x08018376`（在 `main` 内）、`MSP=0x20001EF0`、`XPSR=0x61000000` | 正常 |

**判据**：`rts=True` 期间 **5 个寄存器全部读出同一个值 `0x04000000`**，
这是**总线读失败**的典型模式（不是某个合法的 CPU 状态）。
即：`NRST` 被拉低到连 **SWD 调试端口本身都不响应**。

释放 RTS 后 **立刻**恢复（`PC` 落在 `main`），说明并非供电问题，
而是 **`RTS` 直接驱动了复位网络**。

### 11.2 实验：`rts=True` 时 TX 是否还活着（排除法）

工具：`tools/rts_hold_txrx.py`
（静默 6s → 静默 6s → 发送 8s → 静默 4s，全程 `rts=True` 且不打任何字）

```
P1 silent-after-open  bytes=0  BLbanner=0 uartLines=0
P2 silent-diag-window bytes=0  BLbanner=0 uartLines=0
P3 send 8s: tx=3483 bytes, rx=0 bytes
P4 settle-after-send  bytes=0  BLbanner=0 uartLines=0
```

连续 24 秒**零字节** —— 连 3 秒周期的 `[uart]` 诊断行都没有。

**结论**：`rts=True` 时板子**根本没在跑**（不是"RX 不通"）。

### 11.3 修正上一轮的"RX 一直不通"判断

上一轮观察到"静默时 `edges/200ms=0` 且 `rxIrq=0`"，一度倾向"RX 通路坏"。
本轮用 SWD **直读 `huart1` 结构体**（地址 `0x20000310`，由 `G474.map` 得到）：

```
0x20000310  40013800   Instance       = USART1
0x20000314  0001C200   Init.BaudRate  = 115200
0x20000364  200000F8   pRxBuffPtr     = &s_rxBuf   ← RX 已挂载 ✅
0x20000368  00010001   RxXferSize=1, RxXferCount=1 ← 正在等 1 字节 ✅
0x20000390  00000020   gState  = 0x20 = HAL_UART_STATE_READY
0x20000394  00000022   RxState = 0x22 = HAL_UART_STATE_BUSY_RX
```

同时读 `s_rxIrqCnt = 0`、`s_rxHead = s_rxTail = 0`、`s_rxDropCnt = 0`
（`s_rxIrqCnt @ 0x20000100`）。

**RX 软件侧完全正确且已挂载**，只差 PA10 上出现一个下降沿。
结合 `USART1->CR1=0x002D`（RE=1）、`NVIC->ISER[1]=0x20`（IRQ37 使能）、
`ISR=0x006000D0`（无 FE/NE/ORE/PE 错误、RXNE=0），
**软件侧已被彻底排除**。

### 11.4 `XPSR=0x01000000` 误读澄清

早期把 `PC = 0x01000000` 当作"非法 PC"，实为 CLI 输出的 **`XPSR` 列**
（`0x01000000` = 仅 T 位相关、无异常标志），属正常值。
此时真正的 `PC` 在 `main` 内。**记录此误读，避免后续再被误导。**

### 11.5 当前确证链（全部有据）

| 结论 | 证据 |
|---|---|
| `rts=True` ⟹ NRST 被拉低、CPU/SWD 均死 | 保持 RTS 时 5 寄存器全 `0x04000000`；释放即恢复 |
| `rts=False` ⟹ 板子正常运行 | `PC` 在 `main`，`XPSR` 合法，启动横幅完整 |
| RX 软件侧配置全部正确 | SWD 直读 `pRxBuffPtr/RxXferSize/RxState` + `CR1/ISER1/ISR` |
| ISR **从未触发过** | `s_rxIrqCnt = 0` |
| 无 IWDG 复位 | `RCC_CSR=0x3C000002` → `IWDGRSTF=0` |
| `PINRSTF=1` | 同上，`bit28=1`，与 `RTS→NRST` 一致 |
| CubeProgrammer `-w32` **不能写外设** | 写 `0x40021094` 报 "Failed to download data"，只走 Flash loader |

### 11.6 剩余未解 + 下一步

1. **`rts=False` 时 `write()` 为何仍会周期性复位板子**
   （`write_reset_bisect.py`：第 8 次 write、t≈3.4s 出现横幅；
   `write_reset_csr.py`：t≈3.2s 出现横幅）—— 复位时刻与**累计时长**相关，
   需进一步区分"TX 数据耦合"还是"CH340K 驱动在 write 时翻 RTS"。
2. **PA10 从未出现下降沿** —— 需在**板子持续运行**（不复位）的窗口内，
   用满负荷发送 + 200ms 窗口边沿计数拿到无偏判据。
3. `RCC_CSR` 无法从 PC 清零 → 若要区分复位源，需**改固件**在
   `main()` 开头读一次 `RCC_CSR` 并打印（这是唯一可靠路径）。

## 十二、根因闭环（本轮最终确证）

### 12.1 选项字节：关键发现 `NRST_MODE = 0x3`

```
nSWBOOT0 : 0x0 (BOOT0 taken from option bit nBOOT0)
nBOOT0   : 0x1 (nBOOT0 = 1)
NRST_MODE: 0x3 (Bidirectional reset: NRST pin in reset input/output mode - legacy)
IRHEN    : 0x1 (Internal resets drives NRST pin low until seen as low level)
RDP      : 0xAA (Level 0, no protection)
```

`nSWBOOT0=0 + nBOOT0=1` **已按参考工程 §18.5 设置到位**，但 `NRST_MODE=0x3`
意味着 **`NRST` 是真正的复位输入**，任何拉低它的信号（板载 CH340K 的 `RTS`）
都会直接复位 MCU。

> **重大澄清**：参考工程 §18.5 记录其根治手段是 `nSWBOOT0=0 nBOOT0=1`，
> 其现象是"脉冲把芯片**送入系统 bootloader**（VTOR=0x1FFF0000）"。
> 而本板实测：复位后 `BL: clock HSE+PLL 150MHz OK` → **从 Flash 正常启动**，
> 说明该手段在本板**已生效**（不再进 system bootloader），
> 但 **`NRST` 引脚本身仍是复位输入** —— 所以复位动作依旧发生。
> **这是"同一手段、不同现象"的原因，也解释了为何照搬参考工程经验无效。**

### 12.2 `write()` 触发复位的精确规律（三组对照）

工具 `tools/reset_timing.py`：

| 组 | TX 行为 | 首次复位时刻 |
|---|---|---|
| A | 完全不发（12s） | **无复位** |
| B | **只发 1 字节** | **3.16s** |
| C | 满负荷 256B 连续 | 3.21s |

进一步用"打开即写、精确计时"测得：**横幅出现在 `t=0.154s`**
（之前的 3.2s 只是因为"打开后先等了 3 秒才写"）。

更精细的阶梯实验（静默5s → 写1次+静默10s → 写1次+静默8s）：

| 阶段 | 动作 | 横幅数 | `[uart]` 行数 |
|---|---|---|---|
| A | 打开+静默 5s | **1**（打开动作本身触发） | 4 |
| B | 写 1 次 + 静默 10s | **1** | 8 |
| C | 写 1 次 + 静默 8s | **1** | 4 |

**结论（逐条有据）：**
1. **"打开端口"本身** → 复位 1 次（`RTS` 在 open 时的脉冲）。
2. **每一次 `write()`** → 复位 1 次，之后**无限期稳定**直到下一次 write。
3. **只读不发** → 完全不复位（静默 30s 得 0 复位）。
4. 复位由 write **立即**触发，**与数据量无关**（1 字节即触发）。

### 12.3 复位是"无害"的 —— 但足以毁掉 RX 判定

工具 `tools/post_reset_state.py`（打开→触发→抓 9s）：

```
BL: clock HSE+PLL 150MHz OK
BL: boot state=0 trialLeft=0 activeSlot=0 lastErr=0x00000001
BL: jump to APP slot 0 base=0x0800C080 size=0xDC08
=== STM32G474 CAN Node v3.0.0 | role:A(master) | Oct 11 2026 16:05:45 ===
[FP] board fingerprint = FP_X0
type 'help' for commands
> main: led-bsrr-state M3
[boot] A..H 完整通过
[uart] ... rxIrq=0 ... edges/200ms=0   （重复 8 次）
```

**复位后板子启动完全正常**（BL→APP→指纹→命令提示符→8 条诊断行）。
即复位本身不致命；**致命的是它把刚收到的字节连同 RAM 一起清掉**，
所以 `rxIrq` 永远是 0。

### 12.4 最强见证：原始 ISR 计数 `g_uartRawIsrCnt`

`stm32g4xx_it.c:264` 的 `USART1_IRQHandler` **第一条语句**就自增
`g_uartRawIsrCnt`（在内核任何 HAL 处理之前）。

SWD 直读 `0x200000ec`（`g_uartRawIsrCnt @ 0x200000ec`）：

```
发送 200 字节之前:  g_uartRawIsrCnt = 0
发送 200 字节之后:  g_uartRawIsrCnt = 0
```

**发送 200 字节后，USART1 中断入口计数器仍为 0** —— 这是最直接、最无可争辩的
证据：**PA10 上从未出现过任何起始位下降沿**。

| 1 | RX **软件侧 100% 正确、已挂载** | SWD 直读 `pRxBuffPtr=&s_rxBuf`、`RxXferSize=1/RxXferCount=1`、`RxState=BUSY_RX`、`CR1=0x002D`、`ISER[1]=0x20`、`ISR=0x006000D0` 无错误 |

### 12.6 排除清单（全部有据排除）

- ❌ USART1 软件配置（寄存器逐位解码正常）
- ❌ CCIPR/HSI16 波特率污染（`BL_BARE_BLINK=0`，该分支不编译；实测 `BRR=0x0516`）
- ❌ IWDG 复位环（`IWDGRSTF=0` + uptime/tick 在走）
- ❌ SHA 时钟/电源问题（复位后立刻恢复）
- ❌ 选项字节 BOOT0 问题（`nSWBOOT0/nBOOT0` 已正确）
- ❌ 参考工程"送进 system bootloader"问题（本板已修复，复位后从 Flash 启动）
- ❌ `PC=0x01000000` 非法地址（实为 `XPSR` 列误读）

### 12.7 下一步唯一可行路径（改固件）

**问题定性：这是硬件电路的 `RTS→NRST` 与"PC 侧 write 必然产生 RTS 脉冲"的
组合问题，不是软件 bug。** 要拿到"无偏 RX 判据"必须让**复位不发生在测量窗口内**。

可行方案（按代价排序）：

1. **改固件：绕过复位影响做自环验证**
   在 `main()` 里把 `PA9`(TX) 与 `PA10`(RX) ……物理上无法自环。
   → 改为：让固件**自己**往 RI 写一个字节（`USART1->TDR = 'X'`
   并把 PA9 跳线到 PA10），或**软件模拟** RE 触发（置 `CR1.RE=1` 后写 `RQR.RXFRQ`）
   ——验证 RX 通路软件闭环。**推荐 `RQR` 方式，零外部接线。**

2. **改固件：在 `main()` 开头打印 `RCC_CSR`**
   PC 侧无法清零 `RCC_CSR`，只有固件能做到"捕获并清零"，
   才能证明"复位确为 `PINRSTF`"。

3. **硬件侧（若允许动板）**
   - 断开/割断板载 CH340K 的 `RTS→NRST` 连线，只用 `TXD/RXD/GND`
     （参考工程 §18.3 的"只接 3 根线"做法）。
   - 或在 `NRST` 与地之间不接、而在 `RTS` 线上加隔离。

4. **PC 侧：寻找"不产生 RTS 脉冲"的驱动**
   已排除：`rts=False` 仍会脉冲（因为驱动在 write 路径内部操作）。
   未试：`rtscts=True`、不同 USB 栈、`ftdi`/`ch341` 原生驱动替代 VCP。
   注：`rts=True` 方案**不可用**（会把 NRST 持续拉低，板子死透）。

> **务必先做 #1 与 #2**：这两个都是零外部改动、可立即执行的固件改动，
> 能把"RX 通路是否物理完好"和"复位源"彻底钉死。

## 十三、最终判定：RX 外部通路（CH340K TXD → PA10）确认故障

### 13.1 新增"无观测偏差"判据：`PA10pulseTotal`

**此前所有 RX 判据都有观测偏差**：`BSP_UART_DiagTask` 是"固定窗口采样"
（200ms → 500ms，周期 3s）。若 PC 只发零星字节，窗口很可能整段落在
两字节之间的空闲间隙里 → `edges=0`，但这**不能**证明信号没到。

**新判据**：在 `bsp_uart.c` 新增 `BSP_UART_RxPinPulse()`，由**主循环每圈调用**，
维护 `s_rxPinPulseCnt`（PA10 自开机以来的**累计**跳变数）。
只要引脚动过**任意一次**，该值必定 > 0。**彻底消除窗口偏差。**

代码位置：
- `bsp_uart.c`：`BSP_UART_RxPinPulse()` / `BSP_UART_RxPinPulseCnt()`
- `bsp_uart.h`：原型声明
- `main.c` 主循环：`BSP_UART_RxPinPulse();`（紧邻 `Console_Task()`）
- `BSP_UART_Init()` 末尾：初始化基准电平 `s_rxPinLevel`

另在 `main.c` 启动段新增 **2 秒满速 PA10/PA9 边沿捕获窗口**（`[rxwin]` 行），
同时采 TX(PA9) 以区分 TX/RX 通路。

### 13.2 决定性实验与结果

实验：打开端口 → **连续满负荷发送 0.6 秒**（约 6900 字节 @115200）
→ 立即停止发送 → 纯静默 8 秒收结果。

```
[rst] RCC_CSR=04000002  PINRST=0 PORRST=0 BORRST=0 SFTRST=1 ...   ← 本次 boot 期间无 NRST 复位
[rxwin] 2s: PA10edges=0 PA9edges=0  PA10=1 PA9=1 IDR=A600
[rxwin] RCC_CSR(now)=00000002                                     ← 窗口内确实没有复位
[uart] CR1=002D CR3=0001 BRR=0516 ISR=006000D0
[uart] MODER=ABEBFFFF IDR=A600 PA10=1 PA9=1 rxE/500ms=0 txE/500ms=0
[uart] PA10pulseTotal=0 (自开机累计, >0 = 信号到过引脚)          ← ★★★ 关键
[uart] ISER1=00000020 rxIrq=0 drop=0 head=0 tail=0
[uart] gState=32 RxState=34 RxCnt=1
```

**`PA10pulseTotal = 0`**：发送了约 6900 字节后，PA10 引脚
**自开机以来一次电平跳变都没有过**。

### 13.3 最终结论（三条独立证据汇合）

| 层面 | 判据 | 结果 |
|---|---|---|
| **外部信号是否到达引脚** | `PA10pulseTotal = 0`（主循环累计，无窗口偏差） | ❌ **从未到达** |
| 引脚是否被正确复用 | `GPIOA->MODER = 0xABEBFFFF` → PA10 = AF 模式 | ✅ 配置正确 |
| 引脚空闲电平 | `IDR = 0xA600` → PA10 = 1（上拉生效，空闲态正确） | ✅ 正常 |
| USART 接收使能 | `CR1 = 0x002D`（UE/RE/TE/RXNEIE） | ✅ 正确 |
| USART 无错误 | `ISR = 0x006000D0`（FE/NE/ORE/PE 全 0） | ✅ 正常 |
| NVIC | `ISER[1] = 0x20`（IRQ37 使能） | ✅ 正确 |
| HAL 已挂载接收 | `pRxBuffPtr=&s_rxBuf`、`RxXferSize=1`、`RxState=BUSY_RX` | ✅ 正确 |
| ISR 是否进过 | `g_uartRawIsrCnt=0`、`s_rxIrqCnt=0` | ❌ **从未进入** |
| TX 通路 | PA9 输出全部控制台日志（PC 正常收到） | ✅ **完好** |

> ## 🔴 最终定位
>
> **USART1 的 RX 软件/外设侧 100% 正常且已挂载等待接收；
> 问题是「CH340K 的 TXD → MCU PA10」这条外部走线/连接从未把任何
> 电平变化送到 PA10 引脚上。**
>
> 即：**RX 方向的外部物理通路断**（而 TX 方向的 PA9→CH340K RXD 通路完好）。

### 13.4 为何"参考工程的板载 CH340K 能用"在本板不成立

- 参考工程（工业数据采集终端）的 §18.5 验证是"零干预打开串口 → 834 字节
  **帧流直出**"。注意：**那是"出"（TX 方向）**，并未证明其 RX 方向可用。
- 其 §18.3 的 RX 相关记录针对的是 **USB-TTL 外接线**（"只接 3 根：
  TXD→PA10、RXD→PA9、GND"），即当时 RX 是**外接线**打通的，
  并非板载 CH340K 的 RX 通路。
- 本会话已证实：**两块板的板载 CH340K 的 DTR/RTS 确实接到了
  BOOT0/NRST**（一键下载电路），而 **TXD→PA10 这一路可能并未连通**
  （或存在焊接/走线缺陷）。

## 十四、【纠正 + 定论】PA10 走线开路 —— 用无争议判据终结

### 14.1 ⚠️ 先纠正：`RCC_CSR` 位定义此前标错一整排

以 CMSIS `stm32g474xx.h` 的 `RCC_CSR_xxxRSTF_Pos` 逐条核对：

| bit | 之前错标 | **正确** |
|---|---|---|
| 25 | — | OBLRSTF |
| 26 | SFTRSTF | **PINRSTF** |
| 27 | PORRSTF | BORRSTF |
| 28 | PINRSTF | **SFTRSTF** |
| 29 | BORRSTF | **IWDGRSTF** |
| 30 | OBLRSTF | WWDGRSTF |
| 31 | LPWRRSTF | LPWRRSTF |

**重新解码（推翻第十三章的旧结论）：**

| 实测值 | 旧（错）解读 | **正确解读** |
|---|---|---|
| `0x04000002` | "SFTRSTF" | **PINRSTF** → PC 开/写串口 ⟹ **RTS→NRST 引脚复位** ✅ |
| `0x24000002` | "BORRSTF(欠压)" | **IWDGRSTF** → **看门狗复位** |
| `0x14000002` | "PINRSTF\|SFTRSTF" | SFTRSTF\|PINRSTF → SWD 复位 |

> 🔴 **教训：寄存器位定义必须查头文件，绝不能凭记忆。**
> 我此前把"看门狗复位"误读为"电源欠压"，导致第十三章 13.5 的方向性建议有偏差。

### 14.2 "一改 PA10 就复位"的真相 = `EIE` 漏关导致中断风暴

`CR3 = 0x0001` ⟹ **EIE（错误中断使能）一直是开着的**。
只关 `CR1.RXNEIE` 是不够的：把 PA10 切出复用后，USART 的 RX 输入与引脚断开、
变成悬空 → 持续产生 FE/NE/ORE → **错误中断不断触发 → 主循环被彻底饿死
→ 约 3 秒后被 IWDG 复位**（表现为"一改引脚就复位"，实为看门狗）。

**正确做法**：探测期间必须同时关闭
`CR1.RE | CR1.RXNEIE` 与 `CR3.EIE`，测完再恢复。

### 14.3 终极判据：`[pdtest]` —— 内部下拉 + 高频动态采样

**为什么这条判据无争议：**
- CH340K 的 TXD 是**推挽输出**，空闲必为高、发送期间大量高电平；
- MCU 内部下拉仅约 40kΩ，**绝无可能**把被推挽驱动为高的引脚拉低；
- 因此只要把 PA10 配成"输入 + 内部下拉"，再在 PC 发送期间高频采样：
  - 读到过 **1** ⟹ 有外部推挽驱动 ⟹ **TXD 与 PA10 连通**
  - **全程只读到 0** ⟹ 无任何外部驱动 ⟹ **走线开路**

**必须加 3ms 稳定延时**：切换瞬间引脚要从原来的上拉高电平经 RC 放电到低，
不等待就采样会读到一批"高"（实测 `high=11/107万` 的**假阳性**），
等待后归零。

**结果（20 秒 / 23 万字节连续发送期间，3 次独立测量）：**

```
[pdtest] PA10 w/ pulldown 150ms: high=0 low=1071212  ==> OPEN(全程无外部驱动=走线开路)
```

- 采样率 ≈ **7.1 MHz**（150ms 采 1,071,212 次）
  ⟹ 对 115200 波特（位宽 8.68µs）相当于**每位采样约 62 次**，灵敏度充足
- **107 万次全部读到低**

**辅证（`[t1]`~`[t5]`）**：PA10 在"内部上拉"下读 1、在"内部下拉"下读 0
⟹ 电平**完全跟随 MCU 自己的电阻** ⟹ 引脚处于**浮空**状态。

### 14.4 🔴 最终定论

> **PA10 与板载 CH340K 的 TXD 之间不存在电气连接（走线开路/未连接）。
> 这是纯硬件问题 —— 任何软件改动都不可能让串口 RX 方向收到数据。**

同时确认：**PC 每次打开/写入串口都会通过 `RTS→NRST` 复位整板**
（`PINRSTF` 实锤）。这意味着 **即使 RX 通路修好，CH340K 方案也无法
交互式使用**（每条命令都会被复位打断），因此替代方案必须一并绕开该复位电路。

### 14.5 替代方案（无需改动硬件）

| 方案 | 做法 | 优点 | 约束 |
|---|---|---|---|
| **A. MCU 原生 USB CDC**（推荐） | 用板上第二个 USB-C 口（`USB设备`，走 PA11/PA12）。工程已含 HAL 的 `stm32g4xx_hal_pcd.c`/`stm32g4xx_ll_usb.c`（只需加入编译）；补 CDC-ACM 类 + HSI48 48MHz 时钟 | **彻底绕开 CH340K**；**USB 无 DTR/RTS ⟹ 复位问题一并消失**；Console/OTA 隧道上层代码不用改 | 需实现（中等工作量）；需验证该口确已连到 PA11/PA12 |
| B. CAN 作主交互通道 | 复用已有 UDS/ISO-TP/`ota_tunnel.c` | 改动最小；OTA 本就走 CAN | 需 USB-CAN 适配器；无日志流便利 |
| C. 外接 USB-TTL 到 PA10 | 只接 `TXD→PA10` + `GND`（**严禁接 DTR/RTS**） | 立刻可验证/使用 | 需一根 USB-TTL 线 |
| D. 飞线 `CH340K.TXD → MCU.PA10` | 一条细线 | 修复板载串口 | 需动烙铁（加线） |
