# 01 · Flash 分区规划与 Bootloader/APP 链接配置

> 依据：`G474/MDK-ARM/G474.uvprojx` 中实际配置为
> `<Device>STM32G474VETx</Device>`、`IROM(0x8000000-0x807FFFF)`、`IRAM(0x20000000-0x2001FFFF)`、`ScatterFile` 为空（即用 Keil 默认分散加载）。

## 1. 硬件事实（决定分区可行性的前提）

| 项目 | 实测/文档值 | 来源与影响 |
|---|---|---|
| MCU | STM32G474VETx | `uvprojx` Device 字段 |
| Flash | 512 KB，`0x08000000~0x0807FFFF` | `uvprojx` IROM 配置 |
| Flash 页粒度 | **2 KB** | RM0440 第 3 章 Flash 章节；G4 全系列统一 2KB 页，擦除最小单位 |
| 双 Bank 能力 | 支持，`FLASH_OPTR.DBK` 选项位置 1 后为 **2×256 KB** | RM0440；[AN4767 双 Bank 在线升级](https://www.st.com/resource/en/application_note/dm00230416-onthefly-firmware-update-for-dual-bank-stm32-microcontrollers-stmicroelectronics.pdf#2#1) |
| Bank 划分（DBANK=1） | Bank1 `0x08000000~0x0803FFFF`、Bank2 `0x08040000~0x0807FFFF` | 记忆映射固定，每个 Bank 各 128 页 |
| RAM | 128 KB `0x20000000~0x2001FFFF` | `uvprojx` IRAM 配置 |

### 1.1 为什么两槽位要"对齐 Bank 边界"而不是简单首尾均分

G474 的 DBANK 是**全局选项字节**：置位后，从 `0x08040000` 起取指属于 Bank2。若某个槽的代码跨越 `0x08040000`，那么"擦写该槽自身所在 Bank"时，CPU 会将取指落到正在擦除的 Bank 上 → 读出全 `1`/未定义 → **HardFault**。

因此本方案刻意让：

* **Slot A 完全落在 Bank1**（`0x08000800` 起，不越过 `0x08040000`）
* **Slot B 完全落在 Bank2**（从 `0x08040800` 起，即 Bank2 起始 + 2 KB）

由此获得关键能力：**APP 运行在 Slot A（Bank1）时，可以擦写 Slot B（Bank2），而无需把任何代码复制到 RAM 执行**。这是 A/B 在线升级能安全落地的物理基础。

> 若把 Slot B "上对齐到 Flash 末尾"（`0x0807E800`），它会跨越 Bank2 起始吗？不会——但它会紧贴末尾，而 Slot A 则被迫跨越 `0x08040000`，A 槽取指将横跨两 Bank，回滚/擦写 A 时同样崩溃。**Slot B 必须完全落在 Bank2 内**，这是本分区表的硬约束，`ota/common/ota_common.h` 已用 `#error` 编译期断言锁死。
>
> ⚠️ **措辞澄清（曾导致一次真实编译报错）**：约束是"**包含关系**"（`⊂ [0x08040000, 0x08080000)`），**不是**"起始地址精确对齐 `0x08040000`"。Slot B 实际起点是 `0x08040800` = Bank2 起始 **+ 2KB**，因为 Bank2 第一页 `0x08040000` 被留作控制区镜像份 `BL_HEADER_MIR`。
> 早期版本把头文件断言误写成 `(OTA_SLOT_B_ADDR % OTA_FLASH_BANK_SIZE) != 0` —— 对**绝对地址**取模必然失败（`0x08040800 % 0x40000 = 0x800 ≠ 0`），会让完全正确的分区表编译报错。现已改为区间包含判定。

## 2. 分区表

| 分区 | 起始地址 | 结束地址(含) | 大小 | 页数 | 说明 |
|---|---|---|---|---|---|
| **BL_HEADER（向量表 + 控制区主份）** | `0x08000000` | `0x080007FF` | 2 KB | 1 | BL 向量表占页首 ~`0x1D8` 字节；**控制区两份副本**位于 `+0x000` 与 `+0x800`，与向量表同页但不重叠 |
| **BL_CODE（Bootloader 代码）** | `0x08000800` | `0x08007FFF` | 30 KB | 15 | BL 全部代码；**`addr < OTA_SLOT_A_ADDR` 的保护判断同时护住本区** |
| **Slot A（APP A）** | `0x0800C000` | `0x0803FFFF` | 208 KB | 104 | 含 32 B 镜像头；上界恰好 = Bank1 上界，**完全位于 Bank1** |
| **BL_HEADER_MIR（控制区镜像份）** | `0x08040000` | `0x080407FF` | 2 KB | 1 | 更新 Slot B 时本页随 Bank2 被擦，故必须有镜像 |
| **Slot B（APP B）** | `0x08040800` | `0x08074800` | 208 KB | 104 | 含 32 B 镜像头；起点 = Bank2 起始 + 2KB，**完全位于 Bank2 内** |
| —— 未分配 —— | `0x08078800` | `0x0807FFFF` | 30 KB | 15 | 预留（未来放标定数据/日志；**勿放 UDS 标定数据以外的关键状态**） |

* 两槽大小完全相同（208 KB = `0x34000`），无需按槽区分长度常量。
* 镜像头 32 B 位于槽首；**APP 真正链接基址 = 槽基址 + 0x20**：
  * Slot A 的 APP 链接基址 = `0x0800C080`
  * Slot B 的 APP 链接基址 = `0x08040880`

> **为什么 Slot A 不能从 `0x08000800` 开始**（初版方案的错误，已修正）：
> MCU 复位**固定从 `0x08000000` 取初始 SP 与复位向量**，因此 BL 的向量表必须在 `0x08000000`，
> 而 BL 代码紧随其后。若 Slot A 也从 `0x08000800` 开始，**BL 代码与 Slot A 完全重叠**，
> 一次 A 槽下载（从 `0x08000800` 起擦页）就会擦掉 BL 自身 → 直接变砖，
> 而 `< OTA_SLOT_A_ADDR` 的保护判断也挡不住（它只保护到 Slot A 之前）。
> 因此必须给 BL 预留独立的 30 KB。

### 2.1 控制区与向量表同页，会不会互相破坏？

不会，且是刻意设计：

```
0x08000000 ┌────────────────────────────────────┐
           │ BL 向量表（~0x1D8 字节）            │  ← 复位/异常入口，只读使用，绝不作写目标
0x080001D8 ├────────────────────────────────────┤
           │ 控制区副本0（OTA_Cfg，48 字节）      │
0x08000200 ├────────────────────────────────────┤
           │ 空闲                                │
0x08000400 ├────────────────────────────────────┤
           │ 控制区副本1（OTA_Cfg，48 字节）      │
0x08000428 ├────────────────────────────────────┤
           │ 空闲（约 1 KB 余量）                 │
0x08000800 ├────────────────────────────────────┤ ← 本页结束
           │ BL 代码区（30 KB）                   │
0x0800C000 └────────────────────────────────────┘
```

四点保障：

1. 两份副本偏移为 `0x1D8` 与 `0x400`，**都在本页内**，且都 8 字节对齐（满足双字编程）；
2. 副本0 紧接向量表之后（`0x1D8 ≥ OTA_CFG_VECTAB_BYTES`），不覆盖向量表；
3. 两份副本间距足够（`0x1D8 + 256 ≤ 0x400`），同页擦写时来得及互相保全；
4. **BL 写流程永不以 `0x08000000`（副本0）为擦写目标**——整页擦除会连向量表一起擦掉。
   `bl_param.c` 的写目标只在 `主份+0x400`、`镜像份+0x1D8`、`镜像份+0x400` 三个位置间轮转，
   且**绝不擦掉"唯一最新副本"所在页**；若必须擦 `0x08000000` 页，则须把页首
   `[0, 0x1D8)` 向量表按页镜像原样回写。**这是 BL 实现中必须遵守的第二条血线**
   （第一条是"不擦 Slot A 之前的任何地址"）。

### 2.1 为什么不把控制区放在 Flash 末尾

因为 `0x0807F800` 属于 Bank2。更新 Slot B 需要擦除 Bank2 中的页，若控制区在那里，会**与用户数据一起被擦掉**——这正是很多 A/B 方案在掉电后无法回滚的根因。本方案把控制区放在两个 Bank 的**各自首部**，并互相镜像，任一侧被擦时另一侧仍在。

## 3. 控制区（参数区）掉电安全设计

控制区每份占 1 页（2 KB），页内再分两份副本，**并把页首让给 BL 向量表**：

```
0x08000000 + 0x000 : BL 向量表（~0x1D8 字节）—— 绝不能作为配置写目标
0x08000000 + 0x1D8 : 副本0（OTA_Cfg，48 B）—— 紧接向量表之后，8 字节对齐
0x08000000 + 0x400 : 副本1（OTA_Cfg，48 B）—— 页内后半
0x08000000 + 0x800 : 页结束（下一页 = BL 代码首地址）
```

> ⚠️ 副本1 的偏移是 `0x400`，**不是 `0x800`**。`0x800` 恰好等于页大小，会把副本1
> 写到**下一页**去：主份页的下一页是 `0x08000800`（**BL 代码首地址**），镜像份页的下一页
> 是 `0x08040800`（**Slot B 首地址**）——既写不进去（被保护区拒绝），又可能破坏 BL / Slot B。
> `ota_common.h` 已用 `#error` 断言锁死"副本1 不得跨出本页"。

写入算法（`bl_param.c` / `Ota_ParamCommitTrial()`）：

1. 读副本0、副本1，各自校验 `magic` 与结构 CRC，取 `seq` **较大**的有效副本为"当前值"。
2. 把新值写入**另一份**副本所在偏移，`seq = 当前值.seq + 1`，随后整页回读校验。
3. 若两份都无效 → 用编译期默认值（`IDLE_A`、两槽 CRC 全 0 视为无效）重建副本。

**第二条血线（擦控制区页时）**：`0x08000000` 这一页**同时承载 BL 向量表**。因此：

* 写入目标只在 `主份+0x400`、`镜像份+0x1D8`、`镜像份+0x400` 之间按"写最旧的有效副本"轮转；
* **绝不擦掉"唯一最新副本"所在的那一页**（若最旧与最新同页，则改写到另一物理页）；
* 若某路径确实必须擦 `0x08000000` 页，**必须先把页首 `[0, 0x1D8)` 的向量表按页镜像原样回写**，
  否则下次复位取到被擦成 `0xFF` 的栈顶/复位向量 → HardFault（现象与"变砖"相同）。

**第三条血线（擦 `0x08000000` 页时的必然 lockup）**：

擦除该页时**不能只做"读页镜像 → 擦 → 回写向量表"**。Flash 擦除期间总线忙会把 CPU 取指 stall，
而 **SysTick 每 1 ms 就会挂起一次**；一旦擦除结束、总线释放，挂起的 SysTick 会立刻按
**刚被擦成 `0xFFFFFFFF` 的向量表**取向量 → HardFault → lockup；复位后 SP/PC 仍是 `0xFFFFFFFF` = **变砖**。

这不是"小概率竞争"，而是 1 ms 挂起周期 vs 25 ms 擦除时间的**必然故障**。正确做法：

```c
uint32_t primask = __get_PRIMASK();
__disable_irq();                       /* 覆盖"擦页 + 回写向量表"整个窗口（≈30 ms） */
/* ... 擦 0x08000000 页，回写页首 [0, OTA_CFG_VECTAB_BYTES) 向量表 ... */
if (primask == 0U) { __enable_irq(); } /* 按现场恢复，不无条件开中断 */
```

* 该窗口 ≈30 ms，远小于 IWDG 3 s，期间照常喂狗；
* 因为 BL 的 FDCAN 是**主循环轮询**（不开中断），屏蔽中断**不影响 CAN 收发**；
* **残余风险**：这 30 ms 内掉电仍会丢失向量表（需 SWD 救回）。若要彻底消除，
  把 `BL_PARAM_PRIMARY_WRITE` 置 `0`——BL 只写镜像页、永不擦 primary 页（代价：失去跨物理页冗余）。
  **默认取 1**：因为 primary 页在槽更新时永远不会被擦（更新 Slot B 擦 Bank2；更新 Slot A 只擦
  `0x0800C000` 之后），它是天然常驻副本，值得保留这份恢复能力。

掉电只会破坏"正在写的那一份"，另一份始终是完整旧值，因此状态机永远可恢复。**不需要**任何文件系统、不需要 AT24Cxx/SPI Flash，完全符合"不修改硬件"的约束。

## 4. 三套工程/构建配置

| 构建目标 | IROM1 起始 | IROM1 大小 | `VECT_TAB_OFFSET` | 输出用途 |
|---|---|---|---|---|
| **Bootloader** | `0x08000000` | `0x800`（向量表+控制区页）→ 代码实际从 `0x08000800` 起 | `0x000`（默认） | 上电先运行，负责校验/回滚/跳转/接收 |
| **APP（Slot A 版）** | `0x0800C080` | `0x33F80`（≈207.99 KB） | `0x0000C020` | 现场运行固件，A 槽 |
| **APP（Slot B 版）** | `0x08040880` | `0x33F80` | `0x00040820` | 现场运行固件，B 槽 |

> Bootloader 工程的 IROM1 起始写 `0x08000000`（向量表必须在那里），
> 代码段由链接器自然落在 `0x08000800` 之后的 BL 区（30 KB 预算）；
> 若使用 scatter 文件，明确写成 `0x08000800 0x7800 { ... }` 更清晰。

> 只产出**一个** APP 工程即可：镜像的 `loadAddr` 字段由上位机打包时写入目标槽地址，
> 但**链接期**必须选定基址。因此推荐两种做法，任选其一：
> 1. **双构建配置**（推荐，零风险）：同一 uvprojx 复制两个 Target（`APP_A` / `APP_B`），只有 IROM1 与宏不同；
> 2. **位置无关+重定位**：APP 链接在 Slot A，若下载到 Slot B，Bootloader 跳转前把镜像整体复制到 A 槽——这需要额外的整段拷贝时间与 RAM 缓冲，不推荐。

### 4.1 Bootloader 工程需要配套改动的确切位置

`G474.uvprojx` 中必需修改项（行号取自当前仓库文件）：

```xml
<!-- 第 340 行附近：C/C++ 宏，APP 工程新增两个宏（Slot A 版） -->
<Define>USE_HAL_DRIVER,STM32G474xx,USER_VECT_TAB_ADDRESS,VECT_TAB_OFFSET=0x8020</Define>

<!-- 第 251-255 行：IROM 配置，APP_SlotA 工程 -->
<IROM>
  <Type>1</Type>
  <StartAddress>0x800C080</StartAddress>
  <Size>0x33F80</Size>
</IROM>
```

`Core/Src/system_stm32g4xx.c` 现有代码（**不要改文件逻辑，只改偏移值**）：

```c
/* 现状：USER_VECT_TAB_ADDRESS 未被定义，SCB->VTOR 保持复位默认 0x08000000 */
/* #define USER_VECT_TAB_ADDRESS */
#if defined(USER_VECT_TAB_ADDRESS)
  #define VECT_TAB_BASE_ADDRESS   FLASH_BASE
  #define VECT_TAB_OFFSET         0x00008020U   /* <-- Slot A；Slot B 版改 0x00040820U */
#endif
```

Bootloader 侧则**不需要**改 `system_stm32g4xx.c`（偏移保持 0），但 `main()` 里调用 `HAL_Init()` 前要确保 `SCB->VTOR = 0x08000000`——若不慎从 APP 分支软复位，`VTOR` 可能残留 APP 值，头两行必须显式复位：

```c
SCB->VTOR = OTA_FLASH_BASE;   /* Bootloader 的第一条语句，必须早于 HAL_Init() */
```

## 5. 容量核算与可行性结论

| 项 | 数值 |
|---|---|
| 现有 APP 固件规模 | `can.c` 20.7KB + `console.c` 14.2KB + `uds.c` 11.1KB + `isotp.c` 9.3KB + `main.c` 15KB + HAL 库 → 预计 **60~80 KB**（以实际 `.map` 的 `Total RO Size` 为准） |
| 单槽可用净空间 | 208 KB − 32 B ≈ **207.97 KB** |
| 占用率 | 约 27%~36%，**余量充足** |
| Bootloader 预算 | 30 KB（本方案实际约 13~19 KB，见 02 文档 §A.5） |
| 控制区 | 2 × 2 KB（主份 + 镜像份），页内各 2 份副本，共 4 份冗余 |
| 结论 | ✅ 512 KB 容量下 A/B 双槽（各 208 KB）+ 46 KB BL + 2 份控制区完全可行，无需外扩存储 |

**动手前必须先做的一件事**：打开一次 Bootloader 构建的 `.map` 文件，记录
`Total RO Size (Code + RO Data)` 与 `Total RW Size (RW Data + ZI Data)`，用它验证：

* BL 的 RO+RO Data ≤ 30 KB（`0x7800`），且代码落在 `0x08000800~0x08007FFF` 内；
* APP 的 RO+RO Data ≤ 208 KB（`0x34000`），且落在单槽内；
* APP 的 RW+ZI ≤ 128 KB（本工程实际约 10~20 KB）。

## 6. 风险提示（务必先读）

| 风险 | 后果 | 规避措施 |
|---|---|---|
| **BL 区与 Slot A 重叠**（初版方案的错误） | 一次 A 槽下载就擦掉 BL → **变砖**，且 `< OTA_SLOT_A_ADDR` 的保护挡不住 | 本版已给 BL 预留独立 46 KB（`0x08000800~0x0800B7FF`），Slot A 后移到 `0x0800C000` |
| 擦控制区页时把 BL 向量表一起擦掉 | 下次复位取到 `0xFF` 栈顶/复位向量 → HardFault（现象像"变砖"） | BL 写流程永不以 `0x08000000` 为写目标，只在另外 3 个副本位置轮转；若必须擦该页，则回写页首向量表 |
| 选项字节 `DBK` 被误改后与分区表假设不一致 | Slot B 取指错误 → HardFault | 本项目**不改任何选项字节**；Slot A 上界恰为 `0x08040000`、Slot B 下界恰为 `0x08040000`，两种 DBANK 取值下地址映射都不会崩 |
| 忘记改 APP 的 `VECT_TAB_OFFSET` | APP 中断全部跳向 `0x08000000` 的 BL 向量表 → 进 BL 中断向量后行为错乱 | 在 APP 的 `main()` 里加运行期断言：`assert(SCB->VTOR == (FLASH_BASE \| VECT_TAB_OFFSET))`，串口打印并 `Error_Handler()` |
| 用 `HAL_FLASHEx_Erase` 时误擦 `0x08000000` | 控制区丢失、BL 头部被破坏 | `ota_flash_if.c` 里对任何擦除请求做 `if (addr < OTA_SLOT_A_ADDR) return OTA_FLASH_ERR_PROTECT;` 硬保护 |
| Bootloader 自身被 APP 的下载流程覆盖 | 变砖，只能 SWD 救回 | ① 上述地址硬保护；② `0x34` 只接受 `loadAddr ∈ {Slot A, Slot B}` 的请求；③ BL 区永不作为下载目标 |
| 2048 字节页擦除占用 FLASH 总线，且 IWDG 为 3 s | 擦除中喂狗失败 → 复位循环 | 每次擦除/编程前 `HAL_IWDG_Refresh()`；单页擦除典型 20~40 ms，远小于 3 s；BL 中若启用 IWDG，须在 ISO-TP 等待循环内也喂狗 |
| `nBOOT0`/BOOT0 引脚把启动地址改到别处 | 上电不跑 BL | 保持 `BOOT0 = 0`（从 `0x08000000` 启动）；不要启用 `nSWBOOT0` 相关组合把主 Flash 映射掉 |
