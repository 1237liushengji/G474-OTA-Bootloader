## 二、P1 现象的精确定义（这是本文最重要的一节）

### 2.1 旧结论 vs 实测数据

`docs/APP启动重启循环-诊断报告-2026-10-10.md` §1.2 的结论是：

> "只要写 `TXBAR` 的请求位（真正请求发一帧），**AHB 总线就被挂住约 3 秒**直到复位。"

**这个结论与插桩日志直接矛盾。** `logs/_hse.txt`（带完整 HAL 级插桩）显示：

```
[16:25:31.198] [clk] CCIPR   =00000000          ← FDCANSEL=00 → 内核时钟源已是 HSE ✅
[16:25:31.199] [hal] copy: payload OK            ← 消息已写入消息 RAM
[16:25:31.220] [hal] CCCR  =00000000  PSR=0000070F  TXBC=00000000  TXFQS=00000003
[16:25:31.241] [hal] probe OK -> peripheral writable   ← 写 TSCV 成功，外设可写
[16:25:31.241] [hal] now write TXBAR...
[16:25:31.241] [hal] AMT: after TXBAR write      ← ★ TXBAR 写完立即返回
[16:25:31.241] [boot] T4: after AddMessageToTxFifoQ tick=0x00000874
```

**T3 tick=0x838 → T4 tick=0x874，仅 60 tick ≈ 0.6ms —— 写 `TXBAR` 本身完全没挂。**
复位发生在 `T4` 之后 **3.15 秒**（`16:25:28.386 / 31.241 → 34.4`）。

### 2.2 真正的现象：间歇性挂死 + IWDG 复位

`logs/_final.txt`（**TX 已跳过**版本）与 `logs/_final2.txt`（同版）对比：

| 日志 | S3 打点 tick | S5 是否出现 | 结果 |
|---|---|---|---|
| `_final.txt` | 0x2DF | ❌ **从未出现** | 3.07s 后 IWDG 复位 |
| `_final2.txt` | 0x2DF | ✅ 0x2E6 | 正常跑到 `H: before LCD/IWDG block` |

**同一版本固件、同一 tick 位置、行为不一致 → 这是"间歇性"故障，不是确定性故障。**

关键点：`_final.txt` 里 `S3` 之后**连 `S5: before restore CAN_Configure` 都没打印**。
而 `CAN_SelfTest` 中 S3→S5 之间**只有一句 `s_loopbackSelfTest = false;`**（纯 RAM 写，
不可能耗时 3 秒）。最可能的两种解释：

- **A**：日志丢字（板子先被 CH340 的 RTS/DTR 复位，只发出了半截日志）→ **非真实卡点**
- **B**：卡在**紧随其后的 `CAN_Configure()` → `HAL_FDCAN_Stop()` 等待循环**里

**必须用实验区分 A / B（见 §4）**，不能凭现有日志下结论。

### 2.3 已完成的排除项（这些**不是**根因）

| 被排除项 | 排除依据 |
|---|---|
| **消息 RAM 地址计算错误** | HAL `FDCAN_CalcultateRamBlockAddresses()` 按 `SRAMCAN_SIZE=0x350` 逐实例偏移，与 **RM0440 §44.3.3 + ST 官方社区确认帖 + `stm32-hal2`** 三方一致。FDCAN2 消息 RAM 基址 `0x4000A750`，Tx FIFO 区 `0x4000A750+0x278=0x4000A9C8`，**在有效范围内**。`_hse.txt` 的 `[ram] A750=A55AA55A` / `A9C8=A55AA55A` 探针也证明**可读写** |
| **消息 RAM 布局常量错误** | 同上，848B/实例与 G4 的 212 words 吻合 |
| **消息 RAM 不可访问** | `[ram]` 探针全部回读 `A55AA55A`（成功）；`[hal] probe OK -> peripheral writable` |
| **内核时钟源仍为 PCLK1** | `[clk] CCIPR=0x00000000` → `FDCANSEL=00`=**HSE**，**修复已生效** |
| **外设总线时钟未使能** | `[clk] APB1ENR1=12000400` → bit25(FDCANEN)=1 ✅ |
| **控制器状态异常** | `CCCR=0`（未进 INIT、未配置变更）、`PSR=0x70F`（Bus Idle、LEC=No Error）、`TXBC=0`、`TXFQS=3`（FIFO 空）、`TXBRP=0` |
| **位时序（8tq/10tq/16tq）** | 三种都测过，都挂（`2026-10-10` 日志） |
| **自动重传开关** | DISABLE 后仍挂 |
| **回环 vs 正常模式** | 两者都挂（`_final.txt` 里连 loopback 的 **TX 都没做**也挂） |
| **写 TXBAR 挂死 AHB** | **本文推翻**：T3→T4 仅 0.6ms，写操作本身立即返回 |

### 2.5 ✅ 根因（2026-10-11 最终定位，详见 §四之补）

**`b2133f1` 在给 HAL 加 `TSCV=0U` 探针时，误删了 `HAL_FDCAN_Init()` 内约 90 行核心配置代码**
（`NBTP` 位时序写入、`TXBC` FIFO 模式、`CCCR` 操作模式/帧格式等段）。

⟹ **位时序寄存器 `NBTP` 从未被写入**（保持复位值 0 = 非法时序）→ 控制器未配置 →
协议引擎无法发送 → 挂死 → IWDG 3 秒复位。

已修复（提交 `36590c1`）：HAL 逐字节还原官方基线 + 位时序采样点修正 + 自检恢复。

### 2.4 已排除项之外的候选（**已被 §2.5 取代，保留作排查参考**）

#### 候选 ①：`HAL_FDCAN_Init/Stop` 的超时判定依赖 `HAL_GetTick()`，而该值在启动早期可能不可靠

`stm32g4xx_hal_fdcan.c:188`：`#define FDCAN_TIMEOUT_VALUE 10U`

`HAL_FDCAN_Init` 里有 **3 个等待循环**，全部形如：

```c
tickstart = HAL_GetTick();
while ((CCCR & FDCAN_CCCR_CSA) == FDCAN_CCCR_CSA)
{
    if ((HAL_GetTick() - tickstart) > FDCAN_TIMEOUT_VALUE) { ...return HAL_ERROR; }
}
```

**若 `HAL_GetTick()` 在该时刻不递增**（SysTick 未起 / 被关 / `uwTick` 初值问题），
`HAL_GetTick() - tickstart` 恒为 0 → **永不超时 → 死等 → IWDG 3 秒复位**。

这与"3.07 秒复位"**高度吻合**（3.07s ≈ IWDG 周期）。
也与"间歇性"吻合（取决于 SysTick 此刻是否已在跑）。

**反证**：`_hse.txt` 里 `[boot] tick0=671 tick1=708 delta=37` 证明**主循环里的 SysTick 正常**。
但这**不能证明 `CAN_Init` 调用时刻**的 tick 正常（`CAN_Init` 在 `tick0/tick1` 检查**之后**才调用，
且 `HAL_Init()` 里 `HAL_InitTick()` 的调用时机在 BL 跳转场景下需要单独确认）。

#### 候选 ②：STM32G474 **早期硅版本 errata**（从未排查）

- 全项目**从未记录 IDCODE / REV ID**
- STM32G4 的 FDCAN 在部分 **"Category 2"器件 / 早期 Rev** 上有已知问题
- 佐证：`2026-10-10` 日志里"消息 RAM 逐地址探测可读写"**曾是**排除项，
  但后来发现"SVD 里根本没有 RXF0C/RXF1C/TXBC/TXEFC 四个寄存器"（`can.c:3384-3388` 注释），
  说明**对该芯片 FDCAN IP 的认知曾出现反复** —— 这正是 errata 存在的典型征兆

#### 候选 ③（旁证）：`HAL_FDCAN_Stop()` 的等待循环用**空转计数**而非 tick

```c
while ((CCCR & FDCAN_CCCR_INIT) == 0U)          // HAL_FDCAN_Stop
{
    if (Counter > FDCAN_TIMEOUT_VALUE) { ...return HAL_ERROR; }   // ← Counter 是空转计数
    Counter++;                                   //    不是 tick！
}
```

`CAN_Configure()` 在第二次及以后调用时会走 `HAL_FDCAN_Stop()`。
**如果 `CCCR.INIT` 置位后硬件因故不响应**（如外设被 BL 的 `MspDeInit` 关过时钟后未完全复位），
这里的空转计数会在很短时间内溢出（`0xFFFF` 次空转 ≈ 几 ms），**返回 `HAL_ERROR`**，
而 `CAN_Configure` 里 `if (HAL_FDCAN_Stop(&hfdcan2) != HAL_OK) return HAL_ERROR;` → 它**不会挂死**，
只会让 `CAN_Configure` 失败。**所以此条更像"失败"而非"挂死"**，列为旁证。

## 三、P2 串口 RX 的诊断（定性为硬件，且取证手段本身被污染）

### 3.1 现象

- 连续发送 145 条命令后 `rxIrq` **恒为 0**
- 但 USART1 配置**全部正确**：`CR1=0x2D`(UE|RE|TE|RXNEIE)、`BRR=0x516`、`ISER1=0x20`、
  `MODER=ABEBFFFF`（PA10 = AF7）、`IDR=A600`（PA10=1 空闲高）

**⟹ 信号未到达 PA10。**

### 3.2 🔴 决定性障碍：CH340 的 DTR/RTS 接了 NRST

工作日志（2026-10-11）记录了两个已复现的现象：

| 动作 | 后果 |
|---|---|
| `ser.open()` | 打开瞬间 DTR/RTS 拉高 → **板子被按在复位上** |
| `ser.write()` | **写数据也会复位板子**（8 秒内必出现 2 轮 BL 启动日志） |

用户侧交叉验证：**XCOM（串口助手）打开也完全空白**，断电重上电后同样无输出。
纯 SWD 交叉验证（不碰串口，12s 采样 8 次）：PC 全在 APP 范围、每次不同、**从未复位** →
**APP 稳定跑主循环**。

`RCC_CSR = 0x0437F801`：`PINRSTF(bit26)=1`、`IWDGRSTF(bit29)=0` → **复位源是 NRST 引脚**。

### 3.3 结论

**P2 在软件侧无可修之处。** 必须硬件层解决：

1. 查原理图 / 飞线，确认 **CH340 的 DTR/RTS 是否真的接到 NRST**
2. 若有跳线，**断开 RTS→NRST**；若无，考虑串口线加隔离或改用独立 USB-TTL 模块
3. 在 RX 能验证之前，**PC→设备的命令通道不可用**

### 3.4 对 OTA 主流程的影响（重要）

用户已明确：**Q2 = A（纯 CAN 通道，UDS `0x34/36/37` 经 ISO-TP）**。

这意味着 **P2 不阻塞 OTA 数据通道** —— OTA 走 CAN，不走串口。但 P2 仍会阻塞：
- 用人机命令给设备发 `10 03`（进入扩展会话）的便捷途径（可改用诊断仪角色板）
- 所有串口控制台调试手段（`stats` / `diag` / `help`）

**⟹ 优先级判定：P1 ≫ P2**，但 P2 的硬件确认成本很低（看一眼原理图），建议并行。

## 四之补：§2.5 根因定位（2026-10-11 新增，这是 P1 的最终答案）

### 证据

`git show b2133f1 -- G474/Drivers/STM32G4xx_HAL_Driver/Src/stm32g4xx_hal_fdcan.c`
的 diff 头是 **`@@ -410,107 +410,14 @@`** —— **107 行被删减成 14 行**。

`b2133f1` 在给 `HAL_FDCAN_AddMessageToTxFifoQ` 加 `TSCV=0U` 探针时，
**连带删除了 `HAL_FDCAN_Init()` 内整段硬件配置**：

| 被删代码 | 后果 |
|---|---|
| `Instance->NBTP = ...` | 🔴 **标称位时序寄存器从未被写入**（保持复位值 0 = 非法时序） |
| `Instance->DBTP = ...` | 数据位时序未写（经典 CAN 下无影响） |
| `SET_BIT(TXBC, TxFifoQueueMode)` | Tx FIFO/Queue 模式未设置 |
| `CCCR` 的 `DAR`/`TXP`/`PXHD` | 自动重传/发送暂停/协议异常未设置 |
| `CCCR` 的 `TEST/MON/ASM` + `TEST.LBCK` | 🔴 **操作模式未设置**（normal/loopback 都不生效） |
| `MODIFY_REG(CCCR, FDCAN_FRAME_FD_BRS, ...)` | 帧格式未设置 |

**这完美解释了全部现象**：

- `NBTP=0` → 位时间非法 → **M_CAN 协议引擎无法发送** → 挂死 → IWDG 3s 复位
- 与"写 TXBAR"无关：`_hse.txt` 实测 T3→T4 仅 0.6ms（写操作立即返回）
- 与"回环"无关：`_final.txt` 证明**连回环 TX 都没做也挂 3 秒**（`S3` 已 skipped）
- 与"内核时钟"无关：`CCIPR=0`(HSE) 也挂 —— 因为问题在**配置段缺失**，不在时钟源
- **间歇性**：`HAL_FDCAN_Init` 在 `CAN_Configure()` 里被调用 3 次（Init 1 + 自检 2），
  每次路径/时序略有差异，加上 `CCCR` 残留状态，导致"有时挂、有时不挂"

### 修复

1. `stm32g4xx_hal_fdcan.c` **完整还原到官方基线 `0cd7827`**（含删掉 `TSCV=0U`）
2. `can.c` 位时序 `TSEG1/TSEG2` 由 `13/2` 改 `11/4`（16tq，采样点 87.5%→**75%**）
3. `can.c` **恢复 `CAN_SelfTest` 的回环自发自收**（加 50ms 超时保护）——
   它正是验证本修复的最直接手段

### 教训（写入项目纪律）

> **vendor 库（`Drivers/STM32G4xx_HAL_Driver/`）不允许就地插桩。**
> 若必须加诊断，用以下任一方式：
> - 在**应用层**包一层（如在 `can.c` 里读寄存器存到 `g_canDiag`，**本次已采用**）
> - 用 `#if` 包住探针，并**只增不删**
> - 用调试器的 **watchpoint / 寄存器视图**直接观察
>
> **任何"为了加打点而修改 HAL 行为"的改动，都必须 `git diff` 逐行核对。**
> 本轮 `b2133f1` 的 diff 头 `@@ -410,107 +410,14 @@` 是**一眼可见的红旗**，
> 当时若有人 review 这个 diff，就能省下整整一天的误判。

## 四之补二：原始实验设计（保留作参考）

> 以下为根因未定位时设计的实验，现已被 §四之补 取代。
> 保留原因：若修复后仍有残留问题，可作为二级诊断手段。

> 目标：用**一个实验**区分 §2.4 的候选 ①（HAL tick 依赖）与候选 ②（硅版本 errata），
> 并排除 §2.2 的解释 A（日志丢字）。

### 实验设计原则

- **不依赖串口输出**（因为 P2 会让串口取证失真）→ **用 SWD 读 RAM 变量**
- **不依赖 CH340**（避免 `open`/`write` 复位板子）
- **结果只有两种**，判据明确

### 实验固件（最小化，新增一个 `main.c` 早期分支）

在 `main.c` 的 `HAL_Init()` **之后、任何外设初始化之前**插入：

```c
/* ---- P1 判据实验：放在最早期，记录 tick 行为与 CAN_Init 结果 ---- */
volatile uint32_t g_exp_magic   = 0xC0DE0001U;  /* 固件已跑到此处 */
volatile uint32_t g_exp_tick_a  = 0;            /* 进入前 tick */
volatile uint32_t g_exp_tick_b  = 0;            /* 100 次空转后 tick */
volatile uint32_t g_exp_tick_c  = 0;            /* CAN_Init 后 tick */
volatile uint32_t g_exp_can_st  = 0xDEADBEEF;   /* CAN_Init 返回码 */
volatile uint32_t g_exp_stage   = 0;            /* 阶段码：1=进INIT 2=出INIT 3=进STOP... */
volatile uint32_t g_exp_cccr_before = 0;        /* CAN_Init 前的 CCCR */
volatile uint32_t g_exp_cccr_after  = 0;        /* CAN_Init 后的 CCCR */

/* ... 在 main 里 ... */
g_exp_tick_a = HAL_GetTick();
for (volatile uint32_t i = 0; i < 1000000U; i++) { __NOP(); }
g_exp_tick_b = HAL_GetTick();   /* 判据 1：b-a 应 >0（tick 在走） */

g_exp_cccr_before = FDCAN2->CCCR;
g_exp_stage = 1;
g_exp_can_st = (uint32_t)CAN_Init();
g_exp_stage = 2;
g_exp_cccr_after = FDCAN2->CCCR;
g_exp_tick_c = HAL_GetTick();
```

### 读回方式（**不碰串口**）

```bash
# 前提：先断开所有串口工具（XCOM 等），避免 COM 口被占
STM32_Programmer_CLI -c port=SWD sn=8 mode=UR -coreReg PC
# 读 RAM 变量（地址从 Keil .map 里查 g_exp_* 的符号地址）
STM32_Programmer_CLI -c port=SWD sn=8 mode=UR -r32 <addr> 0x20
```

或者用已有的 `tools/field_dump.py` 扩展。

### 判据表

| `tick_b - tick_a` | `g_exp_can_st` | `g_exp_stage` 停在 | 结论 |
|---|---|---|---|
| **0** | — | — | 🔴 **SysTick 未跑** → 命中候选 ①，先修 tick 初始化 |
| **>0** | `0`(HAL_OK) | **2** | 🟢 `CAN_Init` 成功。故障在**之后**（`CAN_Send`/`CAN_Configure` 第二次调用）→ 继续阶段 3+ |
| **>0** | `1`(HAL_ERROR) | 1 | 🟠 `CAN_Init` 超时返回 → 读 `g_exp_cccr_after` 判断外设状态 |
| **>0** | `0xDEADBEEF` | **1** | 🔴 **卡死在 `CAN_Init` 内**（永远是 stage=1）→ 命中候选 ①② 之一，看 `cccr_after` |
| **>0** | — | 卡死在某 stage | 记录该 stage，逐段加打点 |

**无论结果如何，都不需要接串口** —— 这绕开了 P2 的所有干扰。

### 同步要做的取证（一次做完，避免反复插拔）

```bash
# 1) 每次烧录/实验前，先读一次芯片身份（本项目从未记录！）
STM32_Programmer_CLI -c port=SWD sn=8 mode=UR -r32 0xE0042000 1   # DBGMCU_IDCODE
#    DEV_ID(低16位, G474=0x469) / REV_ID(高16位, 用于查 errata)
# 2) 读 DBGMCU 的 FDCAN 冻结位（确认调试器 halt 时 FDCAN 是否停）
STM32_Programmer_CLI -c port=SWD sn=8 mode=UR -r32 0xE0042008 1   # DBGMCU_APB1FZR1
```

**REV_ID 一旦拿到，立刻去 ST 官网查 STM32G474 errata sheet（ES0430 或对应文档）中
FDCAN 章节** —— 这是本项目**最大的信息缺口**。

## 五、对旧文档的更正（必须回填，避免后来人重走弯路）

### 5.1 更正 1：`docs/APP启动重启循环-诊断报告-2026-10-10.md` §1.2

| 旧结论 | 更正 |
|---|---|
| "写 `TXBAR` 的请求位 → AHB 总线挂住约 3 秒" | ❌ **错**。`_hse.txt` 实测 T3→T4 仅 0.6ms，**写 TXBAR 立即返回**。挂死发生在**更之后** |
| "挂死期间无中断、无 HardFault、无 Error_Handler，SWD 也连不上 —— 总线被外部持有" | 🟡 **部分错**。SWD 连不上是 **`mode=normal`/`hotplug` 连接的固有行为**（`ota/docs/09` §3 早已定性：连接即 halt 内核），**不代表总线被占**。`mode=UR` 一直可以连接 |

### 5.2 更正 2：`can.c:324-339` 的"回环 TX 挂死"注释

```c
/* 【2026-10-10 修复】跳过回环发送。
 * 实测：在 INTERNAL_LOOPBACK 模式下写 TXBAR 请求发送会把 AHB 总线挂死约 3 秒，... */
```

**该注释基于已被推翻的结论。** `_final.txt` 证明：**连 loopback 的 TX 都没做（S3 明确 skipped），
同样会挂 3 秒** → 说明挂死**与发送动作无关**。

### 5.3 `CAN_HEARTBEAT_ENABLE=0` 的临时措施

`main.c:263-273` 注释称"在找到根因前禁用周期发送"。
由于 P1 根因**尚未真正定位**，**该开关应保持 0**，不要急于改回 1 —— 否则会掩盖故障、
让"间歇性挂死"看起来像"稳定运行"。

**注意**：心跳禁用意味着**双机 CAN 通信完全不通**，OTA 的 `0x34/36/37` **必然无法跑通**。
所以 P1 是 OTA 的**硬前置条件**。
