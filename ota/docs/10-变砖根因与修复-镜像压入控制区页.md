# 10 · 变砖根因与修复：BL 代码被链接进了控制区页

> 状态：**根因已定位并修复；两道防线已加（链接布局 + 整页恢复）；守卫已自证。**
> 板上固件当时确实已成砖（下面是实测证据，不是推断）。
> 剩余一步是"冷启动确认 APP 是否被跳转"——需要一次**不接调试器**的上电取证（见 §7）。

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 板子为什么"上电没反应" | **两个独立缺陷叠加**：① BL 把自己的复位向量代码擦掉了（变砖，§2–§4）；② `.bss` 不清零导致 UART 初始化 HardFault（§5） |
| 为什么会塞进去 | `bl.sct` 的执行域是 `0x08000000 + 0xB800`（代码紧挨向量表铺），且 `BL.uvprojx` 的 `<umfTarg>` 是 **1**，µVision **根本没在用 `bl.sct`** |
| 为什么以前没发现 | `ota_common.h` 的编译期断言**只看宏、看不到链接结果**；而当时的静态守卫也只查源码文本，不查 `.hex` |
| 现在怎么防 | ① 链接布局：页 0 只放向量表，代码从 `0x08000800` 起；② `BL_ParamStore` 改为**整页恢复**；③ **去掉 `UNINIT`** + UART 句柄显式清零；④ 新增守卫 `[C9]` + 产物审计 + 2 个反例自证 |

## 2. 失效链条（三个环节缺一不可）

### 环节 A · 链接布局把代码铺进了页 0

`ota/bootloader/MDK-ARM/bl.sct`（事故版本）：

```
LR_IROM1 0x08000000 0x0000B800  {
  ER_IROM1 0x08000000 0x0000B800  {   ; ← 执行域从 0x08000000 开始
    *.o (RESET, +First)               ;   向量表占页首 0x1D8
    .ANY (+RO)                        ;   ← 其余代码就直接从 0x080001D8 往下铺
```

于是**代码正好压住控制区副本 0（0x1D8）与副本 1（0x400）**。

### 环节 B · µVision 压根没用这个 scatter 文件

`BL.uvprojx` 里 `<umfTarg>1</umfTarg>` = "使用 Target 对话框内存布局"，
µVision 会**按 IROM/IRAM 重新生成**分散加载文件，`<ScatterFile>bl.sct</ScatterFile>` 形同虚设。

`make_bl_project.py` 本来想关掉它，但写的是 `<UseMemoryLayoutFromTargetDialog>` ——
**这个标签名在 µVision 工程里根本不存在**（正确的叫 `<umfTarg>`），
所以那次"关闭"从来没生效。这是链条里最隐蔽的一环：改动看着做了，实际没做。

### 环节 C · 写控制区时只回写两样东西

`bl_param.c` 的 `BL_ParamStore()` 是"整页擦除 + 回写"，而旧版只回写：

1. 页首向量表 `[0, 0x1D8)`；
2. 同页的**另一份**配置副本。

**它不回写代码。** 于是页 0 里若有代码，第一次写控制区就把它擦没了。

## 3. 实测证据（怎么定案的）

### 3.1 产物层面：镜像真的压住了保留区

`ota/scripts/audit_bl_layout.py` 对事故版 `firmware/BL.hex`：

```
检查 1 · 镜像是否占用控制区保留区
  [!!] PRIMARY 副本0 @ 0x080001D8 被镜像占用 48/48 字节  00 F0 02 F8 00 F0 92 F8
  [!!] PRIMARY 副本1 @ 0x08000400 被镜像占用 48/48 字节  00 26 20 2F A4 BF 5E 46
检查 2 · 页 0 非 0xFF 字节: 2030/2048      ← 整页几乎全是代码
```

（那两串字节是 Thumb 代码：`00 F0 02 F8` = `BL`，`00 26 20 2F` 是 64 位除法的一部分。）

### 3.2 芯片层面：片上就是"擦过又只补回两样"的样子

读回页 0（事故后的片上实况）：

```
页 0 片上有数据: 568 字节
  0x08000000 ~ 0x08000208   (520 字节)  ← 向量表(472) + 控制区副本0(48)  ✅ 有效 seq=1
  0x08000400 ~ 0x08000430   (48 字节)   ← 正是旧 STEP-3 从页镜像里"照抄回来"的那 48 字节代码
复位向量 = 0x08000325 -> 入口 0x08000324
入口处 16 字节 = FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF   ← 被擦掉了
```

**568 字节这个数字就是铁证**：它恰好等于"向量表 + 一份配置 + 旧算法保留的另一份 48 字节"，
不多不少 —— 只有 `BL_ParamStore` 那条路径能造出这个形态。
复位向量指向的位置全 `FF`，所以上电必然 HardFault → 表现就是"什么都没反应"。

### 3.3 调试器层面：连着调试器，固件永远不会跑

```
> STM32_Programmer_CLI -c port=SWD mode=normal -score -coreReg PC
Core is halted
PC       = 0x0800092C        ← 正好是复位向量入口
```

`0x0800092C` 处是 `09 48 80 47`（`LDR r0,[pc,#36]` + `BLX r0` = `__main`），
但内核**停在复位向量上没执行**。反复 `-rst -run` 也一样。

**结论：只要 ST-Link 处于可连接状态，CubeProgrammer 一连接就把内核停在复位向量。**
`ota/docs/09` §3 记过这条（`mode=UR` 连接即 halt），本次确认 **`mode=normal` 同样如此**。
所以"判断板子在不在跑"必须**断开调试器**，用 Flash 打点或串口取证。

## 4. 修复（四处）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `ota/scripts/bl_layout.py`（新增，**单一真相源**） | 规范 scatter：**两个加载域**，`LR_IROM1` 只覆盖页 0，`ER_IROM1` 只放向量表（472B 正好放满），代码区 `ER_IROM2` 从 `0x08000800` 起 |
| 2 | `ota/bootloader/MDK-ARM/bl.sct` | 按上面的规范重写 |
| 3 | `ota/bootloader/MDK-ARM/BL.uvprojx` | `<umfTarg>` **改为 0**（否则 scatter 被无视）；IROM/OCR_RVCT4 = `0x08000000 / 0x0000B800` |
| 4 | `ota/bootloader/Core/Src/bl_param.c` | `[PARAM-STEP-3]` 由"只回写向量表 + 另一份副本"改为**整页恢复**：按 8 字节双字把页镜像里除"本次要写的那一份"以外的内容原样写回（从地址 0 递增 → 向量表最先落盘） |

> 第 4 条是**第二道防线**：就算链接布局将来又被改错，`BL_ParamStore` 也不会再自杀。
> 第一道防线（正确的 scatter + `umfTarg=0`）保证页 0 压根没有代码。

**为什么必须拆成两个加载域**（这点踩过坑，记下来）：
同一个加载域里放两个执行域时，链接器会把第二个域的**加载地址**紧挨着排，
于是出现"加载地址 0x080001D8 / 执行地址 0x08000800"的自我覆盖，armlink 直接报
`L6788E`；同时第二个域不是根区，还会连带报 `L6202E / L6203E`。
拆成两个加载域后 `ER_IROM2` 成为根区，加载地址 = 执行地址，三个错误一起消失。

## 5. 第二个根因：`UNINIT` 让 `.bss` 不清零 → UART 初始化 HardFault

修好链接布局后把 BL 烧回板上，LED 会闪几下然后停 —— 说明**代码在跑，但跑到一半就死了**。
用调试器读回现场，一次就定死了：

```
Core is halted
PC     = 0x08000936            ← 正好是向量表里的 HardFault 入口（HardFault = 0x08000937）
HFSR   = 0x40000000            ← FORCED（可配置错误升级成 HardFault）
CFSR   = 0x00008200            ← BFSR=0x82：PRECISERR + BFARVALID
BFAR   = 0x20FB0EA4            ← 出错的数据地址：**不在任何合法存储器区间**
异常压栈帧 PC = 0x08006CDC     ← 出错指令所在
```

反汇编那一条：

```
0x08006cd4:  MOV  r1,#0x7eac
0x08006cd8:  MOVT r1,#0x800         ; r1 = 0x08007EAC（常量表基址）
0x08006cdc:  LDRH r1,[r1,lr,LSL #1] ; ← 出错：表下标 lr 是垃圾值，越界成 0x20FB0EA4
```

`lr` 来自 `LDR lr,[r4,#0x24]`，也就是 **UART 句柄里的 `Init.ClockPrescaler`**。
对照 HAL 源码 `stm32g4xx_hal_uart.c`：

```c
usartdiv = (uint32_t)(UART_DIV_SAMPLING16(pclk, huart->Init.BaudRate, huart->Init.ClockPrescaler));
/* 该宏内部：UARTPrescTable[huart->Init.ClockPrescaler]  ← 拿它当下标 */
```

而 `bl_uart.c` 的初始化**只设了 8 个字段，没设 `ClockPrescaler`**（`OneBitSampling`、
`AdvFeatureInit` 等同样没设）。它之所以平时"没事"，是因为别人会替它清零 —— 但
**BL 的散列文件把 RAM 域标了 `UNINIT`，启动代码因此不清 `.bss`**：

```
RW_IRAM1 0x20000000 UNINIT 0x00020000  { .ANY (+RW +ZI) }   ← 事故版本（现已去掉 UNINIT）
```

于是 `s_huart1` 上电后是**内存里的残留值** → `ClockPrescaler` 随机 → 下标越界 → 总线错误。
**这也解释了为什么现象时好时坏**：只有残留值恰好是合法下标（如 0）时才正常，
`ota/docs/08` 把这轮"上电没输出"记成了 HSE 晶振问题，其实主因在这里。

### 修复（两道一起上）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `ota/scripts/bl_layout.py`（散列正文） | **去掉 `UNINIT`**：`.bss` 正常清零（8KB 清零约几十微秒，换掉"随机上电行为"完全值得） |
| 2 | `ota/bootloader/Core/Src/bl_uart.c` | `BL_UartInit()` 里先 `memset(&s_huart1, 0, sizeof(s_huart1))`，再逐字段赋值，并**显式设 `ClockPrescaler = UART_PRESCALER_DIV1`** |

> APP 侧没有这个问题：它的 `.bss` 正常清零，`ClockPrescaler` 恰好为 0（= DIV1）。
> 但 APP 的 `bsp_uart.c` 同样没显式设该字段 —— **属于同一类隐患**，建议一并补上。

### 修复后的实测

```
PC = 0x08002148   BL:BL_DiagDelay+0x6F     ┐
PC = 0x08002104   BL:BL_DiagDelay+0x2B     │ PC 在变化 = 固件确实在运行
PC = 0x08001E52   BL:BL_CanPoll+0x5        │ （LED 自检延时 + CAN 轮询）
PC = 0x08007358   BL:main+0x2A3            ┘
```

**板上固件从"变砖"恢复为"正常运行"**，且页 0 仍只有 472 字节向量表（写控制区的自毁路径没有复现）。

## 7. 这一轮学到的（方法论，避免重犯）

1. **编译期断言看不见链接结果。** `ota_common.h` 的血线断言只比宏，
   代码有没有真的铺进页 0，只有**审计 `.hex`** 才知道。→ 所以有了 `audit_bl_layout.py` 与 `[C9]`。
2. **"改了"不等于"生效"。** `<umfTarg>` 那处，脚本写了一个不存在的标签名，
   表面上做了关闭动作，实际开关一直是 1。→ 凡"关开关"的改动，都要有一条**独立断言**确认它真的关了。
3. **调试器会改变被观测对象。** `mode=UR` 与 `mode=normal` 连接都会把内核停在复位向量；
   用它判断"是否在运行"必然得到错误结论。→ 判定运行状态只能用**不接调试器**的取证。
4. **取证通道本身也会失效。** 断串口助手占用只是第一层；这次更隐蔽的是
   **USB 转串口由板子供电**：一断电端口就消失，重新枚举要 3~6 秒，
   而 BL 在几百毫秒内就把横幅打完了 —— 日志注定抓不到。
   → `serial_capture.py` 现在把"掉线"当一等事件（记时间戳并自动重连），
   并在无串口条件下提供 **Flash 面包屑**（`BL_BOOT_BREADCRUMB`）作为判据。
5. **能持久化的证据优先。** Flash 写入不受 halt / 断电 / 重新枚举影响，
   比"读寄存器"和"抓串口"都可靠。

## 8. 当前遗留与下一步

### 8.0 现在的板上状态（2026-10-05 16:20）

✅ **不再变砖**：烧的是双修复版 `firmware/BL.hex`（`sha256:b1d555dfd073eb18` 前 16 位），
页 0 只有 472 字节向量表，PC 在 BL 代码里变化 —— 固件确实在运行。
Slot A 的产线镜像仍完好（`magic=0x47344F54`、`hdrCrc` 自校验 OK、"BL 判据全部满足"）。

❓ **但 BL 停在 recovery，没有跳转 APP。** PC 采样落在
`BL:main+0x2A3` / `BL:BL_CanPoll` / `BL:HAL_FDCAN_GetRxMessage`，
即 recovery 的 `for(;;)` 主循环；且页 0 里**没有**控制区写入痕迹 ——
说明它**不是**走"两个槽都无效"那条路（那条会写 `lastError`），
而是 `BL_BootWindow()` 判定**收到了诊断请求**（`main.c:169`）后主动进的 recovery。

下一步就是查这一条：上电窗口里 CAN 上到底来了什么（噪声？另一块板的流量？过滤器放太宽？）。
**最有效的做法是把串口日志抓全**（BL 会打印 `BL: diag request in boot window -> recovery`）。
本接线下串口随板断电重枚举，抓不到上电横幅，两个可行办法见 §8.1。

### 8.1 遗留一：串口日志抓不全（要把取证通道修好）

本接线下 USB 转串口**由板子供电**：一断电端口就消失，重枚举要 3~6 秒，
而 BL 在几百毫秒内就把横幅打完了 —— 上电日志注定错过（实测两次，日志只有 lost/back 时间戳）。
两个可行办法（任选其一）：

* **换一条不断的串口**：用外部 USB-TTL（由 PC 供电）接板子的 USART1 TX，
  这样断电重上电时端口不掉，横幅就能完整抓到。（**推荐，后续所有上板测试都受益**）
* **Flash 面包屑**：把 `BL_BOOT_BREADCRUMB` 置 1 编译烧录，上电后**再接调试器**读
  `0x080001D8` —— 出现 `magic="G4BL"`、`seq>=1` 即证明"BL 确实执行过"，
  同时证明"写控制区不再自毁"（这正是本次事故路径的正向回归验证）。

> ⚠️ 调试器本身也会干扰：`mode=UR`/`mode=normal` 连接会把内核停在复位向量；
> 而 `hotplug` 模式虽然报 `Core is running`，但**发不出复位**（`Unable to reset MCU!`），
> 且失败后常把目标留在 `DEV_TARGET_HELD_UNDER_RESET`，甚至把内核留在
> **`Core is locked up`**（实测：连续几次失败的复位尝试之后，`PC` 读回 0x03000000 这种非法值）。
> 此时读选项字节会得到**全 0 的假值**（看起来像 `RDP=Level 1`，其实是读不到）。
> **一次断电重上电即可全部恢复** —— 本次两种假象都复现并确认过
> （恢复后读到的是 `RDP=0xAA Level 0`、`DBANK=0x1`，Flash 内容逐字节正确）。
> 结论：**别用调试器去"复位并观察"**，那是在改写被观测对象。
