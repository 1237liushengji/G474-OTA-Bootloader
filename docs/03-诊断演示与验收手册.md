# 诊断演示与验收手册

> 本文给出从接线到完整 UDS 交互的可复现步骤，所有输出格式对照 `console.c` 与 `uds.c` 的实际打印语句。
> 协议细节见 [ISO-TP 传输层设计](01-ISO-TP传输层设计.md) 与 [UDS 诊断栈设计](02-UDS诊断栈设计.md)。

---

## 1. 前置准备

### 1.1 硬件

| 数量 | 器件 | 说明 |
|---|---|---|
| 2 | STM32G474VET6 开发板 | 板 A = 诊断仪，板 B = ECU |
| 2 | SN65HVD230 CAN 收发器 | 3.3V 供电，与 MCU 电平直连 |
| 2 | USB 转串口 | 分别接两板的 USART1（PA9=TX / PA10=RX，115200 8N1） |

总线接线：CANH↔CANH、CANL↔CANL、**GND↔GND 必须共地**。
上电前用万用表测两模块 CANH–CANL 间电阻应约 **60Ω**（两个 120Ω 终端并联）。

### 1.2 固件角色

诊断功能依赖两端角色互补，**必须烧录两份不同固件**：

```
板 A：Drivers/User/Inc/can.h 中  #define CAN_NODE_ROLE  CAN_NODE_A   → 重新编译 → 烧录
板 B：Drivers/User/Inc/can.h 中  #define CAN_NODE_ROLE  CAN_NODE_B   → 重新编译 → 烧录
```

> 改一处宏后必须**完整重编译**，不能只烧录不重编。

### 1.3 串口参数

`115200 8N1`。任意串口助手均可；推荐 `tools/can_console.py`（自带彩色解析，见第 5 节）。

## 2. 命令清单

`diag` 命令**仅在板 A（诊断仪角色）编译进去**，板 B 上不提供。

| 命令 | 构造的请求 | 用途 |
|---|---|---|
| `diag ver` | `22 F0 00` | 读版本 DID（16 字节，**多帧**） |
| `diag up` | `22 F0 01` | 读运行时间 DID |
| `diag stat` | `22 F0 02` | 读通信统计 DID（19 字节，**多帧**） |
| `diag dtc` | `19 01 FF` | 读故障码列表 |
| `diag ext` | `10 03` | 进入扩展会话 |
| `diag def` | `10 01` | 返回默认会话 |
| `diag tp` | `3E 00` | 手动发送 TesterPresent |
| `diag led 0\|1` | `2E F0 10 <v>` | 写 LED（**需扩展会话**） |
| `diag raw <hex>` | 自定义 | 最多 8 字节，用于触发 NRC 等边界场景 |

## 3. 标准演示流程

以下为板 A 串口的实际输出，按顺序执行即可完整演示 UDS 会话、权限、多帧与故障码。

### 步骤 1：读版本号（多帧 ISO-TP）

```
> diag ver
diag>> 22 F0 00 (via ISO-TP 0x7E0)
diag<< (16 bytes): 62 F0 00 47 34 37 34 2D 43 41 4E 20 76 33 2E 30
  ver: G474-CAN v3.0
```

**看点**：应答 16 字节超过单帧上限，因此这条命令**每次都真实走一遍 FF + FC + CF×2** 的分段与流控协商。

### 步骤 2：默认会话下写 LED 被拒（权限语义）

```
> diag led 1
diag>> 2E F0 10 01 (via ISO-TP 0x7E0)
diag<< (3 bytes): 7F 2E 22
  NRC: sid=2E code=22
```

**看点**：NRC `0x22` = `conditionsNotCorrect`。默认会话不允许写操作 —— 这是 UDS 的安全设计，量产 ECU 会在此基础上叠加 `0x27` 安全访问。

### 步骤 3：提升会话权限

```
> diag ext
diag>> 10 03 (via ISO-TP 0x7E0)
diag<< (6 bytes): 50 03 00 32 01 F4
```

**看点**：应答声明 `P2 = 50ms`、`P2* = 5000ms`。此刻服务器启动 **S3 = 5s** 计时，客户端也开始每 2s 自动发 `3E 80` 保活。

### 步骤 4：写 LED 成功

```
> diag led 1
diag>> 2E F0 10 01 (via ISO-TP 0x7E0)
diag<< (3 bytes): 6E F0 10
```

**现象**：**板 B 的蓝色 LED 点亮**。回读确认：

```
> diag raw 22 F0 10
diag>> 22 F0 10 (via ISO-TP 0x7E0)
diag<< (4 bytes): 62 F0 10 01
  led: 1
```

> **为什么不用抢时间？** 客户端每 2 秒自动发 `3E 80` 保活，S3 不会超时。这与 CANoe / PCAN-Diag 的行为一致 —— 若没有这个机制，手工命令间隔超过 5 秒就会莫名收到 NRC 0x22。

### 步骤 5：读故障码

```
> diag dtc
diag>> 19 01 FF (via ISO-TP 0x7E0)
diag<< (12 bytes): 59 01 01 C1 00 00 C1 01 00 C1 02 00
  DTC list (id,active):
   C100 0
   C101 0
   C102 0
```

**看点**：`active = 0` 表示总线健康。这三条 DTC 并非固定演示数据，而是**由驱动的真实错误计数实时合成**（见第 6 节故障演练）。

### 步骤 6：返回默认会话

```
> diag def
diag>> 10 01 (via ISO-TP 0x7E0)
diag<< (6 bytes): 50 01 00 32 01 F4
```

## 4. 边界与异常场景

### 4.1 未知 DID → NRC 0x31

```
> diag raw 22 F0 FF
diag>> 22 F0 FF (via ISO-TP 0x7E0)
diag<< (3 bytes): 7F 22 31
  NRC: sid=22 code=31
```

### 4.2 未实现的服务 → NRC 0x11

```
> diag raw 31 01 02 03
diag>> 31 01 02 03 (via ISO-TP 0x7E0)
diag<< (3 bytes): 7F 31 11
  NRC: sid=31 code=11
```

### 4.3 非法会话子功能 → NRC 0x12

```
> diag raw 10 05
diag>> 10 05 (via ISO-TP 0x7E0)
diag<< (3 bytes): 7F 10 12
  NRC: sid=10 code=12
```

### 4.4 无应答 → 客户端超时

断开两板之间的 CANH 或 CANL 后任意诊断请求：

```
> diag ver
diag>> 22 F0 00 (via ISO-TP 0x7E0)
diag: response timeout
```

### 4.5 请求未完成时重复下发

```
> diag ver
diag>> 22 F0 00 (via ISO-TP 0x7E0)
diag: busy (previous request pending)
```

ISO-TP 为单通道半双工，上一个发送事务未结束前不接受新请求。

## 5. 总线侧观察（推荐）

板 B 执行 `sniff on` 后，可**同时在物理层看到完整的 ISO-TP 协商过程**：

```
> sniff on
```

再在板 A 执行 `diag ver`，板 B 串口会打印：

```
RX 12345 7E0 8 03 22 F0 00 00 00 00 00     ← 板A请求：SF
RX 12401 7E8 8 10 10 62 F0 00 47 34 37     ← 板B应答：FF，声明总长 0x010 = 16
RX 12408 7E0 3 30 00 02                    ← 板A流控：CTS / 不限块 / STmin 2ms
RX 12412 7E8 8 21 34 2D 43 41 4E 20 76     ← 板B CF，SN=1（7 字节）
RX 12415 7E8 8 22 33 2E 30 00 00 00 00     ← 板B CF，SN=2（3 字节，拼装完成）
```

`sniff` 不打过滤，打印的是**总线上出现的全部报文**，因此请求方向（`0x7E0`）与应答方向（`0x7E8`）都能看到，一次诊断交互的完整协商过程一屏呈现。

**这是讲解 ISO 15765-2 最直观的教具**：FF 声明长度、FC 授予发送权限、CF 按 SN 递增 —— 三个概念在同一屏内全部可见。

PC 端可用 `tools/can_console.py` 记录并导出 CSV 做时序分析。

## 6. 故障演练（验证 DTC 的真实性）

DTC 由驱动的真实错误计数合成，因此可以人为制造总线故障来观察其变化：

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | `diag dtc` 记录基线 | 三条 DTC 的 active 均为 0 |
| 2 | **拔掉 CANH 或 CANL**（或断开对端收发器供电） | 板 A LED1 约 1.5s 后转 100ms 快闪 |
| 3 | 保持断线数秒，让错误计数累积 | `stats` 中 `busOff` / `errPas` 增长 |
| 4 | 重新 `diag dtc` | **`C100` 或 `C101` 的 active 变为 1** |
| 5 | 恢复接线 | 链路自动恢复同步闪烁（bus-off 自动恢复 + 指数退避） |
| 6 | 两板重新上电后 `diag dtc` | 计数清零，DTC 回到 0 |

**这一步是演示中最有说服力的部分**：故障码不是写死的常量，而是随总线真实状态变化。

## 7. 验收清单

| # | 项目 | 判据 | 状态 |
|---|---|---|---|
| 1 | 编译 | 两板各自角色均 0 Error / 0 Warning | ☐ |
| 2 | 基础链路 | 两板上电 1s 内 LED1 同步翻转（周期 2s） | ☐ |
| 3 | 单帧诊断 | `diag up`、`diag raw 22 F0 10` 正常应答 | ☐ |
| 4 | **多帧诊断** | `diag ver` 返回完整 16 字节且 `ver:` 解码正确 | ☐ |
| 5 | 多帧诊断 | `diag stat` 返回完整 19 字节 | ☐ |
| 6 | **会话权限** | 默认会话 `diag led 1` → NRC 0x22 | ☐ |
| 7 | 会话权限 | `diag ext` 后 `diag led 1` → `6E F0 10`，板 B LED 点亮 | ☐ |
| 8 | **S3 超时** | `diag ext` 后立刻 `diag tp`，等 6s 再 `diag led 1` → 回到 NRC 0x22 | ☐ |
| 9 | TesterPresent 保活 | `diag ext` 后**不操作**等 10s，客户端每 2s 自动发 `3E 80`；此时 `diag led 1` 仍成功 | ☐ |
| 10 | NRC 覆盖 | `raw 22 F0 FF`→0x31；`raw 31 01 02 03`→0x11；`raw 10 05`→0x12；默认会话 `2E`→0x22 | ☐ |
| 11 | **DTC 真实性** | 制造 bus-off 后 `diag dtc` 对应 active 置 1，上电后清零 | ☐ |
| 12 | 超时与恢复 | 断线后报 `diag: response timeout`，恢复接线后自动恢复 | ☐ |
| 13 | 总线可观测 | 板 B `sniff on` 下能看到 FF / FC / CF 完整交互 | ☐ |

第 8 项与第 9 项**必须成对验证**：前者证明 S3 超时生效，后者证明 TesterPresent 保活有效。两者同时成立才说明会话管理实现正确。

## 8. 面试演示脚本（建议 3 分钟）

1. **（20s）** 两板上电 → 指出 LED1 同步闪烁，"这是基础 CAN 链路正常的判据"。
2. **（30s）** 板 B `sniff on`，板 A `diag ver` → 指着屏幕讲 **FF 声明长度 → FC 授权 → CF 按 SN 递增**，"16 字节的版本号单帧装不下，这是 ISO-TP 在真实工作"。
3. **（30s）** 板 A `diag led 1` → 收到 **NRC 0x22**，"默认会话不许写，这是 UDS 的权限模型"；`diag ext` 后重试 → 板 B LED 亮起。
4. **（30s）** 说明客户端每 2s 自动发 `3E 80` 保活 S3，"CANoe 就是这么做的，否则手工命令间隔超过 5 秒就会掉会话"。
5. **（40s）** `diag dtc` 看故障码 → 拔掉 CANH → 等几秒 → 再 `diag dtc`，**DTC 状态位翻转** → 恢复接线自动重连。
6. **（30s）** 打开代码指 `isotp.c` 的 `IsoTp_Task()`："整套传输层完全非阻塞，STmin 节拍和 N_Bs/N_Cr 超时都在主循环里，没有一处 `HAL_Delay`。"
