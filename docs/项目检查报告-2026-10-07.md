#### 本轮复核推翻的原报告结论（5 项）

这几条是复核后**主动否掉**的，不写清楚会让后来人以为"报告说的都对"：

1. **L7 是误判。** 原报告称 `app_crc32` 热路径调 3 次、每次全量重算 208KB。实测：
   `zlib.crc32` 3 次重算 208KB 共 **0.242 毫秒**（单次 0.081ms）。给它加缓存层是
   纯负优化（引入 stale 缓存风险换零收益），**故不改**，仅在此更正定性。
2. **E3 的"含 `main.c` 共 12 个 .c"是误判。** 实际就是 **11 个 .c**（`main.c` 本就在内），
   偏差在 `.h`：多一个 CubeMX 生成的 `RTE_Components.h`，故为 11+12。
3. **E6 的"两份 hex 内容分叉"是误判。** `firmware/G474_B.hex` 与
   `G474/MDK-ARM/G474/G474.hex` 的 **MD5 完全相同**（`670d4a6e…`），是同一产物的两个副本。
4. **L6 的触发条件比报告描述的弱。** 全 `bootloader/` 目录 grep `0x78` 只命中
   `bl_crc32.c` 的 CRC 查表常量——**BL 固件实际从不发 0x78**。该修复仍要做
   （属防御性加固，且上位机逻辑本就不该允许无限挂死），但不影响现有真机时序。
5. **L5 判定为「可接受」而非缺陷。** 报告的描述是准确的（`hdrCrc` 只覆盖 `[0,24)`，
   而 `reserved` 在 `[28,32)`，确实落在 CRC 保护范围之外），但它不构成实际风险：
   `OTA_IMG_OFF_RESERVED` 在 BL 侧**只被写、从不被读**——全工程唯一引用是
   `bl_image.c:252` 在 FF02 合成头时置 0，没有任何逻辑读取该字段的值。
   既然无人依赖，"校验它是否为 0"就不产生任何可观测的行为差异。
   保留原样是合理的（头里留预留字段本就是为了将来扩展，届时字段一启用就会补校验）。

#### 复核后决定「不改代码」的 2 项

* **M6**：落盘是幂等短路的（`if (cfg.lastError != otaErr)`），且只在**已失败**的降级
  路径触发——此时事务已结束，丢帧无关紧要。报告建议的"只置内存标志、事务结束后统一
  落盘"在下载已失败时**时机根本不存在**，且会让 `lastError` 丢失、破坏现场诊断。
* **M13**：Flash 擦除期间掉电必然丢页，软件无法规避。彻底解法（控制区移出代码页 /
  双 Bank 掉电保护）超出本轮范围。**已按"风险告知"登记**至
  [`ota/docs/04-AB双槽与回滚机制.md` 第 5.1 节](../ota/docs/04-AB双槽与回滚机制.md)，
  含上板操作纪律（改 BL/APP 或动分区表时必须接 SWD、不得中途断电）。

#### E2 顺带发现：`.gitignore` 曾静默丢弃基线烧写件

原 `.gitignore` 写 `BL.hex`（无路径限定），实测 `git check-ignore` 证实它会匹配
`firmware/BL.hex`——**基线烧写件会被静默排除出版本控制**。已改为路径锚定写法
（`/BL.hex`、`G474/MDK-ARM/BL/BL.hex`…），并实测复核：`firmware/*.hex|bin` 现在被跟踪，
构建输出仍被忽略。

## 二、阻断级缺陷（必须修复，否则真机一块固件都刷不进去）

### 🔴 B1　0x34 长度校验写成 10，应为 11

| | |
|---|---|
| 位置 | `ota/bootloader/Core/Src/bl_diag.c:796` |
| 契约 | 0x34 请求体 = `34 00 44` + addr(4B) + size(4B) = **11 字节** |

```c
if (len != 10U)                              // ← 应为 11U
{ ... }
addr = BL_DiagBe32(&req[3]);
size = BL_DiagBe32(&req[7]);                 // 已经访问到第 11 字节
```

代码自己都在读 `req[10]`，却把门槛设在 10——自相矛盾。

三方对照全部指向 11：

| 位置 | 长度 |
|---|---|
| `ota_host.py:589` `uds_request_download` | 3+4+4 = **11** ✅ |
| `ota_host.py:1061` 模拟器 `_uds_handle` | `!= 11` ✅ |
| `ota/app/ota_agent.c:468`（APP 同构实现） | `!= 11U` ✅ |
| **`bl_diag.c:796`（Bootloader）** | **`!= 10U`** ❌ |

**后果**：真机上 0x34 恒回 `7F 34 13`，上位机在 `request_download` 处直接抛错，一块固件都刷不进去。
**为什么没被测出**：`test_ota_host.py` 全部跑在 `SimulatedEcu` 上（走 11 字节分支），从不编译执行 `bl_diag.c`。典型的"模拟器与固件分叉"。

**修法**：
```c
if (len != 11U)   /* 34 00 44 + addr(4B) + size(4B) */
```
并在 `ota_common.h` 定义 `UDS_DL_REQ_LEN 11U`，三方统一引用，让 `verify_all.py` 能守卫。

### 🔴 B2　FF00 擦除例程要求 6 字节，上位机只发 4 字节

| | |
|---|---|
| 位置 | `bl_diag.c:486`（设备）vs `ota_host.py:1739`（上位机） |

```c
// 设备
if (len != 6U) { ... NRC 0x13 ... }          // 31 01 FF 00 + size(2B)
size = (uint32_t)BL_DiagBe16(&req[4]);        // 上限仅 65535
```
```python
# 上位机
self.uds.routine_control(UDS_ROUTINE_ERASE)   # data 缺省 b"" -> 4 字节
```

**双重问题**：
1. **长度不匹配**：上位机发 4 字节，设备要 6 字节 → 恒回 `7F 31 13`，流程在擦除阶段即中断。
2. **设计本身不可用**：`size` 字段只有 16 位，上限 65535 < 单槽净荷 212864 字节。即使修好长度，FF00 也无法表达整槽擦除。`ota_agent.c:704` 的注释也承认"≤64KB，完整槽升级请直接走 0x34"。

**修法（建议彻底废弃 FF00）**：0x34 的 `BL_DiagPrepareDownload` 已隐式无条件擦除（`bl_diag.c:187-220`），上位机 `ota_host.py:1737-1739` 那次 FF00 纯属重复劳动。删除该步骤即可同时解决长度不匹配、16 位上限、以及下述 B6 的"擦两次吃掉超时预算"三个问题。

### 🔴 B3　断点续传时块序号基线归零，续传必被 NRC 0x73 打死

| | |
|---|---|
| 位置 | `bl_diag.c:155-158` + `bl_diag.c:199` |

```c
static uint8_t BL_DiagExpectedSeq(void)
{
  return UDS_BLOCK_SEQ_OF(s_dl.blockCount + 1U);
}
// BL_DiagPrepareDownload:
s_dl.blockCount = 0U;                        // ← 续传时也清零
```

契约 `ota_common.h:179-181` 明确规定：
> 断点续传时首块序号仍按同一公式计算：`seq = ((blockIndex - 1) % 255) + 1`，其中 `blockIndex` 是**绝对块号**。

上位机 `ota_host.py:1770` 用的正是 `seq = block_seq(index)`，`index` 从 `--resume N` 起。所以 N=17 时上位机首发 `seq=17`，而设备期望 `seq=1` → `7F 36 73` → 重试 3 次仍为 17 → 抛错退出。

**关键**：上位机的模拟器**已经实现了正确逻辑**（`ota_host.py:1074-1082` 按 addr 偏移反推绝对块号）——**模拟器是对的，固件是错的**。

**修法**：`BL_DiagPrepareDownload` 中按偏移反推起始绝对块号（需先解决 B4 以确定块大小）：
```c
s_dl.blockCount = (addr - s_dl.appBase) / s_dl.blockSize;
```

### 🔴 B4　8 字节对齐要求与默认块大小 1021 互斥，续传 7/8 概率被拒

| | |
|---|---|
| 位置 | `bl_diag.c:279`（设备）vs `ota_common.h:224`（契约） |

```c
if ((addr % 8U) != 0U) { return false; }      // 双字编程：续传地址必须 8 字节对齐
```
而契约默认块大小 `UDS_DL_MAX_BLOCK_PAYLOAD = OTA_ISOTP_MAX_MSG - 3 = 1021`，**1021 mod 8 = 5**。实算续传偏移：

| `--resume N` | offset | offset % 8 | 结果 |
|---|---|---|---|
| 17 | 16336 | 0 | ✅ 通过 |
| 18 | 17357 | 5 | ❌ NRC 0x31 |
| 19 | 18378 | 2 | ❌ |
| 20 | 19399 | 7 | ❌ |
| 21 | 20420 | 4 | ❌ |
| 22 | 21441 | 1 | ❌ |

**默认配置下 8 个续传起点有 7 个被设备拒绝**，且上位机不给出任何针对性提示。这是契约层自相矛盾：块大小由 ISO-TP 上限推导（1021），却被 Flash 双字粒度（8）约束。

**修法（推荐第 1 个，一劳永逸）**：
1. **块大小归一到 8 的倍数**：契约改 `UDS_DL_MAX_BLOCK_PAYLOAD = (OTA_ISOTP_MAX_MSG - 3) & ~7U` = **1016**，三方同步。吞吐损失 0.5%，换来续传可用，同时 B3 的根因也一并消除（偏移可反推块号）。
2. 或 `BL_DiagRangeOk` 放宽为 `addr % 2 == 0`，`BL_FlashWrite` 侧把非 8 对齐起点向下取整到 8 边界。
3. 或上位机在 `--resume` 前置校验并明确报错。

### 🔴 B5　FF02 激活返回码被完全忽略 → 没刷进去也报"成功"

| | |
|---|---|
| 位置 | `ota_host.py:1823-1825` |

```python
self.log(f"激活/提交 31 01 {UDS_ROUTINE_ACTIVATE:04X}")
self.uds.routine_control(UDS_ROUTINE_ACTIVATE)
result.activated = True          # ← 无论设备回什么都记 True
```

而设备侧 `bl_diag.c:671-676` 明确会返回失败码：
```c
resp[4] = rc;    /* 0x00=成功；0x01=头写失败/回读失败/BL_ImageValidate 失败/配置写失败 */
```

即镜像头 CRC 不符、栈顶指针非法、复位向量越界、配置区写失败——**所有"固件实际没激活"的场景都回 0x01**，上位机全部丢弃，随后照常 `11 01` 复位，最后打印 `activated: True`。用户看到"刷写成功"而设备跑的仍是旧固件。

```python
rsp = self.uds.routine_control(UDS_ROUTINE_ACTIVATE)

result.activate_status = status
if status != 0x00:
    raise OtaError(f"31 01 FF02 激活失败: status=0x{status:02X}"
                   f"（可读 22 F180 检查 lastError）")
result.activated = True
```

## 三、高危缺陷

### 🟠 H1　跳转 APP 前未清 SysTick/PendSV pending，且先开中断后跳转

位置：`bl_jump.c:43-51`、`:66-71`

```c
SysTick->CTRL = 0U; ...
for (i = 0U; i < 8U; i++) { NVIC->ICER[i] = ~0U; NVIC->ICPR[i] = ~0U; }
...
__enable_irq();          // :66
__DSB(); __ISB();
entry();                 // :71  ← APP 还没跑
```

SysTick/PendSV 是**系统异常，不在 NVIC 里**——pending 位在 `SCB->ICSR`（`PENDSTSET`/`PENDSVCLR`），`NVIC->ICPR` 清不到。写 `SysTick->CTRL = 0` 只清 COUNTFLAG，**不清 `ICSR.PENDSTSET`**。

BL 全程 SysTick 以 1ms 运行，而 `BL_JumpToApp()` 紧接在 `HAL_IWDG_Refresh()` 之后被调用，**进入时几乎必然有一个 SysTick 处于 pending**。时序变成：`__enable_irq()` 立刻接受 SysTick → 通过**已改成 APP 的 VTOR** 取到 **APP 的 SysTick_Handler**，而此时 `entry()` 还没执行——APP 的 `.data` 未拷、`.bss` 未清零。行为不可预期，且无 BL 侧兜底。

**修法**：
```c
SCB->ICSR = SCB_ICSR_PENDSTCLR | SCB_ICSR_PENDSVCLR | SCB_ICSR_PENDCLRSET;
__DSB();
__enable_irq();
__DSB(); __ISB();
entry();
```

---

### 🟠 H2　`BL_PARAM_PRIMARY_WRITE=0`（官方推荐的加固手段）会擦掉唯一最新副本所在页

位置：`bl_param.c:163-173`

```c
if (s_candPage[oldestIdx] == s_candPage[newestIdx])
{
#if (BL_PARAM_PRIMARY_WRITE != 0)
  *page = (...) ? OTA_CFG_MIRROR_ADDR : OTA_CFG_PRIMARY_ADDR;
#else
  *page = OTA_CFG_MIRROR_ADDR;      // ← 恒等于 newest 所在页
#endif
```

当 `BL_PARAM_PRIMARY_WRITE == 0` 时，扫描循环（`:134-139`）跳过 PRIMARY 的两个候选，**剩下两个候选 `MIRROR c0/c1` 在同一物理页** → `oldestIdx` 与 `newestIdx` 永远同页 → 永远走此分支 → **永远擦 MIRROR 页，而那正是当前最新有效副本所在地**。

直接违反函数自己声明的血线 1（"绝不擦掉唯一最新副本所在页"）。掉电落在"擦完、尚未回写"窗口时，**4 份副本全部作废**，配置退化为默认 IDLE_A。

**讽刺之处**：该宏正是 `bl_param.c:33-35` 推荐的"规避变砖风险的加固手段"，而它引入了一个新的配置全丢窗口。

**修法**：`PRIMARY_WRITE==0` 时不存在"另一物理页"，正确做法是承认"擦页即丢一份"，在擦之前确认另一份已足够新；或引入第三份存储。**不要**保留当前这个"擦最新页"的分支。

---

### 🟠 H3　`BL_PARAM_PRIMARY_WRITE=0` 未覆盖"全部副本无效"回退路径

位置：`bl_param.c:155-161`

```c
if (oldestIdx < 0)
{
  *page = OTA_CFG_PRIMARY_ADDR;      // ← 没有 #if 保护
```

`#if` 只包住了扫描循环，**没包住这个回退分支**。置 0 的语义是"只写 MIRROR 页"，但 MIRROR 两份都无效时，代码反而去擦 PRIMARY 页——正是该开关要彻底避免的动作。全新未格式化设备必然走这条路径，等于"越干净的板子越危险"。

**修法**：把该分支一并纳入 `#if`，置 0 时改为写 MIRROR 页副本 0。

### 🟠 H4　上位机忽略对端 FC 的 STmin，147 帧背靠背连发

位置：`ota_host.py:1435-1448`

```python
bs = fr[1] if len(fr) > 1 else 0
n = len(cfs) - idx if bs == 0 else min(bs, len(cfs) - idx)
for k in range(n):
    self.tunnel.tx_frame(ISOTP_REQ_ID, cfs[idx + k])   # 无间隔连发
```

读到了 `fs`（fr[0]）和 `bs`（fr[1]），**唯独没读 `fr[2]` = STmin**。设备在 `bl_isotp.c:195` 明确要求 2ms。一个 1021 字节块 = `FF + 146×CF` = **147 帧**，而 STM32G4 的 FDCAN RX FIFO0 在本工程 HAL 中仅 **3 深度**（`stm32g4xx_hal_fdcan.c:213 SRAMCAN_RF0_NBR = 3U`），BL 侧轮询只要有一次被 2KB flash 编程阻塞超过 2ms 就丢帧 → ISO-TP SN 错序 → 整块作废。

**收发两个方向不对称**：接收方向 `ota_host.py:1465` 倒是正确发了带 STmin 的 FC。

**修法**：
```python
stmin = fr[2] if len(fr) > 2 else 0
stmin_s = 0.001 * stmin if stmin <= 0x7F else 0.0001 * (0xF1 + (stmin & 0x0F))
...
time.sleep(stmin_s)
```
根治方案：把 RX FIFO0 从 3 扩到 16+，或改用 RX 中断 + 双缓冲。

## 四、中危缺陷

| # | 位置 | 问题 |
|---|---|---|
| M1 | `bl_image.c:68-77` | 头部搜索第 2 位（`+0x100`）**深入净荷区**。契约规定头恒在 `slotBase+0`，此搜索无正向作用，反而会把净荷里形似魔数的数据**提升为合法头**。且 `loadAddr` 校验锚在 `hdrAddr` 而非 `slotBase`（`:105`），使"载入地址必须等于本槽 APP 基址"的契约约束被静默放宽；若 `hdrAddr=+0x100`，CRC 计算会越界读 0x100 字节，Slot A 情况下**跨过分区边界读进 MIRROR 控制页**。修法：只允许 `slotBase+0`，`loadAddr` 与 `slotBase + OTA_IMG_HDR_SIZE` 比较。 |

## 九、上板前必读提醒

1. **OTA 全流程从未在硬件上跑过**（`WORKSPACE_SOURCES.md:132` 明确记录），且本报告的 B1/B2/B3/B4 说明它**当前跑不通**。请勿基于"上位机 dry-run 通过"就认为链路可用——`test_ota_host.py` 全程跑在模拟器上，而**模拟器的 0x34 长度是 11，固件是 10**。
2. **B5 是最危险的一条**：即便前面所有问题都修好，只要 FF02 返回码被忽略，激活失败也会被报成"刷写成功"。上板后务必用 `22 F180`（OTA 状态）与 `22 F182`（版本）**独立确认**新固件真的在跑，不要信任上位机的 `activated: True`。
3. **M13 残余风险**：擦 PRIMARY 页时 BL 自己的向量表会短暂消失，此刻掉电 → 变砖，需 SWD 救回。H2/H3 修好后该风险仍存在（这是页内双份方案的固有代价），建议考虑把向量表移出擦除页。
4. **判断"板子在不在跑"必须断开调试器冷启动**：CubeProgrammer 的 `mode=UR` 与 `mode=normal` 连接都会把内核停在复位向量（实测 `PC = 0x0800092C`），连着调试器读状态必然得到错误结论。
5. **烧录顺序**：先烧 BL（`0x08000000`）→ 再用上位机刷 Slot A。先烧 APP 而无 BL 会因 `0x08000000` 为空而上电 HardFault。
6. **建议给守卫补两类新检查**（当前 29 项完全没覆盖）：
   - UDS 各服务请求长度与契约常量的一致性（B1/B2 这类问题才能被自动拦住）
   - 设备端与上位机在长度/序号/字节序上的**交叉一致性**（而非只查常量是否等于常量）
