# STM32G474 双CAN 工程 OTA + Bootloader 扩展方案

> 目标仓库：**[1237liushengji/stm32g474-dual-can](https://github.com/1237liushengji/stm32g474-dual-can)**
> 器件：**STM32G474VETx**（Flash 512 KB / RAM 128 KB），FDCAN2 经典 CAN 500 kbit/s，MDK-ARM 工程
>
> **本方案完全建立在现有代码之上**：现有工程已经具备 FDCAN 驱动、ISO-TP 传输层、UDS 诊断栈、
> 串口控制台。OTA 因此**不新造私有协议**，而是复用 UDS 的 `0x34/0x36/0x37` 标准刷写服务 ——
> 既能直接沿用现有 `diag` 命令与上位机解析，又与量产 ECU 的刷写流程同构。

## 2. 方案总览

```
┌─────────────────────────────── Flash 512 KB ───────────────────────────────┐
│ 0x08000000  向量表+控制区主份(2KB) ← BL 向量表必须在此，永不被擦，绝对保护区  │
│ 0x08000800  Bootloader 代码(30KB)  ← < OTA_SLOT_A_ADDR 的保护同时护住本区     │
│ 0x0800C000  Slot A  (208KB)       ← 上界恰为 Bank1 上界（DBANK=1 时）        │
│ 0x08040000  控制区镜像份(2KB)     ← 更新 Slot B 时随 Bank2 被擦，故需镜像     │
│ 0x08040800  Slot B  (208KB)       ← 下对齐 Bank2 起始                        │
└─────────────────────────────────────────────────────────────────────────────┘
       ▲                        ▲                          ▲
   Bootloader              APP（当前运行槽）          目标槽（升级时写入）
   校验/回滚/接收           提供 0x34/0x36/0x37        永不是正在运行的那个
```

三条设计主线：

1. **APP 与 Bootloader 暴露同一套 UDS 服** —— 上位机不需要知道当前跑的是谁，也不需要两套协议栈；
2. **目标槽恒为"非活动槽"** —— 正在运行的固件绝不被写入，因此**任何时刻都有一份可回滚的旧固件**；
3. **镜像头由设备在激活时合成** —— 下载流只含净固件，避免"写入起点"与"链接基址"两套偏移。

### 2.1 升级与回滚时序（浓缩版）

```
PC ──10 03──► 进入扩展会话 ──22 F181──► 查当前槽(A) ──34──► 声明写入地址=Slot B APP基址、长度=净固件大小
   ◄──74 20 03 F8── maxLen=1016（★ 0x34 隐式擦除，FF00 显式擦除已废弃）
   ──36 <seq> <1016B>──► ...（210 块，满 2KB 页才落盘）... ◄──76 <seq>──
   ──37 + 整镜像CRC32──► 残余补齐落盘 ◄──77──
   ──31 01 FF01──► 设备重算 CRC32 比对 ◄──71 01 FF 01 00 <crc>──
   ──31 01 FF02──► 设备合成槽首 32B 镜像头 + 置 TRIAL_B、trialLeft=3 ◄──71 01 FF 02 00──
   ──11 01──► 软复位 ◄──51 01──
                    ↓
   Bootloader: TRIAL_B，trialLeft 3→2 → 校验 Slot B → 跳转 → APP 自检
                    ↓ 自检通过                    ↓ 自检不通过（3 次启动内）
             FF04 落定 IDLE_B（新固件转正）    自动回滚 IDLE_A（旧固件继续跑）
```

## 4. 快速上手

### 4.1 首次烧录（**顺序不能错**）

```
1. 烧 Bootloader（IROM1 = 0x08000000，size 0x800）   → 上电进 recovery，串口打印等待刷写
2. 用上位机把 APP 镜像刷进 Slot A                     → 复位后 BL 校验并跳转
3. 以后升级全部走 OTA，不再需要 SWD
```

> ⚠️ 若先烧 APP（链接在 `0x08000800`）而没有 BL，`0x08000000` 处是全 `0xFF`，
> 复位后取到非法栈顶/复位向量会 **HardFault 死机**。**BL 必须第一个烧。**

### 4.2 打包与刷写

```bash
# 打包：给 MDK 生成的 .bin 加上 32 字节镜像头
python ota/tools/ota_host.py --pack app.bin --load-addr 0x0800C080 --version 2.0 -o app_v2.0.ota

# 离线自检（无硬件）：打印将要发送的完整报文序列
python ota/tools/ota_host.py --dry-run app_v2.0.ota

# 真机刷写（USB-CAN 适配器直连，推荐）
python ota/tools/ota_host.py --port PCAN_USBBUS1 app_v2.0.ota --precheck --verify

# 真机刷写（串口隧道：板A 中继，见 03 号文档 §6）
python ota/tools/ota_host.py --port COM5 --tunnel app_v2.0.ota --precheck --verify
```

### 4.3 自检命令（不需要硬件）

```bash
python ota/tools/test_ota_host.py        # 上位机单元测试
python ota/bootloader/verify_bl.py       # Bootloader 静态不变量自检
```

## 5. 必须知道的两个现实约束

### 5.1 吞吐：CAN 直连下约 **9 秒**，串口隧道下约 **74 秒**

**已完成吞吐优化**：`ISOTP_MAX_MSG` 由 128 提升到 **1024**，单块净荷 125→**1016 字节**。

| 环节 | 优化前（块 125 B） | 优化后（块 1016 B） |
|---|---|---|
| 满槽 208 KB 镜像的 `0x36` 报文数 | 1 835 | **209** |
| CAN 侧纯传输（147 帧/块 × 2 ms） | ≈ 73 s | **≈ 6.0 s** |
| Flash 编程（104 页 × 25 ms） | ≈ 2.9 s | ≈ 2.6 s |
| CRC32 校验 | ≈ 12 ms | ≈ 12 ms |
| **CAN 直连合计** | **≈ 76 s** | **≈ 9 s**（↑ 约 8.4×） |
| *串口隧道（ASCII 十六进制）* | ≈ 64 s | ≈ 74 s |
| **串口隧道合计** | **≈ 2~3 分钟** | **≈ 74 s** |

**两条必须知道的结论**：

1. **ISO-TP 层的 3.5 KB/s 上限没变**（由 `STmin=2ms` 决定）。块大小只减少报文条数与设备侧开销，
   所以收益体现在"少 8 倍的 `0x36/0x76` 往返与页缓冲拷贝"。
2. **走串口隧道时瓶颈会转移到串口**：CAN 侧从 73 s 降到 6 s，但串口侧仍要 ~74 s。
   要拿到完整的 8 倍收益，**必须用 PC 直连 USB-CAN 适配器**。隧道模式下建议显式调小块
   （如 `--block-size 500`）让主循环从容排空，并监控 `rxOverruns`。

**代价**：收发缓冲各 1 KB，RAM 增加约 **1.8 KB**（本机 128 KB，实际使用仅 10~20 KB）。


### 5.2 安全：三层校验，绝不"裸传"

1. **传输层逐块确认**：每个 `0x36` 必须收到 `0x76 <seq>`，序号错序立刻 NRC `0x73`；CAN 硬件层另有自动重发与 CRC15；
2. **报文级 CRC32**：镜像头 `payloadCrc` + 设备对实际写入内容重算 CRC32 比对（`31 01 FF01`）——**唯一位于 CAN CRC 之外的端到端校验**；
3. **跳转前双重结构校验**：独立校验栈顶指针（必须在 `0x20000000~0x2001FFFF` 且 8 字节对齐）与复位向量（bit0=1 且落在槽内）——挡住"CRC 正确但向量表被破坏"的极端场景。

### 5.3 绝对保护区

`0x08000000~0x080007FF`（控制区主份）与 Bootloader 自身固件所在的低地址区，
在 `ota_agent.c` / `bl_flash_if.c` 里都有硬编码判断：**任何擦写地址 `< OTA_SLOT_A_ADDR` 一律返回错误**，
且 `0x34` 只接受落在两个 APP 槽内的地址。`ota/common/ota_common.h` 另有编译期 `#error` 断言锁死两槽不得跨越 Bank 边界。

### 5.4 吞吐优化必须**三处一起改**（部署顺序，漏一处会直接失败）

`ISOTP_MAX_MSG` 是**编译进固件的常量**，上位机必须与设备一致：

| 顺序 | 动作 | 漏掉的后果 |
|---|---|---|
| 1 | 改 `Drivers/User/Inc/isotp.h`：`ISOTP_MAX_MSG 128 → 1024`，重编并烧录 **APP** | —— |
| 2 | 改 `Drivers/User/Src/uds.c`：`Uds_Service22()` 的 `resp[64]` → `resp[ISOTP_MAX_MSG]` | 大 DID 应答**越界写栈** |
| 3 | Bootloader 侧引用契约宏（`BL_ISOTP_MAX_MSG = OTA_ISOTP_MAX_MSG`），重编并烧录 **BL** | BL 收不下 1016 B 块 → 回 `FC=OVFLW` |
| 4 | 上位机用 1016 块大小（`ota_host.py` 默认已为 1016） | —— |

**降级共存规则**（重要）：上位机按设备 `0x34` 应答里通告的 `maxLen` 决定块大小。
若固件仍是旧版（`maxLen=125`），**新版上位机会自动按 125 分块**，因此"先升级工具、后升级固件"是安全的；
反之若固件已升到 1016 而工具仍写死 125，则**只是慢**，不会失败。真正会失败的是
**固件已支持 1016、工具却硬发 1016 而设备 `ISOTP_MAX_MSG` 仍是 128** —— 这只会发生在
"只改了上位机、没重编固件"的情况下，请务必按上表顺序部署。

`ota_common.h` 已加断言 `#if defined(ISOTP_MAX_MSG) && (ISOTP_MAX_MSG != OTA_ISOTP_MAX_MSG) #error`，
使"固件侧两处不一致"在编译期就暴露；跨代码库的数值一致性由 `ota/verify/verify_all.py` 静态守卫。

## 变更记录

### 2026-10-07 · 单块净荷 1021 → 1016（8 字节对齐）

**根因**：STM32G4 Flash 只支持 8 字节（双字）编程，因此设备侧 `BL_DiagRangeOk` 要求
断点续传的起始地址必须 8 字节对齐。而断点续传偏移 = `(N-1) × 块大小`，若块大小不是
8 的倍数，则 8 个连续续传起点里会有 7 个落在非对齐地址上，**全部被设备回 NRC 0x31 拒绝**。

| 旧块大小 1021（mod 8 = 5） | 偏移 | 偏移 % 8 | 结果 |
|---|---|---|---|
| `--resume 17` | 16336 | 0 | 通过 |
| `--resume 18` | 17357 | 5 | **NRC 0x31** |
| `--resume 19` | 18378 | 2 | **NRC 0x31** |
| `--resume 20` | 19399 | 7 | **NRC 0x31** |

**修法**：`UDS_DL_MAX_BLOCK_PAYLOAD` 由 `(OTA_ISOTP_MAX_MSG - 3U)` 改为
`((OTA_ISOTP_MAX_MSG - 3U) & ~7U)` = **1016**（推导式而非字面量，改报文上限会自动重新对齐）。

* 1016 + 2(SID + blockSeq) = 1018 ≤ 1024，ISO-TP 上限仍然满足；
* 吞吐损失 0.5%（满槽镜像 21 秒 → 21.1 秒）；
* 换来**任意续传起点都 8 对齐**，断点续传真正可用。

**必须同步的三处**（`verify_all.py` 的 C1/C4/C8 已改为按推导式守卫，跨库不一致会被拦住）：

| 位置 | 值 |
|---|---|
| `ota/common/ota_common.h` | `UDS_DL_MAX_BLOCK_PAYLOAD = ((OTA_ISOTP_MAX_MSG - 3U) & ~7U)` |
| `ota/tools/ota_host.py` | `ISOTP_DEFAULT_BLOCK_SIZE = (ISOTP_MAX_MSG - 3) & ~7` |
| 派生数值 | 满槽 **210 块**；单块 1 FF + 145 CF = **146 帧**；`0x34` 应答 `74 20 03 F8` |

### 2026-10-07 · 0x34 长度校验 10 → 11（血线 6）

Bootloader 侧 `BL_DiagService34` 曾把长度校验写成 `len != 10U`，而代码实际访问到
`req[10]`（请求体是 `34 00 44` + addr(4B) + size(4B) = **11 字节**），自相矛盾。
真机上 0x34 恒回 `7F 34 13`（NRC 0x13 IncorrectMessageLength），**一块固件都刷不进去**。

之所以长期未被发现：APP 侧与上位机都是 11，且单元测试全部跑在 `SimulatedEcu` 上
（模拟器也是 11），**原有的 29 项守卫与 111 条单测没有一项覆盖 UDS 请求长度**。

* 契约新增 `UDS_DL_REQ_LEN 11U`，BL / APP 双方一律引用该常量，禁止裸数字；
* `verify_all.py` 新增 **C10** 检查项（设备端 UDS 请求长度与三方一致性），
  并配 4 条反例（把 BL / APP 的校验改回裸数字、FF00 退回仅 6U、上位机重新单独发 FF00），
  确保该类回归能被自动拦住。

### 2026-10-07 · FF00 显式擦除例程降级为冗余

`31 01 FF 00` 的 size 字段只有 16 位（上限 65535），**小于单槽净荷 212928 字节**，
本就无法表达整槽擦除；而 `0x34` 的 `BL_DiagPrepareDownload` 已**隐式无条件擦除**目标槽。

* 设备侧改为**同时接受 4 字节（不带 size，擦整槽）与 6 字节（带 size）**，
  长度常量取自契约 `UDS_RID_ERASE_REQ_LEN_MIN/MAX`（此前硬性要求 6 字节，
  而上位机发的是 4 字节 → 整槽刷写在第一步就被中断）；
* 上位机**不再调用** FF00（`ota_host.py` 的刷写流程中已无 `routine_control(UDS_ROUTINE_ERASE)`），
  避免两次擦除吃掉超时预算（单次全槽擦除估算 2.6s vs 默认 timeout 3.0s，几乎无余量）。

### 2026-10-07 · FF02 激活返回码不再被忽略（B5，最危险的一条）

上位机曾丢弃 `31 01 FF 02` 的返回码直接置 `activated = True`。而设备在该例程失败时
（合成镜像头 / 回读校验 / `BL_ImageValidate` / 配置区落盘任一失败）会回 `status = 0x01`。
结果是**激活失败却打印刷写成功**，用户看到成功而设备仍运行旧固件 —— 静默失败。

* 现在解析 `status`，非 0 即抛错，并提示用 `22 F180` / `22 F182` / `22 F183` 进一步确认；
* 结果对象新增 `activate_status` 字段；
* 同一处顺带修正 `0x31 01 FF01` 的 **fail-open**：契约的
  `UDS_VERIFY_RESP_MIN_LEN` 由 4 改为 **5**（status 在第 5 字节，4 字节应答
  `[71,01,FF,01]` 根本不含 status，旧实现会把它当成"校验通过"从而跳过 CRC 校验）。

### 2026-10-07 · 断点续传块序号基线（B3）

契约规定 `seq = ((blockIndex - 1) % 255) + 1`，其中 `blockIndex` 是**绝对块号**。
设备侧曾在 `BL_DiagPrepareDownload` 中无条件 `s_dl.blockCount = 0U`，
导致 `--resume N` 时上位机按绝对块号发 `seq = N`、设备却期望 `seq = 1` → 必回 NRC 0x73。

* 现在按 `firstBlockIndex = (addr - appBase) / 块大小 + 1` 反推绝对块号；
* 结构体新增 `blockSize` / `firstBlockIndex` 字段，期望序号改为
  `UDS_BLOCK_SEQ_OF(s_dl.firstBlockIndex + s_dl.blockCount)`；
* 顺带修正模拟器：此前只有 FF00 路径才 `mem.clear()`，现在 0x34 路径也与固件一致地隐式擦除
  （这类"模拟器与固件分叉"正是 B1 长期未被测试发现的根因）。

## 第二梯队修复（2026-10-07 · H1~H4）

第一梯队（阻断级 B1~B5，见上）解决的是"真机OTA 必然失败"。第二梯队处理的是
**"代码看起来完全合理，只在真机特定时序下才失效"**的四项——它们的共同特点是
单元测试与原有 30 项守卫**全部测不到**，因此一并补了守卫（新增 C11）与反例。

### 2026-10-07 · 跳转前清系统异常挂起位（H1）

`bl_jump.c` 的 `BL_JumpToApp()` 原先只清 `NVIC->ICER/ICPR`。但 Cortex-M4 的
**系统异常**（SysTick / PendSV）挂起位**NVIC 清不到，只能走 `SCB->ICSR`**。
本工程 SysTick 每 1ms 挂起一次；改`VTOR` 之后若 SysTick 仍 pending，APP 入口后
会在其生效那一瞬按 **APP 自己的向量表**取向量，而此刻 APP 还没初始化完 →
**随机 HardFault / 偶发启动即死**。

这个缺陷最讨厌的地方是概率极低（只在跳转瞬间恰处 SysTick 窗口内，约千分之一），
现场表现为"昨天刷几十次都好好的，今天有一两次起不来"，常规复现几乎抓不到。

* 已补 `SCB->ICSR = SCB_ICSR_PENDSTCLR_Msk | SCB_ICSR_PENDSVCLR_Msk`（写 1 清除）；
* `__enable_irq()` 在 `entry()` 之前的顺序**保留不动**：只有复位才会被硬件清PRIMASK，
  带 `PRIMASK=1` 跳过去会让 APP 永远收不到中断，比窗口期误触发严重得多；
* 文档 `docs/02` 新增**血线 9**。

### 2026-10-07 · 控制区写目标选择的两条绕过路径（H2/H3）

`BL_PARAM_PRIMARY_WRITE = 0` 这个宏的**唯一目的**是"彻底不碰 PRIMARY 页"
（该页与 BL 向量表同页）。但 `BL_ParamSelectTarget()` 里有两条路径绕过它：

| 编号 | 缺陷 | 典型触发场景 |
|---|---|---|
| **H3** | "全部副本无效"回退路径**裸写** `OTA_CFG_PRIMARY_ADDR` | **全新芯片首次上电**（Flash 全 0xFF）——恰是该宏最需要生效的时刻 |
| **H2** | 同页分支 `*off` 恒为副本0。置 0 时所有有效副本都在 MIRROR 页，`oldestIdx == newestIdx` 恒成立 → **永远写副本0**，副本1 永不写 | 任何一次正常配置落盘 |

H2 的后果不是"少一份冗余"，而是**双副本机制名存实亡** —— 每次写都擦掉唯一幸存者。

* H3：回退路径改为 `#if` 条件编译分流，置 0 时只写 MIRROR 页；
* H2：同页分支按 `s_candOff[newestIdx]` 选**非最新**的那一份，形成真正 ping-pong：
  写 copy0 → STEP-3 恢复 copy1 → copy1 成为最新 → 下次写 copy1 → ……
  于是擦除窗口之外**恒有两份**有效配置，血线 1 才真正成立；
* 文件头"置 0 可彻底避免"的表述已按修复后的事实精确化；文档 `docs/02` 新增**血线 10**。
* ⚠️ 修复前若曾用 `=0` 编译并烧写过，**建议重新烧一次 BL**：旧固件在首次写配置时
  仍会擦 PRIMARY 页。

### 2026-10-07 · 上位机遵守FC 的 STmin（H4）

`_send_remaining()` 原先只读FC 的 BS（块大小），**完全忽略第 3 字节的 STmin**，
把 146 帧背靠背连发。对本工程这是致命的：BL 的 FDCAN RX FIFO0 只有 **3 深度**，
连续帧到达速率一旦超过 BL 的处理速率就溢出丢帧 → ISO-TP 重组超时 → "刷写到某一帧
卡住"，且随总线负载与中断延迟波动，**极难复现**。

* 新增 `isotp_stmin_to_seconds()`，按 ISO 15765-2 标准解码：
  `0x00..0x7F` = 0..127 ms，`0xF1..0xF9` = 100..900 µs；保留区间**不人为限速**
  （`BS` 才是决定丢帧风险的字段）；
* CF 之间实际延时；首个 CF 紧跟 FC 立即发（STmin 约束的是 CF **之间**的间隔），
  故 146 帧产生 145 个间隔；
* 延时器**可注入**（`sleep_fn`），生产用 `time.sleep`，单测注入假延时器
  （否则满槽测试要多花~60 s：210 块 × 146 帧 × 2 ms）；
* 新增 6 条单测（`test_stmin_*`），文档 `docs/03` §5.2 新增**血线 8**。

> 吞吐代价：满槽 210 块 × 145 间隔 × 2 ms ≈ **61 s**（此前"背靠背"实际发不出去，
> 只是被 FIFO 溢出吞掉了）。这是 ISO-TP 层面的固有上限，与块大小无关。

### 守卫补强

| 项 | 内容 |
|---|---|
| **C11**（新增） | BL->APP 交接与流控节拍：H1 清`SCB->ICSR` / H3 回退路径 `#if` 保护 / H2 同页副本轮转 / H4 读 STmin 且 `sleep_fn` 延时 + 解码函数存在 |

**教训**：这四项的共性是"**缺少某个必须存在的动作或字段**"，而不是"某个值写错了"。
常量一致性守卫天然抓不到这类问题 —— 必须显式断言"该动作存在"。
这与第一梯队 B1 的教训（长度一致性 ≠ 值一致性）是同一类盲区。
