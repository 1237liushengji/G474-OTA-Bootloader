# 03 · OTA 通信协议（复用既有 ISO-TP + UDS）

> 前置事实（全部来自仓库实际代码，逐条可核对）：
> * 传输层：`G474/Drivers/User/Src/isotp.c`，经典 CAN 8 字节帧，地址对 `0x7E0`（请求）/ `0x7E8`（应答），模块按 `rxId` 自过滤。
> * 应用层：`G474/Drivers/User/Src/uds.c`，已有 `0x10/0x22/0x2E/0x19/0x3E`，扩展点在 `Uds_ServerOnMsg()` 的 `switch`。
> * 接收缓冲：`ISOTP_MAX_MSG = 128` → **已优化为 1024**（`isotp.h`），**单条应用报文上限 1024 字节**，单块净荷 1016 字节。
> * FDCAN 过滤器是硬编码的（`can.c` `CAN_Configure()`）：正常模式 `StdFiltersNbr = 2`，FilterIndex0 = 业务 ID（`0x321`/`0x322`），FilterIndex1 = 诊断 ID（`0x7E0`/`0x7E8`）。
> * ISO-TP 接收方固定回 `FC(CTS, BS=0, STmin=2ms)`。

**结论：不新造私有协议。** OTA 直接落在既有 UDS 栈上，新增 `0x34/0x36/0x37/0x31/0x11` 五个服务与若干 DID。这样做的收益是：现有 `diag` 控制台命令、客户端超时逻辑、会话保活、上位机 `can_console.py` 的报文解析全部继续可用，且与"量产 ECU 标准刷写流程"完全一致。

---

## 1. 角色与链路

| 角色 | 物理 | 说明 |
|---|---|---|
| **诊断仪 / 上位机** | PC | 发出 UDS 请求。两种接入方式见 §6 |
| **目标节点（被升级方）** | 板 B | 运行 **APP**（正常态）或 **Bootloader**（recovery 态），二者共享同一 UDS 子集 |
| **转发/中继（可选）** | 板 A | 当上位机只能通过串口接入时，板 A 充当诊断仪并把请求转发到 CAN |

关键设计：**APP 与 Bootloader 暴露完全相同的服务集与字节级格式**。因此上位机不需要知道"现在跑的是 APP 还是 BL"，也不需要两套协议栈——这是把刷写入口放在 APP 内（而非只在 BL 里）的核心价值。

## 2. 诊断 ID 与过滤器改动

| 方向 | CAN ID | 说明 |
|---|---|---|
| 请求 | `0x7E0` | 诊断仪 → 目标节点 |
| 应答 | `0x7E8` | 目标节点 → 诊断仪 |
| 业务（保持不动） | `0x321` / `0x322` | 双机 LED 同步心跳，**OTA 全程不受影响** |

**必须改的一处（当前会挡住 OTA）**：`can.c` 里过滤器只按"角色"二选一，板 A 只收 `0x7E8`、板 B 只收 `0x7E0`。当板 A 要扮演诊断仪、同时板 B 又需要接收时都不成问题；但**两块板都可能需要收发两个诊断 ID**（例如单板自测、或板 A 既要当诊断仪又要被远程升级）。

推荐改法（保持原有业务过滤不变，只放开诊断侧）：

```c
/* can.c / CAN_Configure() 内，替换原 FilterIndex0/1 的 ID 赋值逻辑 */
/* 业务帧过滤：仍然只看本节点关心的那一个业务 ID */
filterConfig.FilterIndex = 0U;
filterConfig.FilterID1   = (CAN_NODE_ROLE == CAN_NODE_A) ? CAN_ID_RESP_B2A : CAN_ID_CMD_A2B;
filterConfig.FilterID2   = 0x7FFU;
/* 诊断过滤：两个诊断 ID 都收（收发复用同一 ISO-TP 通道，由 isotp 层判 ID） */
filterConfig.FilterIndex = 1U;
filterConfig.FilterID1   = ISOTP_DIAG_REQ_ID;    /* 0x7E0 */
filterConfig.FilterID2   = 0x7FFU;               /* 见下方说明：只用一条掩码过滤器无法覆盖两个ID */
```

> ⚠️ **硬件限制**：一条掩码型过滤器只能匹配"一个 ID + 一个掩码"，`FilterID2` 是掩码不是第二个 ID。要同时收 `0x7E0` 与 `0x7E8`，必须**增加一条过滤器**（把 `StdFiltersNbr` 从 2 改为 3，FilterIndex2 配 `0x7E8`），或用 `FDCAN_FILTER_RANGE` 型（`0x7E0~0x7E8`，但会连带收到 `0x7E1~0x7E7`，由 `isotp.c` 的 ID 判断兜底丢弃，代价可接受且更省过滤器）。
>
> 推荐 `FDCAN_FILTER_RANGE` 方案：`StdFiltersNbr = 3`，FilterIndex2 = `{FilterType=RANGE, FilterID1=0x7E0, FilterID2=0x7E8}`。**这是"双 CAN/双诊断 ID 共存"必须动的最小改动**，也是原工程 README 中"双 CAN"扩展方向的自然延伸。

## 3. 服务与例程总表

| SID | 服务 | 请求 | 正响应 | 会话要求 |
|---|---|---|---|---|
| `0x10` | DiagnosticSessionControl | `10 03` | `50 03 00 32 01 F4` | — |
| `0x11` | ECUReset | `11 01` | `51 01` | 扩展 |
| `0x22` | ReadDataByIdentifier | `22 F1 8x` | `62 F1 8x <data>` | — |
| `0x2E` | WriteDataByIdentifier | `2E F1 90 01` | `6E F1 90` | 扩展 |
| `0x31` | RoutineControl | `31 01 <RID>` | `71 01 <RID> <result>` | 扩展 |
| `0x34` | RequestDownload | `34 00 44 <addr4> <size4>` | `74 20 <maxLen2>` | 扩展 |
| `0x36` | TransferData | `36 <seq> <data...>` | `76 <seq>` | 扩展 |
| `0x37` | RequestTransferExit | `37` | `77` | 扩展 |

### 3.1 新增 DID

| DID | 长度 | 含义 |
|---|---|---|
| `F180` | 1 | OTA 状态：`00`=IDLE_A、`01`=IDLE_B、`02`=TRIAL_A、`03`=TRIAL_B |
| `F181` | 1 | 当前活动槽：`00`=A、`01`=B |
| `F182` | 4 | 版本：A 槽 major/minor + B 槽 major/minor |
| `F183` | 8 | A 槽 CRC32（4B 大端）+ B 槽 CRC32 |
| `F184` | 1 | 能力位图：bit0 支持 0x34/36/37、bit1 支持 0x31 例程、bit2 双槽 A/B。**固定 0x07** |
| `F190` | 1（写） | 写 `01` = 置"下次复位进入 Bootloader"请求标志 |

`F180~F184` 使上位机可以在刷写前**预检**当前状态（是否需要先进 BL、目标槽是哪个、旧版本是什么），这就是 `ota_host.py --precheck` 的实现依据。

### 3.2 RoutineControl 例程

| RID | 名称 | 请求附加数据 | 结果字节 | 语义 |
|---|---|---|---|---|
| `FF00` | Erase | 可选 2B 大端总长度 | `00` 成功 / `01` 失败 | **冗余路径**：`0x34` 已隐式擦除。请求体 4B（不带 size，擦整槽）或 6B（带 size，上限 65535 < 单槽 212928，故无法表达整槽）。上位机不再调用 |
| `FF01` | Verify | 无 | `00` 成功 / `01` CRC 不符 / `02` 长度不符 | 按 CRC32 校验已接收数据 |
| `FF02` | Activate | 无 | `00` 成功 / `01` 失败 | 写配置为 `TRIAL_<目标槽>`，允许随后 `11 01` 复位 |
| `FF03` | Rollback | 无 | `00` 成功 / `01` 失败 | 显式切回另一槽 |
| `FF04` | Commit | 无 | `00` 成功 | **仅 APP 实现**：试运行自检通过后落定，`TRIAL_x → IDLE_x` |

## 4. 完整刷写时序（字节级）

以"当前运行 Slot A，升级到 Slot B"为例：

```
上位机                                            目标节点(APP → BL)
  │                                                    │
  │─ 10 03 ───────────────────────────────────────────►│ 进入扩展会话
  │◄─ 50 03 00 32 01 F4 ───────────────────────────────│ S3 计时开始(5s)
  │─ 22 F1 84 ────────────────────────────────────────►│ 预检能力位图
  │◄─ 62 F1 84 07 ─────────────────────────────────────│
  │─ 22 F1 81 ────────────────────────────────────────►│ 查当前活动槽
  │◄─ 62 F1 81 00 ─────────────────────────────────────│ 00 = 运行在 A
  │─ 22 F1 82 ────────────────────────────────────────►│ 查旧版本
  │◄─ 62 F1 82 03 00 00 00 ────────────────────────────│ A=3.0 B=无
  │                                                    │
  │  ══ 阶段1：准备（目标槽自动判定为 B）══              │
  │─ 34 00 44 <Slot B 的 APP 基址> <净固件长度> ────────►│ addr=槽基址+0x80，size=payloadSize
  │◄─ 74 20 03 F8 ─────────────────────────────────────│ maxLen = 1016 字节/块（0x03F8）
  │                                                    │  ★ 0x34 隐式擦除 addr 起的页区间
  │                                                    │    （FF00 显式擦除已废弃，见 §3 注）
  │                                                    │
  │  ══ 阶段2：数据传输（块序号 1..255 循环）══           │
  │─ 36 01 <1016B> ───────────────────────────────────►│ 累积进 2KB 页缓冲
  │◄─ 76 01 ───────────────────────────────────────────│
  │─ 36 02 <1016B> ───────────────────────────────────►│
  │◄─ 76 02 ───────────────────────────────────────────│
  │   ... 每 2 块触发一次 Flash 页编程 ...               │
  │─ 36 E1 <剩余字节> ────────────────────────────────►│ 第 226 块（<255，本次不回绕）
  │─ 36 01 <剩余字节> ────────────────────────────────►│ 序号回绕到 1
  │◄─ 76 01 ───────────────────────────────────────────│
  │                                                    │
  │  ══ 阶段3：收尾与校验 ══                            │
  │─ 37 <整镜像CRC32(4B 大端)> ───────────────────────►│ 残余字节 0xFF 补齐后落盘
  │◄─ 77 00 ───────────────────────────────────────────│
  │─ 31 01 FF 01 ─────────────────────────────────────►│ CRC32 校验
  │◄─ 71 01 FF 01 00 <设备实算CRC32> ──────────────────│ 00 = 校验通过（9 字节）
  │                                                    │
  │  ══ 阶段4：激活与复位 ══                            │
  │─ 31 01 FF 02 ─────────────────────────────────────►│ 置 TRIAL_B / trialLeft=3
  │◄─ 71 01 FF 02 00 ──────────────────────────────────│
  │   （若隧道模式：此处关闭隧道，等待应答发完）            │
  │─ 11 01 ───────────────────────────────────────────►│ 应答后 50ms 软复位
  │◄─ 51 01 ───────────────────────────────────────────│
  │                                                    │ ↓ 复位
  │                                         Bootloader 启动：state=TRIAL_B
  │                                         trialLeft 3→2，校验 Slot B → 跳转 APP_B
```

### 4.1 关键字段约定

* **`0x34` 的 `addr`**：**目标槽的 APP 链接基址** = 槽基址 + 32B 镜像头（Slot A → `0x0800C080`，Slot B → `0x08040880`）。
  * **契约要点（已冻结）**：传输流**只含净固件**，槽首 32B 镜像头**由设备在 FF02 激活时自己合成**。上位机不要把镜像头塞进 `0x34/0x36` 流里。
    * 为什么：`0x34` 的 `addr` 语义就是"APP 链接基址"，若还把头放进流，就出现了"写入起点"与"链接基址"两套偏移，需要设备额外区分两种写模式，收益为零（头只有 32B，设备合成更可靠）。
    * 设备合成内容：`magic`、`imgSize = 32 + total`、`payloadSize = total`、`loadAddr = 槽 APP 基址`、`payloadCrc = 0x37 携带值（缺省用本次累计 CRC）`、`hdrCrc`、`version`（缺省 0）。合成后必须回读校验，失败则 FF02 返回结果码 `01`。
  * 设备用它反推目标槽；若 `addr` 落在**活动槽**内 → NRC `0x22`（不许写正在运行的固件）；落在两槽之外或 `< OTA_SLOT_A_ADDR` → NRC `0x31`。
  * **断点续传**：`addr` 允许落在目标槽内任意位置（= 槽 APP 基址 + N·blockSize），此时 `size` = 剩余长度，擦除范围自 `addr` 起向上取整到页，因此不会重擦已写页。
* **`0x34` 的 `size`**：本次要写的净固件字节数（全量时 = 镜像头 `payloadSize`），受 `OTA_IMG_MAX_PAYLOAD`（`208KB − 32B`）约束。
* **`0x37` 携带 4 字节整镜像 CRC32**（大端）：`[37, crc32×4]`，长度 5。它同时充当 ① FF01 的参考值 ② 合成镜像头里的 `payloadCrc`。**不携带也能跑**，但 FF01 就只能按长度校验、合成头的 CRC 字段为 0，设备会打告警。
* **`0x31 01 FF01` 的 CRC 来源**：设备对**本轮实际接收的字节流**重算 CRC32，与 `0x37` 携带值（若有）比对；未携带时与镜像头登记值比对（仅全量下载成立）。两侧必须都是标准 CRC-32/ISO-HDLC（初值 `0xFFFFFFFF`、结果异或 `0xFFFFFFFF`、反射多项式 `0xEDB88320`），自检向量 `CRC32("123456789") == 0xCBF43926`。
  * **应答格式（已冻结，9 字节）**：`71 01 FF 01 <status> <crc32 4B 大端>`；`status`：`00` 通过 / `01` CRC 不符 / `02` 长度不符。设备若只回 4 字节（仅 `status`）也视为合法，上位机两种都要能解析。
  * 续传语义：**上位机按哪个范围算，设备就按那个范围算** —— 续传时上位机比对"剩余区段"的 CRC，因此 `0x37` 应携带该剩余区段的 CRC（而不是整镜像 CRC）。
* **`0x36` 的 `seq`**：取值 `1..255`，**`255` 之后回绕到 `1`（不是 `0`）**，`0` 永远非法（回 NRC `0x73` wrongBlockSequenceCounter）。设备与上位机必须用同一公式：`seq = ((blockIndex - 1) % 255) + 1`（`ota_common.h` 的 `UDS_BLOCK_SEQ_OF` 宏即此式）；断点续传 `--resume N` 的首块序号也按此式计算。
  * 序号不符时设备回 NRC `0x73`，**标准帧里不带"期望序号"**，上位机应按自己算出的序号**重发该块**（设备不会前进期望值，因此重发必然能对上）。
* **`0x36` 的净荷上限**：由 `0x34` 应答的 `maxLen` 给出。本方案 `maxLen = 1016`，推导见 §5.1。

## 5. 容量、时序与吞吐量核算（**必读，这是本方案最大的现实约束**）

### 5.1 单块净荷为什么是 1016 字节（已做吞吐优化 + 8 字节对齐）

```
ISO-TP 应用报文总长 = UDS 报文长 ≤ ISOTP_MAX_MSG = 1024
UDS 0x36 报文 = 1(SID) + 1(blockSeq) + N(data)
=> N ≤ 1024 − 2 = 1022
再向下对齐到 8 的倍数（Flash 双字编程要求，见下方"为什么必须 8 对齐"）
=> N = (1022) & ~7 = 1016
```

**为什么必须 8 字节对齐（血线 5，2026-10-07 修正）**：
STM32G4 Flash 只支持 8 字节（双字）编程，设备侧 `BL_DiagRangeOk` 因此要求
**断点续传的起始地址必须 8 字节对齐**。而续传偏移 = `(N-1) × 块大小`，
若块大小不是 8 的倍数（如旧值 1021，mod 8 = 5），则 8 个连续续传起点里
**有 7 个落在非对齐地址上，全部被设备回 NRC 0x31 拒绝**：

| `--resume N` | 偏移 = (N-1)×1021 | 偏移 % 8 | 结果 |
|---|---|---|---|
| 17 | 16336 | 0 | 通过 |
| 18 | 17357 | 5 | **NRC 0x31** |
| 19 | 18378 | 2 | **NRC 0x31** |
| 20 | 19399 | 7 | **NRC 0x31** |

改为 1016（8 的倍数）后，**任意续传起点都合法**。吞吐代价仅 0.5%
（满槽镜像 21 秒 → 21.1 秒），而 1016 + 2(SID+blockSeq) = 1018 ≤ 1024 仍满足 ISO-TP 上限。

**这是一个已落地的优化**：原工程 `isotp.h` 的 `ISOTP_MAX_MSG` 是 **128**，当时单块净荷只能到 125 字节。
把它提到 **1024** 后：

| 项 | 优化前（128） | 优化后（1024） | 变化 |
|---|---|---|---|
| 单块净荷 | 125 B | **1016 B** | ×8.1 |
| 满槽镜像的 `0x36` 报文数 | 1 835 | **210** | ÷8.7 |
| 收发缓冲 RAM（`isotp.c` 两个数组） | 2 × 128 B | 2 × 1 KB | **+1.75 KB** |
| 设备侧处理开销 | 8.1 倍报文解析/应答 | 基准 | 大幅下降 |

**代价只有约 1.8 KB RAM**（本机 128 KB，实际使用仅 10~20 KB）。

**必须同步的三处**（否则会出现"上位机按 1016 发、设备只收 128"的**静默溢流失败**）：

| 位置 | 改动 | 说明 |
|---|---|---|
| `Drivers/User/Inc/isotp.h` | `ISOTP_MAX_MSG 128 → 1024` | 收发缓冲随之一并放大（`isotp.c` 里是 `uint8_t [ISOTP_MAX_MSG]`） |
| `Drivers/User/Src/uds.c` | `Uds_Service22()` 的 `uint8_t resp[64]` → `uint8_t resp[ISOTP_MAX_MSG]` | **不改就会静默截断多字节 DID 应答**（`ISOTP_MAX_MSG` 变大后没有代码会越过它，但一旦有超过 64 字节的 DID，`rlen` 就会越界写栈） |
| `ota/common/ota_common.h` | `UDS_DL_MAX_BLOCK_PAYLOAD` / `UDS_MAXLEN_FIELD` 改为由 `OTA_ISOTP_MAX_MSG` 推导 | 已落地；并加断言：与 `isotp.h` 的 `ISOTP_MAX_MSG` 不一致就直接编译报错 |

> 契约头里现在是这样定义的，**三方（BL/APP/上位机）一律引用它，不要再写 128/125/1021 字面量**：
> ```c
> #define OTA_ISOTP_MAX_MSG         1024U
> #define UDS_DL_MAX_BLOCK_PAYLOAD  ((OTA_ISOTP_MAX_MSG - 3U) & ~7U)   /* = 1016，8 字节倍数 */
> #define UDS_MAXLEN_FIELD          UDS_DL_MAX_BLOCK_PAYLOAD
> #if defined(ISOTP_MAX_MSG) && (ISOTP_MAX_MSG != OTA_ISOTP_MAX_MSG)
> #error "ota_common.h 的 OTA_ISOTP_MAX_MSG 与应用层 isotp.h 的 ISOTP_MAX_MSG 不一致"
> #endif
> #if ((UDS_DL_MAX_BLOCK_PAYLOAD % 8U) != 0U)
> #error "UDS_DL_MAX_BLOCK_PAYLOAD 必须是 8 字节倍数：Flash 双字编程要求续传地址 8 对齐..."
> #endif
> ```

### 5.2 ISO-TP 层时间

> ⚠️ **血线 8：STmin 必须被遵守（2026-10-07 修复，H4）**
>
> 本节所有时间估算的前提是"发送方确实按 FC 的 STmin 限速"。修复前的上位机
> **只读了 FC 的 BS（块大小），完全忽略了第3 字节的 STmin**，把 146 帧背靠背连发。
> 对本工程这是致命的：BL 的 FDCAN RX FIFO0 只有 **3 深度**，一旦连续帧到达速率
> 超过 BL 的处理速率，FIFO 溢出 → 丢帧 → ISO-TP 重组超时，表现为"刷写到某一帧
> 卡住"，且随 CAN 总线负载与中断延迟波动，**极难复现**。
>
> 现状：`ota_host.py` 的 `_send_remaining()` 按 ISO 15765-2 标准解码 STmin
> （`0x00..0x7F` = 0..127 ms；`0xF1..0xF9` = 100..900 µs），并在 CF 之间实际延时；
> 保留区间不人为限速（`BS` 才是决定丢帧风险的字段）。首个 CF 紧跟 FC 立即发出
> （STmin 约束的是 CF **之间**的间隔），因此 146 帧产生 145 个间隔。
>
> 下表中的 "2 ms" 现在是**强制值**而非期望值。若将来有人为提速改掉这段延时逻辑，
> `verify_all.py` 的 C11 检查项会 FAIL。

发送方（本工程接收方固定要求 `STmin = 2 ms`）：

| 项 | 计算 |
|---|---|
| 每个 CAN 帧 | 8 字节数据 + 约 47 位开销 ≈ 111 位 → 500 kbit/s 下 **≈ 222 µs** |
| 连续帧间隔 | 受 STmin 限制 = **2 ms**（远大于总线传输时间，**STmin 是瓶颈**） |
| 每个 CF 有效载荷 | 7 字节 |
| **ISO-TP 有效吞吐** | 7 B / 2 ms = **≈ 3.5 KB/s**（与块大小无关） |

> 注意：块大小只减少**报文条数与设备侧开销**，不改变 ISO-TP 层的 3.5 KB/s 上限——
> 该上限由 `STmin` 决定。所以优化收益体现在"少 8 倍的 `0x36`/`0x76` 往返与页缓冲拷贝"，
> 而不是把总线速率提上去。
>
> 另一个容易踩的坑：桥节点隧道模式下每帧还要打印一行 RXTX（约 26~30 字符
> @115200 ≈ 2.3 ms），接收侧靠 `CAN_RX_RING_LEN = 16` 的环形缓冲撑着。
> 隧道模式请用 `--block-size 500` 起步（见 `TUNNEL_SUGGESTED_BLOCK_SIZE`），
> 再用 `22 F002` 查 `rxOverruns` 判断是否丢帧。

### 5.3 端到端时间（满槽 208 KB 镜像、每块 **1016 B**）

镜像净荷上限 = 208 KB − 0x80 B(槽首保留区) = **212 928 B**（`OTA_IMG_MAX_PAYLOAD`）。

| 项 | 计算 | 结果 |
|---|---|---|
| 块数 | 212 928 B ÷ 1016 B | **210 块**（210 < 255，**本次不触发 seq 回绕**） |
| 每块请求报文分帧 | 1018 B → 1 FF + 145 CF | **146 帧** |
| 每块应答报文分帧 | 2 B → 1 SF | 1 帧 |
| ISO-TP 每块耗时 | 147 帧 × 2 ms | **≈ 294 ms** |
| **纯传输时间** | 210 × 294 ms | **≈ 6.2 s** |
| Flash 编程 | 104 页 × (擦除 ~25 ms + 编程 ~1 ms) | ≈ **2.6 s** |
| CRC32 校验（软件，150 MHz） | 212 KB × 8 周期/字节 ÷ 150 MHz | ≈ **12 ms** |

**合计 ≈ 9 秒**（优化前为 **≈ 76 秒**，提升约 **8.4 倍**）。

> ⚠️ 擦除耗时估算按 25 ms/页 是**乐观**的。`bl_flash_if.c` 自己的注释写"20~40ms"，
> 若真机落到 30~40 ms，单次全槽擦除就会超出上位机默认 timeout 3.0 s。
> 刷写前请用 `--info` 或先做一次小镜像试刷确认实际擦除耗时，必要时显式调大 `--timeout`。

> **单条报文的超时余量验证**：设备侧 `N_Bs/N_Cr` 超时与上位机应答超时都是 1 s / 3 s，
> 而单条 1018 B 报文只需 ≈294 ms，余量 **3 倍以上**，因此放大块大小**不会**引入超时风险。
>
> ⚠️ **但有一处操作超时要比 3 s 更宽裕，现场容易误判为"固件卡死"**：
> * **`0x34` 的全槽擦除**（`0x34` 隐式触发，FF00 已废弃）：目标槽 208 KB = 104 页 × ≈25 ms ≈ **2.6 s**，
>   而设备在 `0x10 03` 应答里声明的 `P2* = 5000 ms`（5 s）。两者都贴近上位机默认的 `--timeout 3.0`，
>   因此**全槽刷写建议显式 `--timeout 6.0`**，否则会在擦除尚未完成时误报超时。
>   注意 25 ms/页 是乐观估计，`bl_flash_if.c` 注释写的是 20~40 ms，真机可能直接超时。
> * **`0x11` 复位后的会话重建**：BL 启动窗口约 1 s，之后才可能应答 `10 03`；
>   上位机已用 `--session-retry`（默认 3 s，100 ms 间隔重试）覆盖这一点。
>
> **新增的监控点**：一条 1018 B 报文会产生 145 个连续帧，远多于 `can.c` 的 16 深度 RX 环形缓冲。
> 之所以安全，是因为 `isotp.c` 采用"**每个主循环周期只发一个 CF**"（`IsoTp_Task()` 的 `TX_SENDING`
> 状态）——主循环一圈 ≪ 2 ms，缓冲几乎总是空的。但**若主循环被长时间阻塞**（例如新增了阻塞式
> 打印或 `HAL_Delay`），就会静默丢帧。因此升级后**必须读 `22 F002` 确认 `rxOverruns == 0`**。

### 5.4 串口隧道模式的**新瓶颈**（优化后最需要注意的一点）

若上位机走"板 A 串口隧道"（§6 方式二），数据要经过 `115200 8N1` 的 ASCII 十六进制编码：

| 项 | 优化前（125 B/块） | 优化后（1016 B/块） |
|---|---|---|
| 每块的命令行长度 | 19 帧 × ≈26 字符 ≈ 500 字符 ≈ 43 ms | 147 帧 × ≈26 字符 ≈ 3800 字符 ≈ **330 ms** |
| 串口侧总耗时（229 KB） | ≈ 64 s | **≈ 74 s** |
| CAN 侧耗时 | ≈ 73 s | ≈ 6 s |
| **合计** | **≈ 2~3 分钟** | **≈ 74 s（瓶颈完全转移到串口）** |

**结论（很重要）**：

* 走串口隧道时，**吞吐优化把瓶颈从 CAN 转移到了串口**：CAN 侧从 73 s 降到 6 s，但串口侧仍是 ~74 s。
  总时间由 ~2.5 分钟降到 ~74 秒，**仍然有 2 倍收益**，但远不到 8 倍。
* 隧道模式下 147 帧 CF 以 2 ms 间隔涌入，而打印一行需 ≈2.3 ms → **打印速度已追不上接收速度**，
  建议隧道模式**显式调小块**（例如 `--block-size 500`），让每块帧数降到主循环能从容排空的水平；
  并监控 `rxOverruns`。
* **要拿到完整的 8 倍收益，必须用 §6 方式一（PC 直连 USB-CAN 适配器）**，此时串口只用于日志。
* 进一步优化隧道：把 `tx`/`RXTX` 命令**二进制化**（省掉约 4 倍 ASCII 编码开销），可把串口侧也拉进 20 秒量级。
* 无论哪种方式，**升级期间必须保证 CAN 上只有诊断流量**，否则 `CAN_PollRx` 的 16 深度环形缓冲会溢出（`rxOverruns` 计数会暴露这一点）。

## 6. 上位机接入方式

### 方式一（推荐）：PC 直连 USB-CAN 适配器

PC 侧用 `python-can`（PCAN/周立功/Kvaser/`canable` 等）直接收发 `0x7E0/0x7E8`，目标节点只跑 APP/BL 固件，**无需任何固件改动**。这是量产刷写的标准做法，也是 AN4767 描述的同构流程。

### 方式二：串口隧道（复用现有 `can_console.py` 的链路）

当手头只有串口、没有 USB-CAN 适配器时，让**板 A 当诊断仪中继**：

1. 在 `console.c` 的命令表新增三条命令（**这是 APP 侧必须新增的代码**，签名与既有命令一致）：

   | 命令 | 作用 | 回显 |
   |---|---|---|
   | `tun on` / `tun off` | 开启/关闭隧道模式 | `tunnel: on` / `tunnel: off` |
   | `tx <id3hex> <n> <2n个hex>` | 直接把一帧原始 CAN 帧发到总线 | `TXOK` / `TXERR` |

2. 隧道开启期间，主循环把收到的**诊断 ID** 帧按既有格式打印（复用 `Console_PrintFrame` 的输出格式，前缀改为 `RXTX` 以便与业务帧 `RX` 区分）：

   ```
   RXTX 7E8 8 03 7F 34 31 00 00 00 00
   ```

3. 于是 PC 只需按行"发一帧 / 收一行"，在 `ota_host.py` 里自建 ISO-TP 与 UDS 客户端即可完成刷写，**完全不用碰板 B 的固件**。

> **隧道模式的三个硬性约束**：
> 1. `tun on` 后节点自身的 UDS 客户端（板 A 的 `Uds_ClientOnMsg`）会与隧道争抢 ISO-TP 单通道，因此**隧道期间不要用 `diag` 命令**；
> 2. ISO-TP 是单事务半双工：上位机必须严格"一问一答"，收到上一应答后才能发下一请求，否则 `ISOTP_BUSY`；
> 3. ASCII 隧道吞吐见 §5.4，必要时把命令改造成二进制（如 `W` + 原始字节 + 长度校验），可省掉约 4 倍编码开销。

## 9. 安全（必含的完整性机制）

本方案**不含"裸传"**，完整性由三层构成：

1. **传输层逐块确认**：每个 `0x36` 都必须收到 `0x76 <seq>` 才继续；序号错序立即报 `0x73`。CAN 硬件层另有 FDCAN 自动重发（`AutoRetransmission = ENABLE`）与 CRC15 校验。
2. **报文级 CRC32**：镜像头 `payloadCrc` + 设备对实际写入内容重算 CRC32 比对（`31 01 FF01`）。这是防"总线噪声导致写入错误数据"的关键一层，也是唯一位于 CAN CRC 之外的端到端校验。
3. **跳转前双重结构校验**：BL 在跳转前独立校验栈顶指针（必须在 `0x20000000~0x2001FFFF` 且 8 字节对齐）与复位向量（bit0=1 且落在槽内）。这能挡住"CRC 正确但向量表被破坏"的极端场景。

> **进一步加固（可选，第二步）**：加 `0x27 SecurityAccess` 种子/密钥（既有 `uds.c` 已用"扩展会话"演示同一安全语义），或对镜像头 `reserved` 字段启用 HMAC-SHA256 截断签名，防止非法固件写入。当前工程无 `0x27`，本方案不擅自引入，只预留 `OTA_IMG_OFF_RESERVED`。
