# APP 启动重启循环 — 诊断报告

> 日期：2026-10-10
> 结论级别：**已定位到函数级**（待刷入诊断固件收窄到语句级）
> 影响：**这是本项目的头号阻塞缺陷** —— 它导致串口命令行、OTA 全链路均不可用

---

## 一、核心结论

**APP 从来没有进入过主循环。** 它在启动过程中卡死，随后被独立看门狗（IWDG）
每 **约 3.2 秒**复位一次，如此无限循环。

这直接解释了此前的全部"怪现象"：

| 此前的表象 | 真实原因 |
|---|---|
| 串口发命令零响应、连 `unknown cmd` 回显都没有 | 主循环未运行 → `Console_Task()` 从未执行 → 无人消费接收环形缓冲 |
| `ota_host.py --precheck` 卡在第一步 `TUN ON` 超时 | 隧道命令依赖 `Console_Task()`，同上 |
| XCOM 里"能看到输出但发命令无反应" | 看到的输出全部来自**启动早期**（横幅），之后板子就卡住并复位 |
| 反复排查串口接线/波特率/大小写/占用均无解 | **方向本身就错了** —— 问题不在串口链路 |

---

## 二、证据链（三条独立证据）

### 证据 1：复位周期 = IWDG 超时

抓包脚本**只命令了 1 次**复位（`--reset`），但 BL + APP 启动序列出现了**两次**：

```
[19:50:08.442] --- reset 1/1 ---                          ← 脚本唯一一次复位
[19:50:09.216] BL: jump to APP slot 0 base=0x0800C080     ← 第 1 次启动
[19:50:09.422] === STM32G474 CAN Node v3.0.0 | role:A ===
[19:50:09.422] > main: led-bsrr-state M3                  ← 输出终止
[19:50:12.574] BL: clock HSE+PLL 150MHz OK                ← 板子自复位（+3.16s）
[19:50:13.739] BL: jump to APP ...                        ← 第 2 次启动
```

`firmware` 的 IWDG 配置为 `LSI/32 = 1kHz，Reload 3000` → **标称 3s**
（LSI 有偏差，实测 3.1~3.4s 属正常范围）。

### 证据 2：喂狗时间轴对不上

`App_EarlyDelay(nops)` 每 20 万 NOP 喂一次狗（纯忙等，**不依赖 SysTick**），
所以启动早期的 LED 闪灯阶段一直在喂狗，能撑到横幅打印完。

横幅之后到 LCD 初始化块（下一个喂狗点）之间，**没有任何喂狗动作**：

```
横幅 + "M3" 打印  →  [CAN_Init]  [CAN_SelfTest]  [Uds_Init]  [Ota_Init]  →  LCD 块首次喂狗
                    └──────────── 这一段内无喂狗 → 3s 后必然复位 ────────────┘
```

### 证据 3：卡点被无条件打印"夹住"

这段区间内有两个函数**都有无条件打印**：

- `CAN_SelfTest()` → 打印 `CAN self-test: PASS` 或 `FAIL`（二选一，必打）
- `Ota_Init()` → 打印 `ota: TRIAL boot ...` 或 `ota: slot N state M`（必打）

**串口里这两条一条都没有出现** → 卡点在它们之前，即
**`CAN_Init()`（含 `CAN_Configure()`）或 `CAN_SelfTest()` 之内**。

### 附带证据：这是长期缺陷，非近期引入

`logs/serial_20261005_172218.log`（10-05 旧固件）呈现完全相同的形态：
横幅打印后 +3.16s 出现 BL 输出。**说明该缺陷自 10-05 起就存在。**

## 三、已逐条排除的项（避免重复排查）

| 检查项 | 结论 |
|---|---|
| `USART1_IRQHandler` 接线 | 正确，与 `bsp_uart.c` 共用同一 `huart1`（`extern` 于 bsp_uart.h） |
| 引脚定义 | PA9=TX / PA10=RX，均 AF7 ✓；全项目无第二处使用 | 
| `HAL_UART_MspInit` 覆盖 | 不存在（无 CubeMX 生成版本与之竞争） |
| `SysTick_Handler` | 存在且调用 `HAL_IncTick()` ✓；无自定义 `HAL_InitTick`/`HAL_GetTick` |
| `TICK_INT_PRIORITY` | 15（合法，< 16） |
| FDCAN 时钟分支 | `RCC_FDCANCLKSOURCE_PCLK1` 不会返回 `HAL_ERROR` |
| `CAN_Send()` | 只查 TX FIFO 满即返回，无死循环 |
| `CAN_Configure()` 用户代码 | 无"无超时"等待循环 |
| `CAN_DEBUG_SELFTEST` | = 0（外部回环调试模式未被误开） |

## 四、待验证的两种机理

| 假设 | 机理 | 佐证 |
|---|---|---|
| **A. HardFault** | `HardFault_Handler` 原本是**静默 `while(1)`**，故障现场只剩"3 秒后被复位" | 该 handler 确实无任何输出（见 `stm32g4xx_it.c` 原实现） |
| **B. tick 冻结** | `HAL_GetTick()` 不推进 → HAL 内所有 `while ((HAL_GetTick()-start) > TIMEOUT)` 变成**死循环**（FDCAN HAL 的 `FDCAN_TIMEOUT_VALUE = 10ms` 即此类） | 需实测确认 |

> 注：`App_EarlyDelay` 不依赖 tick，所以"横幅能打印"**不能**证明 tick 正常。

## 五、已就位的诊断手段

固件已改造并编译通过（**0 Error 0 Warning**，已打包为
`firmware/G474_A_factory.hex`，**尚未刷入**）：

1. **启动打点 A~H**（`BSP_UART_BootMark`）—— 每条附当前 `HAL_GetTick()` 十六进制值，
   卡点会被"夹"在两个相邻打点之间
2. **tick 活性检查** —— 40ms 忙等前后各取一次 tick，`delta > 0` 即 SysTick 正常
3. **`Error_Handler()` 自报** —— 打印 `!! ERROR_HANDLER !!`
4. **`HardFault_Handler()` 自报** —— 打印 `CFSR / HFSR / MMFAR / BFAR / PC / MSP / PSP`，
   判读方式已写进代码注释（DACCVIOL / PRECISERR / VECTTBL 等）

应急输出全部**直接写 USART1 寄存器**（不经 HAL、不依赖中断），并先检查 `CR1.UE|TE`
以免在启动早期死等 TXE。

## 六、下一步

硬件当前已断开（串口 0 个、ST-Link 0 个）。接回后执行：

```bash
# 1) 刷入诊断固件（板1 = ST-Link SN=8）
python ota/scripts/flash.py --file firmware/G474_A_factory.hex --sn 8 --yes

# 2) 抓启动输出（板1 = COM7）
python ota/scripts/serial_capture.py --port COM7 --seconds 20 --reset
```

**判读**：
- 停在 `[boot] B: before CAN_Init` 之后 → 卡在 `CAN_Init()`
- 停在 `[boot] D: before CAN_SelfTest` 之后 → 卡在 `CAN_SelfTest()`
- 出现 `!! HARDFAULT !!` → 按 CFSR/BFAR 判断故障类型
- 出现 `!! ERROR_HANDLER !!` → 某 HAL 调用返回错误被当致命错误处理
- `delta > 0` 正常 / `delta = 0` → 印证假设 B（tick 冻结）
