# 04 · A/B 双槽与回滚机制、参数区读写

> 前置：分区表见 [01 · 分区规划与链接配置](01-分区规划与链接配置.md)，协议见 [03 · OTA 通信协议](03-OTA协议与刷写时序.md)。
> 本文回答三个必须明确的问题：**状态存在哪、什么时候切、失败怎么退。**

---

## 1. 控制区（参数区）落在哪、为什么

| 副本 | 地址 | 何时被擦 | 保护理由 |
|---|---|---|---|
| 主份 | `0x08000000`（2 KB 页） | **永不被擦** | 它是 Flash 第一页，位于 Bootloader 区；BL 固件与 APP 的下载流程都不允许触碰 `< OTA_SLOT_A_ADDR` 的地址 |
| 镜像份 | `0x08040000`（2 KB 页） | 更新 **Slot B** 时随 Bank2 一起被擦 | 所以必须有另一份；主份在这次擦除中安然无恙 |

**每份页内再放两份结构体副本**（偏移 `0x000` 与 `0x400`），结构见 `ota/common/ota_common.h` 的 `OTA_Cfg`：

```c
typedef struct {
  uint32_t magic;          /* OTA_CFG_MAGIC = "G4BL"，非法则本副本作废 */
  uint32_t seq;            /* 单调递增序号：多副本中取"有效且 seq 最大"者为当前值 */
  uint32_t state;          /* OTA_ST_IDLE_A / IDLE_B / TRIAL_A / TRIAL_B */
  uint32_t trialLeft;      /* 试运行剩余复位次数（仅 TRIAL 有意义） */
  uint32_t slotCrc[2];     /* [0]=Slot A 净固件 CRC32，[1]=Slot B */
  uint32_t slotSize[2];    /* [0]=Slot A 净固件字节数，[1]=Slot B */
  uint32_t slotVersion[2]; /* [0]=Slot A 版本，[1]=Slot B（编码 0xMMmm0000） */
  uint32_t lastError;      /* 最近失败原因，现场诊断用（OTA_ERR_xxx） */
  uint32_t crc;            /* 对 [0, offsetof(crc)) 的 CRC32 —— 覆盖除自身外全部字段 */
} OTA_Cfg;
```

容量核算：`sizeof(OTA_Cfg) = 12 × u32 = 48` 字节（成员全是 `uint32_t`，结构无填充；
`offsetof(crc) = 44`，48 是 8 的倍数）。两份副本位于页内 `+0x1D8` 与 `+0x400`，
互不重叠且都 8 字节对齐，一页 2 KB 容纳两份副本后仍有约 1.9 KB 余量。

> ⚠️ **三方一律用 `sizeof`/`offsetof`，禁止写字节数字面量**。这个结构曾被误算为 36 字节
> （把"9 个字段"当成"9 个 u32"，漏算了 3 个 `[2]` 数组的第二个元素）；若照错值读写记录，
> `lastError`(40) 与 `crc`(44) 会落在未写入区，配置副本校验必然失败且**是静默失败**。
> `ota_common.h` 已用编译期 `#if` 把 `sizeof(OTA_Cfg) == 48` 与 `offsetof(crc) == 44` 锁死。

## 2. 掉电安全的写策略（**这是参数区唯一的难点**）

### 2.1 问题

Flash 只能"1→0"，写入前必须整页擦除。而**同一页内存放着两份副本** —— 擦一页会把两份都清掉，一旦此刻掉电，状态就永久丢失（等于变砖）。

### 2.2 解决办法：副本放在不同页，且写入时"读-擦-回写"

本方案把两份副本放在**两个不同的物理页**（`0x08000000` 与 `0x08040000`），因此：

* 页面级的擦除只会毁掉**其中一份**，另一份完好；

而**同一页内的两份副本**（`+0x000` / `+0x400`）是为"单页内也能取新"准备的兜底，写入时必须遵循四步：

```
BL_ParamStore(newCfg):
 1. 读整页(2KB)到 static 暂存区
 2. 确定"当前有效副本偏移" cur_off（有效且 seq 大者）
 3. 目标偏移 dst_off = 同页内另一个偏移（+0x000 与 +0x400 互为另一份）
 4. 擦除该页  →  把暂存区里"非 dst_off 的那份"原样回写  →  再把 newCfg(seq=cur.seq+1) 写入 dst_off
 5. 整页回读校验，失败则把状态标记为 lastError 并重试一次
```

> **为什么必须回写另一份**：整页擦除是无差别的，如果不回写，`+0x400` 的旧副本就没了；虽然另一物理页的主/镜像份仍在，但那会导致"两份都只剩一个副本"的窗口期，抗掉电能力从 4 份降到 2 份。**回写是廉价且必要的。**
>
> 这段逻辑就是 `ota/common/ota_common.h` 里 `OTA_CFG_SLOT_OFFSET / OTA_CFG_SLOT_MIRROR_OFF` 存在的意义，也是 Bootloader 实现任务中标记的"核心正确性点"。

### 2.3 读取策略

4 个候选（2 页 × 2 副本）逐一校验 `magic == OTA_CFG_MAGIC` 且结构 CRC 自洽，从**全部通过校验**的候选中取 `seq` 最大者。若 4 个全无效 → 用编译期默认值重建：

```c
{ .magic = OTA_CFG_MAGIC, .seq = 1, .state = OTA_ST_IDLE_A,
  .trialLeft = 0, .slotCrc = {0,0}, .slotSize = {0,0},
  .slotVersion = {0,0}, .lastError = OTA_ERR_NONE }
```

`slotSize[0] == slotSize[1] == 0` 表示两槽都无效 → Bootloader 进入 **recovery 模式**（等 PC 刷写），这是全新芯片/首次烧录后的正常起点。

## 3. 状态机

### 3.1 四个状态

| 状态 | 含义 | BL 上电后的动作 |
|---|---|---|
| `IDLE_A` | 稳态，A 槽是经过现场验证的已知良好固件 | 直接校验 A 并跳转（1s 启动窗口内若无诊断请求） |
| `IDLE_B` | 稳态，B 槽已验证 | 直接校验 B 并跳转 |
| `TRIAL_A` | A 槽是**新固件**，尚未被 APP 确认 | `trialLeft--`；按剩余次数决定"继续试"或"回滚到 B" |
| `TRIAL_B` | B 槽是新固件，尚未确认 | 同 TRIAL_A，回滚方向是 A |

> **关键点**：`TRIAL` 只表示"新固件第一次跑"，**不代表"没有可用固件"**。正因为另一槽里还留着旧的已验证固件，回滚才有地方可回。因此方案里**绝不允许"把新固件覆盖写进正在运行的槽"** —— 那会在写入过程中同时毁掉新旧两份，从而丧失回滚能力。目标槽恒为"非活动槽"（由设备自己判定，见协议 §4.1），这就是这条约束在协议层的落地。

### 3.2 状态迁移图

```
                        ┌──────────────────────────────────────────┐
                        │            首次上电 / 控制区无效            │
                        └───────────────────┬──────────────────────┘
                                            ▼
                                      ┌───────────┐
                          ┌──────────►│  IDLE_A   │◄──────────┐
                          │           └─────┬─────┘           │
                          │                 │ 下载到 B 槽并 FF02 activate
                          │                 ▼                 │
            试运行失败回滚  │           ┌───────────┐   试运行失败回滚
            (trialLeft=0) │           │  TRIAL_B  │           │
                          │           └─────┬─────┘           │
                          │                 │ FF04 commit（APP 自检通过）
                          │                 ▼                 │
                          │           ┌───────────┐           │
                          └───────────┤  IDLE_B   ├───────────┘
                                      └─────┬─────┘
                                            │ 下载到 A 槽并 FF02 activate
                                            ▼
                                      ┌───────────┐
                                      │  TRIAL_A  │
                                      └───────────┘
```

### 3.3 试运行计数（`trialLeft`）的精确语义

* `FF02`（激活）把 `state = TRIAL_<目标槽>`、`trialLeft = OTA_TRIAL_BOOT_LIMIT = 3`。
* 每次 BL 上电且 `state ∈ {TRIAL_A, TRIAL_B}`：
  1. **先把 `trialLeft` 减 1 并写回控制区**（顺序很重要：必须早于跳转判定，这样"跳进去就死、连复位都来不及写"的场景也能正确累加）；
  2. 若减后 `trialLeft == 0` → 判定新固件起不来 → 切到另一槽、`state = IDLE_<另一槽>`、`trialLeft = 0`、`lastError = OTA_ERR_TRANSFER`，然后校验并跳转另一槽；
  3. 否则正常校验并跳转当前 TRIAL 槽。
* **APP 自检通过后**调用 `31 01 FF04`（Commit，或直接本地 `Ota_ParamCommitTrial()`）：`state = IDLE_<当前槽>`、`trialLeft = 0`。此时新固件正式"转正"，旧槽成为下一次升级的目标。

**计数逐步对照（务必与实现一致）**：

| 上电次序 | BL 读到的 trialLeft | 递减后 | BL 行为 |
|---|---|---|---|
| 激活后第 1 次 | 3 | 2 | 跳转新槽，APP 进入试运行 |
| 第 2 次 | 2 | 1 | 同上 |
| 第 3 次 | 1 | 0 | **判定失败，回滚到旧槽** |
| 第 4 次 | 0 | — | 已在 `IDLE_<旧槽>`，正常跳转旧固件 |

> 因此"激活后容许 2 次复位仍不确认，第 3 次即回滚"。若想放宽，只需调大 `OTA_TRIAL_BOOT_LIMIT`；**不要**把递减放到跳转之后（跳进去 HardFault 就不会再执行到了）。
>
> 为什么是 3 次：需要容忍"上电后立刻掉电/复位"的正常抖动（例如现场供电不稳、调试器复位），同时避免无限重试。3 次 ×（启动窗口 + 校验）约 3 秒，工程上足够且不拖长失败恢复时间。

> **注意**：`TRIAL` 期间 BL 的启动窗口**跳过等待**（直接校验跳转），否则每次上电都要多等 1s；只有 `IDLE` 状态才等启动窗口。这样既能快速启动正常固件，又保留了长按进入 BL 的能力。

## 4. APP 侧的四个必需动作

### 4.1 `Ota_Init()`：启动时挂载

```c
void Ota_Init(void)
{
    /* 1. 读取控制区（复用 BL 的相同结构；APP 侧只读多、只在 Commit 时写一处） */
    Ota_ParamLoad(&s_cfg);

    /* 2. 若本槽处于 TRIAL，启动一个延时确认定时器 */
    s_selfCheckPending = (s_cfg.state == OTA_ST_TRIAL_A && s_runningSlot == 0U) ||
                         (s_cfg.state == OTA_ST_TRIAL_B && s_runningSlot == 1U);
    s_selfCheckTick    = HAL_GetTick();
}
```

`OTA_STATE_ACTIVE_SLOT(state)` 宏从状态反推活动槽（`IDLE_A/TRIAL_A → 0`，`IDLE_B/TRIAL_B → 1`）。

### 4.2 `Ota_Task()`：自检通过后落定

试运行固件必须"自己证明自己活着"。判据用工程里现成的东西，不新增语义：

| 判据 | 来源 | 建议阈值 |
|---|---|---|
| FDCAN 已成功收发过至少一帧 | `CAN_GetStats()->txAckCount > 0` 且 `rxCount > 0` | — |
| CAN 自检通过 | `CAN_SelfTest()` 返回值 | — |
| 主循环稳定运行 | `HAL_GetTick()` 已走过 `OTA_SELFCHECK_MS` | 3000 ms |

三者同时满足且 `s_selfCheckPending` 为真 → 发 `31 01 FF04` 落定（或直接调用 `Ota_ParamCommit()` 本地写，无需走 CAN）。**若 3 秒内没满足**（例如 CAN 从未通信成功），就**不落定**，让 BL 在后续复位中按 `trialLeft` 自动回滚。

> 这条设计的价值：**回滚不是"靠人发现坏了去手动退"，而是"固件自己没能在 3 次启动内证明健康就自动退"**。这是 OTA 从"能升级"到"敢升级"的分界线。

### 4.3 `0x2E F190 01`：请求下次进入 Bootloader

置一个 RAM 标志 + 写控制区 `state` 不变但把 `lastError` 清 0，然后 `NVIC_SystemReset()`。BL 上电后按 `IDLE` 流程走到启动窗口，若此时 PC 已在发诊断请求就会留在 BL。**更稳妥的做法**是同时设置一个持久请求标志（可用 `OTA_Cfg` 的保留字段或 `trialLeft` 之外的字段），本方案用 `0x2E F190` 只做"软请求"，实际进 BL 由 `11 01` 复位 + 启动窗口内的诊断请求共同保证。

### 4.4 页面缓冲与 Flash 编程（`ota_agent.c` 的核心）

APP 收到 `0x36` 时**不能每块都擦写**（2 KB 页要凑满再写，否则一页被写 17 次会反复擦除）：

```
static uint8_t s_pageBuf[OTA_FLASH_PAGE_SIZE];   /* 2 KB */
static uint32_t s_pageFill;                      /* 当前已填充字节数 */
static uint32_t s_downloaded;                    /* 本次累计接收字节数 */
static uint32_t s_runningCrc;                    /* 边收边算的 CRC32 */

收到 0x36 <seq> <data>:
  crc 更新(data)
  while (data 有剩余):
      拷贝 min(剩余, 2048 - s_pageFill) 到页缓冲
      if (s_pageFill == 2048):
          HAL_IWDG_Refresh(&hiwdg);              ← 页编程前喂狗
          BL_FlashWrite(目标地址, s_pageBuf, 2048)
          目标地址 += 2048; s_pageFill = 0
  回 76 <seq>
```

`0x37` 时把残余 `s_pageFill` 用 `0xFF` 补齐到 8 字节对齐后写盘。**只有写完最后一页，`31 01 FF01` 的 CRC 校验才有意义**。

## 5. 风险与边界条件清单

| 场景 | 系统行为 | 验证方法 |
|---|---|---|
| 传输中途掉电 | 控制区状态未变（仍是 `IDLE_A`），BL 启动时校验 A 有效 → 跳 A，旧固件照常运行。目标槽 B 处于"部分写入"状态，但**不影响启动**，因为没人会去校验它 | 刷写 50% 时断电，重新上电应正常启动旧固件；再上电刷写可覆盖重来 |
| 传输中途 CAN 断线 | `IsoTp` 在 1s（N_Cr/N_Bs）后超时，`Uds_Task` 报 `diag: isotp timeout`；下载状态保持，可用 `--resume N` 从第 N 块续传（前提是**设备未复位**） | 拔掉 CANH 再插回，观察日志与 `rxOverruns` |
| `0x36` 写 Flash 失败 | 返回 NRC `0x70`，放弃本次下载，`lastError = OTA_ERR_PROGRAM`；已写入的页留在目标槽（无害，下次擦除覆盖） | 故意传超长镜像触发长度校验 |
| 新固件 CRC 正确但无法运行 | `TRIAL` 计数从 3 递减到 0 后**自动回滚**到旧槽 | 见 [05 测试文档](05-测试与验收方法.md) 的回滚用例 |
| 两槽都无效（首次烧录/被全擦） | BL 进入 **recovery 模式**，串口打印等待刷写，CAN 保持在线 | 用 Keil 只烧 BL、不烧 APP，上电应停在 BL 并能被上位机刷写 |
| 控制区两份副本都被破坏 | 按默认值重建（`IDLE_A`、两槽 size=0）→ 走 recovery | 用调试器把两页都改成 `0x00`，上电应进 recovery 而不是死锁 |
| `trialLeft` 写入过程中掉电 | `seq` 与结构 CRC 保证读到的是"改前"或"改后"的完整值，不会读到半个结构 | 单元级：`ota_param` 的读函数必须对 CRC 失败做跳过 |
| 误把 BL 区当下载目标 | `BL_FlashErase/Write` 的 `< OTA_SLOT_A_ADDR` 保护直接返回 `OTA_FLASH_ERR_PROTECT`；`0x34` 也会以 NRC `0x31` 拒绝 | 故意用 `34 00 44 08 00 00 00 ...` 请求下载，应被拒 |

### 5.1 未消除的残余风险（M6 / M13，2026-10-07 复核后保留）

以下两条**经复核后决定不改代码**，属已知残余风险，上板前须知悉。

#### M13（真实单点失效）：擦 PRIMARY 页期间掉电会变砖，只能 SWD 救

**机制**：PRIMARY 控制页（`0x08000000`）与 BL 自己的向量表**同页**。`BL_ParamStore()`
擦该页时（约 25ms），页 0 全为 `0xFF`，BL 向量表随之消失。此刻掉电 → 复位后
CPU 从 `0x08000000` 取向量，`SP`/`PC` 全为 `0xFFFFFFFF` → **HardFault → lockup**，
且复位后仍是 `0xFFFFFFFF`，**等同变砖，只能用 SWD 救回**。

代码已做的缓解（`bl_param.c` [PARAM-STEP-1..3]）：
* 擦除前先把整页读到 `s_pageBuf` 暂存；
* 擦除窗口全程 `__disable_irq()`（窗口约 30ms，远小于 IWDG 3s），避免挂起的
  SysTick 按"已擦掉的向量表"取向量；
* 擦后按 8 字节双字**从 0 起**回写，**向量表最先落盘**，把砖化窗口压到最小；
* 只写镜像中非 `0xFF` 的双字，避免无谓编程。

**为什么仍不能消除**：这是 Flash 擦除的物理特性——擦除期间掉电必然丢页，软件无法
规避。彻底解法只有两条，都超出本轮范围：
1. **把控制区挪出 BL 代码页**（例如放到 Bank2 的独立页，或调整 `bl.sct` 让页 0
   只放向量表）。这是本项目"第一道防线"的设计意图，但需要重新核算分区表并重刷。
2. **改用 STM32G474 的双 Bank + Option Bytes 掉电保护**，或启用读保护（`RDP`）。

> ⚠️ **上板操作纪律**：升级 BL/APP 固件或改动分区表时，**必须接 SWD 且不要中途
> 断电**。日常 OTA 走 MIRROR/跨页冗余路径不触碰 PRIMARY 页，不受此风险影响。

#### M6（可接受）：错误路径落盘 `lastError` 会短暂阻塞 CAN 轮询

**机制**：下载失败时 `BL_DiagRecordError()` → `BL_ParamStore()` → 擦写配置页，
期间 `__disable_irq()` 约 20~40ms，`BL_CanPoll()` 完全停摆，3 深度 RX FIFO 溢出丢帧。
表现形式可能是"莫名其妙的 NRC 0x73"。

**为什么不改**（复核结论）：
1. 落盘是**幂等短路**的（`if (cfg.lastError != otaErr)` 才写），同一错误只落盘一次；
2. 该路径只在**已经失败**的降级场景触发，此时 `s_dl.active` 已置 `false`、事务已结束，
   总线上丢的帧无关紧要——真正需要担心的是"正常传输中丢帧"，而那条路径不碰配置页；
3. 报告原建议的"错误只置内存标志、事务结束后统一落盘"在下载已失败时**时机不存在**
   （事务已经结束），且会让 `lastError` 丢失，破坏现场诊断能力——而该字段正是为此存在。

结论：保留现状。代价是失败路径上丢几帧，换来的是错误码可靠落盘。
