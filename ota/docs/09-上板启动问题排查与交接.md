## 2. 根因：镜像头魔数字节序写反（已修）

**契约**：`OTA_IMG_MAGIC = 0x47344F54`（"G4OT"），BL 的 `BL_ImageRdU32()` 按**小端**读取：
`p[0] | p[1]<<8 | p[2]<<16 | p[3]<<24`。

因此 Flash 里应存放字节 **`54 4F 34 47`**。

**实际错误**：产线镜像生成器用 `struct.pack_into('>4s', hdr, 0, b'G4OT')`（**大端**）写入，
Flash 里变成 `47 34 4F 54`，BL 读回 `0x544F3447` ≠ `0x47344F54` → 校验失败
（`result=0x00000001 = BL_IMG_ERR_HDR_MAGIC`）。

**定位方式**（关键）：在 BL 里直接打印它读到的值：

```
TRACE magic: slot=0 base=0x0800C000 m[0]=0x544F3447 m[+0x100]=0x0800C35F
```

`0x544F3447` 正是 `0x47344F54` 的字节反转 —— 一眼定案。

**已修**：`ota/scripts/make_factory_image.py` 改为 `struct.pack_into('<I', hdr, 0, OTA_IMG_MAGIC)`，
并在注释中写明字节序陷阱。

## 3. 排查过程中被证明是"错误做法"的手段（勿重蹈）

| 做法 | 问题 | 正确做法 |
|---|---|---|
| 用 `dump_flash.py` 的解析结果判断魔数正确性 | 该脚本当时用**大端**（`'>I'`）解析，把反转的魔数报成"正确"，**给出假阳性**，误导数轮 | 解析必须与 BL 一致用**小端**；已修正，并新增"BL 会不会接受该镜像"判据 |
| 用 `mode=UR` 连接后读 PC 判断"是否在运行" | `mode=UR` 是**复位下连接**，**连接即 halt**，PC 永远停在复位向量 `0x08000324` | 判断运行状态必须**断开调试器**冷启动，或显式 `-run` 后立刻读 PC |
| 反复"改一版→烧一版→试一版" | 每轮信息量太小，来回多轮 | **一次加足打点**，用一次烧录拿到全部信息 |
| 把芯片读回内容当作"当前状态" | 读回若不在失败之后立即做，就是过期信息 | 失败后**立即**读回 |
| 推测"HSE 晶振坏了" | BL 日志明明打了 `clock HSE+PLL 150MHz OK` | 先读**选项字节**（一条命令即可排除 BOOT0/RDP/DBANK 整类可能） |

## 4. 下一步（唯一待做的一步）

镜像头已修正，当前芯片内镜像经读回验证为**有效**。需做一次**不带调试器**的冷启动：

```
1. 拔掉 ST-Link（完全断开调试连接）
2. 板子断电，等 2 秒
3. 上电
4. 观察串口（COM5 @115200）
```

### 预期与判读

| 串口输出 | 含义 | 下一步 |
|---|---|---|
| `TRACE [8c] validate OK -> jumping`<br>`BL: jump to APP slot 0 base=0x0800C080 size=...` | ✅ 跳转成功 | 看 APP 是否打印 `main: led-bsrr-state M3` |
| `TRACE [8d] FAIL result=0x2` | 头 CRC 问题 | 重新生成并烧产线镜像 |
| `TRACE [8d] FAIL result=0x3` | 净荷 CRC 问题 | 同上 |
| 完全不打印 | BL 未运行 | 检查是否仍连着调试器 |

### 若 APP 不打印

APP 已加**早期 LED 打点**（`HAL_Init` / 时钟 / 串口三处），
因为 `HAL_Init()` 与 `SystemClock_Config()` 都在 `BSP_UART_Init()` **之前**，
卡在那里串口永远不会有输出：

| LED 闪 N 下 | 含义 |
|---|---|
| 1 下 | HAL_Init 完成，MCU 在执行 APP |
| 2 下 | 时钟配置成功 |
| 3 下 | 串口就绪（之后有文字日志） |

只闪 1 下 → 卡在 `SystemClock_Config()`；一下不闪 → APP 未被跳转到。

## 5. 恢复/重烧完整步骤

```powershell
cd D:\DSH\OTA_Bootloader

# 1) 烧 Bootloader（仅当 BL 需要更新时；每块板一次）
python ota/scripts/flash.py bl --yes

# 2) 生成产线镜像（裸 APP -> 32B 头 + APP，落槽基址 0x0800C000）
python ota/scripts/make_factory_image.py --hex firmware/G474_A.hex --slot A --version 3.0
python ota/scripts/make_factory_image.py --hex firmware/G474_B.hex --slot A --version 3.0

# 3) 烧（板A 烧 A 角色、板B 烧 B 角色）
python ota/scripts/flash.py --file firmware/G474_A_factory.hex --yes   # 板A
python ota/scripts/flash.py --file firmware/G474_B_factory.hex --yes   # 板B

# 4) 校验芯片内容（读回并按 BL 判据核对）
python ota/scripts/dump_flash.py --all
```

> ⚠️ `flash.py` 默认只写不擦（`-w` 不带 `-e`），因此 **BL 与 APP 互不影响**。
> 切勿用 `--erase-all`，那会同时擦掉另一组件与配置区。

## 7. 关键教训

1. **让设备自己说出它读到了什么**，而不是用工具间接推断。
   `TRACE magic: m[0]=0x544F3447` 一行就终结了数轮猜测。
2. **验证工具本身也要被验证**。`dump_flash.py` 的大端解析与 BL 的小端读取不一致，
   导致"用错工具验证错的东西 → 得到全对结论"。
3. **调试器会改变被观测对象**。`mode=UR` 连接即 halt，
   用它判断"是否在运行"必然得到错误结论。
4. **契约常量要写明字节序**。`0x47344F54` 这个值"本身"就是小端序列，
   极易被误当成"要按大端写字节串"——已在代码注释中标明。
